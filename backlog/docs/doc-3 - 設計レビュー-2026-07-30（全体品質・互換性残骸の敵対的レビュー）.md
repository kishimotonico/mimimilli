# 設計レビュー 2026-07-30（全体品質・互換性残骸の敵対的レビュー）

未公開・破壊的変更OK・DBはキャッシュという前提で、不要な互換性維持・フォールバック・過剰な複雑さを中心にプロジェクト全体を点検した。レビュー担当5（server×2 / shared / client×2）+ Codex全体レビューで指摘を収集し、確定前に全件を敵対的検証（反証担当2＋追加2）に通した。確定した指摘は TASK-129〜149 と DRAFT-33 に起票済み。この文書は起票に載らなかった判断と、既存ドラフトへの追加材料を残す。

## 反証されて起票を見送った指摘

- catalog データ補正マイグレーション（0006〜0008）をやめてバージョンbump全再作成に統一する案: 反証成立。0006/0007は通常のスキーマ変更で、データ補正は0008のみ。bump運用にすると audio_probe_cache（実測プローブキャッシュ）が全損し、ライブラリ全体の再プローブが必要になる。0008の「壊れた行だけ補正」は意図的な設計（TASK-91/92の経緯、tests/real/catalogProbeCacheMigration.test.ts 冒頭コメント）。現行の使い分けを維持する
- fixture の dlsiteFetch が force 引数を無視する件: キャッシュ概念がない fixture の意図的な単純化で問題なし
- 補記: resumeV1Pending / migrateResumeV1 は当初「毎スキャン動く恒久機構なので残す」と判定したが、後段の調査で resume_v1_pending へ書き込む本番コードは旧単一DB取り込みのみと判明し、TASK-130 の削除対象へ拡大した（v1 = ADR-0008以前の旧単一DB時代のresume形式。Tauri期のことではない）

## 仕様簡素化の検討結果（2026-07-30 第2ラウンド）

採用（起票済み）:

- DLsite通知3種の契約統合（TASK-149）: shared のスキーマ2系統・adapter メソッド2本・route の parse-failed 特別分岐を discriminated union に統合。TASK-132（client側）と合わせて全層一貫

推奨したが未決（ユーザー判断待ち）:

- 検索プリセットの削除断行（DRAFT-30）: server実装・search_presetsテーブル・sharedスキーマ・fixture実装で計200〜250行超。client利用ゼロ、requirements-v4 に「プリセット」の記述なし。スマートフォルダー（ルールビルダー）が構造的に上位互換。失うものは実質ゼロ

検討して見送った案（蒸し返さないための記録）:

- ビュー軸（all/recent/added/fav/unplayed/missing）とスマートフォルダーの概念統合: ビューは filterByView の約20行の単純switch。統合にはルールエンジンへ日付・真偽値・enum比較の追加が必要で、統合コストが現状維持を上回る。固定ビュー/汎用ルールの二層が最もシンプル
- SearchPreset と SmartFolder の統合: 評価モデルが根本的に異なる（サーバー側ルール評価 vs クライアント側の検索状態再適用）。統合は複雑化
- last-played と resume のエンドポイント統合: 実測で頻度が1桁以上違う（resumeは再生中5秒間隔、last-playedはトラック読み込み毎に1回）。HANDOFF の「高頻度のため分離」は実測で裏付けられた。分離維持
- fixture シナリオ（default/empty/new-work/errors）の削減: 4つとも dev script・テスト・ビジュアルテストで現役
- navigation の「URLを正としてatomを廃止」する所有権転換: filesSelectedPath の絶対パス（URLは相対segments+rootFolder依存）と filesDirection（URLに存在しない純UI状態）があり、置き場所を変えるだけに終わる。改善するなら push/replace 宣言の単一ヘルパー集約（TASK-145のnotes参照）
- POST /export の削除: requirements-v4 §10 は「将来検討」だが実装40行で複雑さの温床になっておらず、削除は動く機能を失うだけ。docs側を実態に合わせる程度でよい

shell.css の見積もり（DRAFT-29の材料）: 2653行の内訳はレイアウト系宣言727・意匠系357・トークン参照466・単純フラットセレクタ169（約44%）。Tailwind utility 移行で現実的に削れるのは全体の15〜25%程度。大幅圧縮ではなく「レイアウトはutility化、意匠・状態・アニメーションはコンポーネントクラス存続」の併存が妥当

## 起票しなかった軽微な観察

- usePlayer.ts の controller state を atom 経由で runtime ref へ再複製する構造（Codex指摘#26）: 同期コマンドが古い playbackRate を読む可能性という指摘だが、実害の再現経路を確認できておらず、修正はプレイヤー中核に触るためリスクの割に益が薄い。プレイヤーを触るタスクのついでに controller.getState() 直接参照へ寄せるか検討
- playlist/track の JSON 列と正規化表の二重保存（catalogSchema.ts:34,48以降、workRepo.ts:1200）: 同一トランザクション内で更新されており現状は整合。どちらを正とするかは DataAdapter 分割（DRAFT-28）とセットで整理
- scan の SSE・ジョブ管理（routes/scan.ts、scanJobManager.ts）の複雑さは、リロード後の再接続・Last-Event-ID replay という実要件に見合っており過剰実装ではないと判断
- DataAdapter 34操作は全て呼び出し元1箇所（routes直結）で、「未使用メソッド」による削減余地はない。縮小は機能削除（プリセット等）と統合（TASK-149）で行い、その後に DRAFT-28 のポート分割を検討する順序が良い

## DRAFT-28（server構造改善）への追加材料

Codexレビューで得た、着手時に使える具体観測。

- DataAdapter は約34操作（adapter.ts:96）。real/index.ts は1158行の単一factoryで、real と fixture が別々のDLsite状態遷移を持ち、bulk対象・タイトル保護・URL/カバー適用・エラークリアの挙動が既に分岐している。状態遷移は共通のapplication層へ一本化する
- DLsiteジョブ状態がモジュールグローバル（routes/dlsiteProgress.ts:17）。全 createApp() が currentJob/queue/listener を共有し、並列テストやVite再ロードで混線する。DlsiteJobManager をインスタンス化して composition root で注入する
- scanJobManager.ts:9,173 が routes/dlsiteProgress.ts へ逆依存している（application→route層）
- routes/dlsite.ts:18 が real adapter 固有例外（dlsiteScheduler.ts）を import している
- 本番bootstrapから終了処理を呼べない。real adapter の close()（real/index.ts:131）は index.ts:23 で DataAdapter 型に消え、SIGINT/SIGTERM でジョブ取消やDB closeができない。composition root が {adapter, dispose} と lifecycle を持つ
- メディア境界が route と adapter に分裂している。adapter.ts:55 が ETag などHTTP概念を持ち、routes/media.ts:51 が FS open と Range 処理を行う。メディア専用ポートに寄せる
- core の純度: worksQuery.ts:17 と smartFolder.ts:62 が Date.now() / crypto.getRandomValues() を直接呼ぶ。now/seed は評価コンテキストとして注入する
- core/dlsiteTitle.ts:1 が node:path.basename と real の physicalPath 表現に依存している。sourceFolderName を adapter 側で正規化して渡す
- PATCH /works/:id は bookmark を先に user DB へ確定してからメタ更新するため、メタ失敗時に bookmark だけ残る（real/index.ts:696）。.meta.json の atomic write を先行させ、catalog/user を後追いにする
- 関連する具体バグは TASK-141（metaパス対応の固定）として先行起票済み

## DRAFT-29（client構造改善）への追加材料

- settings の購読と意味付けが App.tsx:44・useNavigationHistory.ts:92・FilesBreadcrumbs.tsx:11 に分散。setup判定を専用gateへ移し、ready後は Files 境界から root を供給する。関連バグは TASK-142 として先行起票済み
- Files の選択状態が絶対パス（features/files/model/atoms.ts:9）とURL相対segments（navigationUrl.ts:13）の二重表現で、変換のために useNavigationHistory.ts:98 に pending state と settings 依存が生じている。ルート相対segmentsへ統一する
- work entity 境界に DLsite 機能が混在（entities/work/api.ts:17以降の通知/fetch/apply/bulk）。features/dlsite か entities/dlsite へ移し、query key と invalidation も同じ境界へ

- WorkInfoDialog.tsx:7 が編集コンポーネント DlsiteEditor の内部定数 STATUS_LABEL に依存（表示→編集の逆向き依存。境界整理時に共通化）
