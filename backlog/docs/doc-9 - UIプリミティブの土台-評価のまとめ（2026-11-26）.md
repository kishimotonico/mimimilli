# UIプリミティブの土台 評価のまとめ（2026-11-26）

クライアントのUIプリミティブ（メニュー、コンテキストメニュー、ポップオーバー、ダイアログ、コンボボックス、セレクト、ツールチップ、トースト、スライダー、タブ）を何の上に載せるかについて、3つの評価を集めた。最初の評価は Sonnet、セカンドオピニオンは Fable と Codex（Astra）。Fable と Astra には最初の評価の結論を伏せ、候補は例であって上限ではないと伝えた。決定は試作タスクで行い、ADRに残す。この doc はその根拠の記録で、記載のうち「学習知識」とあるものは裏を取っていない。

## 結論の比較

| 評価 | 推す案 | 次点 | 主な見送り理由 |
|---|---|---|---|
| Sonnet | Base UI | React Aria Components | Radix はコンボボックスが無く土台として欠ける。Headless UI はコンテキストメニュー・ツールチップ・スライダーが無く更新も止まっている |
| Fable | Base UI | Radix | Ark は AnimatePresence と組む公式の道筋が弱い。React Aria は独自のイベント層が Esc 規約・グローバルショートカットと噛み合いにくく、SR対応の強みがこのアプリでは効かない |
| Astra | Ark UI | Base UI | 試作で Ark の内部リスナーが Esc の順序を崩す、または退出時に外せないなら全面採用を見送り、同じケースを Base UI で試して切り分ける |

3者が一致した点:

- 候補は Base UI と Ark UI に絞れる
- ブラウザ標準中心（popover 属性、CSS anchor positioning）は、メニューの矢印移動・先頭文字移動・サブメニュー・チェック項目が標準に無く、結局自作になる。土台にはしない
- プリミティブごとに別ライブラリ（cmdk、Downshift など）は Esc とフォーカスの流儀が複数になる。コンボボックスやコマンドパレットに固有の要件が出たときに個別に検討する
- スタイル付きライブラリをテーマで寄せる案は、対象の確定やレイヤーの協調を解決せず、既存の見た目の調整幅を狭める
- 選定の重要度は中〜高。見た目と呼び出し側の書き方は薄い共通層で吸収できるが、Esc を誰が受けるか、フォーカスを誰が戻すか、外側クリック、ポータル先、モーダル時の inert、退出時のマウント境界は共通層を貫通する
- 試作は捨てる前提の worktree で、作品一覧の右クリックメニュー、dialog 内のメニュー、入れ子のポップオーバーを題材にする

## 争点: Base UI か Ark UI か

1. 多数の対象で1つのメニューを共有し、対象を渡せるか
   - Ark: `Menu.ContextTrigger` に `value` を渡して共有でき、`onTriggerValueChange` で対象が分かる（Astra・Fable、公式資料）
   - Base UI: `Menu.createHandle()` で複数トリガーの共有と payload があるが、`ContextMenu.Root` は `handle` を型から除いている。一覧の外枠を1つの Trigger にし、対象はアプリの状態で持つ形になる。利用側の `onContextMenu` は Base UI のハンドラより先に走り、`event.preventBaseUIHandler()` で止められる（Fable、Base UI 1.9.0 の配布物を読んで確認）
2. motion の AnimatePresence（ADR-0014）と組めるか
   - Base UI: 公式手順がある。`open` を制御し、`<AnimatePresence>{open && <Portal keepMounted>…}`、Popup は `render={<motion.div/>}`（Fable、ctx7）
   - Ark: 出入りは自前の Presence（`lazyMount` / `unmountOnExit`）が前提で、AnimatePresence との併用の道筋が弱い（Fable、学習知識）。Astra も open と present を分けて扱えるかを試作の確認点に挙げている

## 候補ごとの要点

### Base UI（@base-ui/react 1.9.0、2026-10、月次リリース、MUI）

- 部品: Menu、ContextMenu、Menubar、Popover、Dialog、Combobox、Autocomplete、Select、Slider、Tabs、Tooltip（Provider で共有遅延）、Toast、Checkbox、Radio、ScrollArea、Drawer など
- ContextMenu は Menu の部品をそのまま使う。CheckboxItem、RadioItem、Group の見出し、Separator、サブメニュー（safePolygon あり）。右クリック座標に幅0の仮想アンカーを作って開く。押したまま項目の上で離すと選べる。タッチは長押し500ms
- 項目は `data-highlighted` / `data-checked` / `data-disabled` を出し、`className` は状態を受ける関数にできる
- Portal は `container` を受け、dialog の中へ出せる
- Esc は document の keydown（バブル段）で受け、IME 変換中は無視し、閉じたら `preventDefault` する。`onOpenChange` の `eventDetails` に理由があり、キャンセルもできる。入れ子は内側から閉じる。ただし `defaultPrevented` は見ない
- フォーカス復帰は `finalFocus`（false / ref / 閉じ方を受ける関数）で指定できる。内部で FloatingFocusManager を使う
- Menu は既定で modal（スクロール固定、外側のポインター操作を止める内部バックドロップ）
- Dialog は top layer を使わない（`showModal` / `showPopover` の呼び出しが無い）
- Combobox に `virtualized` があり、@tanstack/react-virtual のデモがある（Sonnet）
- 依存は `@floating-ui/react-dom` 系で、`@floating-ui/react` を内部に取り込んでいる
- バンドル実測（esbuild、minify+gzip、react external）: context-menu のみで約62KB（Sonnet）

### Ark UI（@ark-ui/react 5.40.1、Zag.js、Chakra 系、更新頻度が高い）

- Menu に ContextTrigger、ボタン用 Trigger、子メニュー（`Menu.TriggerItem`）、チェック・ラジオ、typeahead、anchorPoint がある。通常の項目に検索用の `valueText` を渡せるので、件数やショートカットをラベルに混ぜずに先頭文字移動ができる（Astra、公式資料）
- 対象値の伝達と閉じた後のフォーカスは最近も修正されている（Astra、変更履歴）。試作時のバージョンを記録する
- 状態機械が挙動を強く握るので、規約から外れた調整がしにくい（Fable、学習知識）

### Radix UI（radix-ui 1.8.1）

- ContextMenu に Sub、CheckboxItem、RadioItem、Portal の `container`、`forceMount`、`onEscapeKeyDown` がある。Root の公開 API に `open` prop の記載が無く、開いたまま対象を替えるケースは同期の設計が要る（Astra）
- Combobox が無い。中心メンバーが Base UI 側へ移った（学習知識）。バンドルは context-menu で約33KB

### React Aria Components（1.22.1）/ react-aria フック層

- `MenuTrigger trigger="contextMenu"`（v1.20.0 から）で、ポインター座標、長押し、Shift+F10 などを扱う。`SubmenuTrigger`、`textValue` による typeahead。`UNSAFE_PortalProvider` で出力先を一括指定できる
- `isExiting` を使う motion 連携の公式例がある（Sonnet）。一方、アニメーションは `data-entering` / `data-exiting` と CSS が前提で、独自のイベント層が document で受けるショートカットや Esc の多段規約と噛み合いにくい（Fable、学習知識）
- 仮想化された多数の行で1つのメニューを共有する方法は資料で確認できず

### Ariakit（0.4.44）、Headless UI（2.2.10）、floating-ui 自作継続

- Ariakit: コンテキストメニューは `getAnchorRect` の作例で、専用部品が無い。1.0 未満
- Headless UI: サブメニュー、コンテキストメニュー、ツールチップ、トースト、スライダーが無い。2026-04 から更新が無い
- floating-ui 自作: `useListNavigation`、`useTypeahead`、`FloatingTree`、`safePolygon` はあるが、サブメニューのホバー判定、先頭文字移動、入れ子の Esc、フォーカス管理を自前で保守し続けることになる。「信頼できるライブラリは積極導入」の方針と逆

## 既存コードの現状（調査時点）

- 依存: react 19.2.7、@floating-ui/react 0.27.20、motion 13、@tanstack/react-virtual、lucide-react、Pragmatic drag and drop。UI部品ライブラリは無い
- メニュー: `shared/ui/Menu.tsx` の `PopupMenu`（矢印移動・先頭文字移動・サブメニュー・チェック項目なし）と、`role="menu"` を手書きした6箇所（WorkMetadataActions、PlaybackRatePicker、WorkPlayButton、SidebarAddMenu、LibrarySortMenu、FilesAddressBarMenu）
- ポップオーバー: `useAnchoredPopover` / `usePopoverDismissal` の利用が約12箇所。Esc は `usePopoverEscape` が document の keydown（バブル段）で受け、`preventDefault` で dialog の cancel を止め、`stopPropagation` する。モジュール内の配列でスタックを持ち、`defaultPrevented` と `isComposing` を見る
- ダイアログ: `useDialogModal`（`showModal()`、Tab 循環を手で補完、cancel、復帰）、`Modal`、`ConfirmDialog`、`Lightbox`。ポップアップは `anchor.closest("dialog") ?? document.body` へポータルして inert を避ける。Toast は `popover="manual"` で、最前面の dialog 直下へポータルする（`useTopmostOpenModalDialog`、`openModalDialogsAtom`）
- コンボボックス: `TagCombobox`（IME 変換中の Esc/Enter 無視、Esc 一段の規約まで作り込み済み）
- ツールチップは無く `title` 属性が約112箇所。スライダーは自作の `role="slider"`（NowPlayingScrub）と素の range 5箇所が混在。タブは ScanSidebar の手書き。素の `<select>` は SmartFolderDialog
- グローバルショートカットは `[role="menu"]`、`[role="listbox"]`、`[role="slider"]`、`dialog[open]` のセレクタに依存する（`useGlobalShortcuts.ts`）
- TASK-248 の計画に「フォーカス復帰は自前、FloatingFocusManager 禁止（ADR-0014 原則3）」。理由は軸A→Bの切替で退出中の旧Aが新Bからフォーカスを奪うのを防ぐため
- `contextmenu` のハンドラはどこにも無い

## 試作で確かめること（3者の指摘を統合）

- 対象と例外: 仮想化一覧の外に常設のメニューを1つ置き、右クリック時に入力欄・編集可能領域・実際に選択中の文字の上ならブラウザに任せる。それ以外は既定動作を止め、作品ID・座標・所属 dialog を一度に確定する。A を開いたまま並べ替え・スクロール・B の右クリックを続けても、表示と実行先が一致する。対象が消えたら操作を取り消す。メニューキー／Shift+F10 はフォーカス中の行を対象に、その矩形を起点にする
- ネイティブ dialog: 親子のメニューをともに dialog 内へ出し、端での反転、クリップ、ポインター到達、Tab の行き先を確認する。多重 dialog で最前面だけが操作できる。modal メニューのスクロール固定と aria-hidden が dialog 内で悪さをしない。成立しなければライブラリの Dialog 版と比べる
- Dialog を寄せる案（Fable）: Base UI の Dialog に寄せると、inert 回避のポータル、`openModalDialogsAtom`、Tab 循環の補完、cancel の伝播止め、Toast の付け替えが不要になり、Esc とフォーカスが1系統になる。代わりに z-index の階層管理が戻り、`dialog[open]` に依存する判定を書き換える
- Esc と IME: サブメニュー → メニュー → 既存ポップオーバー → dialog の順に一段ずつ閉じる。フォーカスがメニュー外・body にある場合、前面に別の dialog がある場合も。自作ポップオーバーの中にライブラリのメニューがあると、`usePopoverEscape` は `stopPropagation` しか呼ばず、ライブラリは `defaultPrevented` を見ないため、外側が閉じるか両方閉じる恐れがある。IME 変換中は Esc で候補だけが取り消され、Enter で実行やフォーム送信が起きない。矢印・先頭文字・チェック切り替えで背後のプレイヤーが反応しない
- 退出と復帰: AnimatePresence の条件描画で退出 DOM の寿命を管理できる。退出中に中身（対象の作品）が null にならない（対象は自前の状態で持ち、閉じても消さず次に開くとき上書きする、または AnimatePresence の内側の子へ props で渡す）。閉じた瞬間から退出中の要素は操作を受けない。A の退出中に B を開いても A の完了処理が B に影響しない。ライブラリの既定の復帰と自前の復帰を重複させない。Esc は同じ作品の起点へ、行が消えていれば一覧の有効なフォーカス位置へ戻す。軸A→B切替（`GroupValuePopover`）で旧Aがフォーカスを奪わない
- 仮想化: 開いている間の再取得・選択変更での中身と復帰先。外枠1つの Trigger で数千行のときに開閉で行が再レンダーしない。modal のスクロール固定でレイアウトがずれない
- その他: vitest + happy-dom で動くか、ドキュメント全体の `contextmenu` 抑止とライブラリの Trigger の `stopPropagation` の順序、Pragmatic DnD との干渉、本番ビルドのバンドル増分

## 置き換えの順番（案）

1. 試作（捨てる前提）でライブラリとダイアログの扱いを決め、ADR を書く
2. ボタン起点のメニューとポップアップの見た目・振る舞いをモックで相談する
3. メニュー（右クリック起点とボタン起点で項目定義を共有）とポップオーバーを同じ統合ブランチで寄せ、`usePopoverEscape` を削除して終える（移行中に新旧の Esc 処理が入れ子で混在しないように）
4. ツールチップ → セレクト、スライダー、タブ → コンボボックス（IME と Esc 規約を個別に検証してから）→ ダイアログとトースト（試作の判断に従う）
5. DRAFT-53（doc-8）

Astra は「右クリックメニューを試作し、同じ項目を使うボタンを1つ付ける。専用の見本画面だけでは仮想化とフォーカス復帰の不具合を見落とす」とも指摘している。共通層は薄く保ち、ライブラリの props を全部通す汎用ラッパーは作らない（ADR-0014 の汎用 Presence ラッパー禁止と同じ理由。Fable）。画面側にライブラリの store を渡さない（Astra）。
