数千〜数万件（想定5,000〜30,000作品）規模でのパフォーマンス調査（Codex読み取り専用調査+Claude裏取り）と、それを受けたタスク分割へのCodexレビューの記録。TASK-57〜63・73〜77・DRAFT-25 の背景資料。タスク本文の「2026-07-19のパフォーマンス調査」「Codexレビュー（2026-07-19）」は本docを指す。

関連: real側のSQL化はTASK-71のADR（永続化トポロジー・検索所有権）の決定を待つ（並行セッションとの調整済み。doc-1 も参照）。

## 調査の結論

5,000件では操作によって待ち時間が目立ち始め、30,000件では現状のまま安定運用するのは難しい構造。静的コード調査のみで実測ベンチは未実施。見積りは1作品あたり5〜10タグ・10トラック前後を仮定。

| 優先度 | 問題 | 対応タスク |
|---|---|---|
| 高 | listSummaries() がキャッシュなし・N+1クエリ・重いJSON全復元 | TASK-57 |
| 高 | クライアントがページング未使用で全件受信（スマートフォルダーも） | TASK-58/73/74 |
| 高 | グリッド/リストが全件DOM化。リストは全件の元画像を即時取得 | TASK-59/60 |

## 個別の問題（要点）

### listSummaries() の実コスト（TASK-57）

server/src/adapters/real/workRepo.ts:166。呼ぶたびに works 全列SELECT + タグ全件SELECT + 作品ごとに work_dlsite を1回SELECT（N+1）。30,000作品で約30,002クエリ/リクエスト。trackCount 算出のためだけに playlists_json を全件JSONパース（平均1KBなら生JSON約30MB、オブジェクト化後60〜120MB）。ほぼ全API（検索・ファセット・スマートフォルダー・FSブラウズ）が経由する。DLsite一括取得（real/index.ts:348 の getWork 逐次呼び）にも同種のN+1あり。

### ページング未使用と重いDTO（TASK-58/73/74）

クライアント buildWorksParams()（client/src/features/library/model/libraryPresentation.ts:23）が page/limit を送らず、サーバー paginate（server/src/core/worksQuery.ts:135）は両方指定時のみ slice → 通常一覧は常に全件転送。WorkSummary は physicalPath/urls/dlsite全体/全タグを含み30,000件で21〜45MB。総件数取得 searchWorks({limit:1})（useLibraryQueries.ts:61）は page 未指定のため実際は全件返る。スマートフォルダーAPI（routes/smartFolders.ts:42）はページング契約自体がない。

randomソート（worksQuery.ts:118）はリクエストごとに再シャッフルするため、ページングと非互換（ページごとに重複・欠落する）。seed方式・単一ページサンプル等の仕様決定が必須（TASK-73）。

### 全件DOM化と元画像eager取得（TASK-59/60）

WorkGrid.tsx はグリッド・リストとも全件 map()。content-visibility:auto はあるが React 要素は全件生成（30,000件で数十万DOMノード）。ジャスティファイドレイアウトは画像寸法確定ごとに全件再レイアウト、キーボード操作は全タイル querySelectorAll で O(N)。リスト表示 WorkRow.tsx:41 は CoverImg に requestWidth も loading も渡さず、全行が元画像を eager 取得（元画像平均500KBなら30,000件で理論上15GB）。

### 検索のデバウンス・中断なし（TASK-61）

TopBar.tsx:84 が1文字ごとにstate更新→React Query発行。fetch（shared/api/http.ts:61）に AbortSignal 未指定で古い検索もサーバーが最後まで処理。AbortSignal はサーバー内の同期SQLite処理を中断できないため、負荷削減の主役はデバウンス。日本語IMEのcomposition対応も必要。

### スキャン（TASK-62/75/76）

POST /scan は完了までHTTP保持（TASK-56のモーダルはUI上の継続のみで、サーバー側ジョブ化は含まない→TASK-76）。祖先除外 scanner.ts:293-295 が O(R²)（30,000候補で最大約9億比較）。markMissingExcept（workRepo.ts:270）は全seen IDの NOT IN 句で SQLite パラメータ上限に接近。全トラックの stat + audio_probe_cache のトラック単位SELECT。増分スキャン（TASK-75）は「mtime/size一致」だけだと音声削除・差替・カバー更新・ディレクトリ移動・重複UUIDを見逃すため、fingerprint対象の設計が先。

スキーマ変更の注意: TASK-57（track_count列）と TASK-75（fingerprint列）はどちらもDBスキーマ変更を伴い、このプロジェクトは user_version 変更でDBを作り直す設計（db.ts）。列追加をまとめるか、データ消失の扱いを決めて時期を調整する。

### サムネイル配信（TASK-63）

thumbnailCache.ts / routes/media.ts。幅指定ありは初回Sharp変換+WebP（single-flightあり）だが、異なるキーの並列数は無制限。ETag/Last-Modified/Cache-Control なしで304が使えず毎回 getWork()+SQL+stat。幅指定なしは元画像そのまま配信。immutable を使うならバージョントークン付きURL限定（DTOへのcover version搭載はTASK-58と調整）。

### SQLiteインデックス（DRAFT-25 / TASK-71）

現状のインデックスは点検索には十分だが、SQL検索移行時は works(status,id)/(added_at,id) 等の複合インデックスが必要。無条件に増やすと書込が遅くなるため、クエリ設計とEXPLAIN QUERY PLANを決めてから追加する。

## アーキテクチャ方針への言及

ADR-0004自身が「全件処理はスケールしなくなったら見直す」と明記しており、30,000件を正式ターゲットにするなら見直し時期。推奨は、routes層は薄いまま・fixtureは既存純粋関数を維持・realのみ検索・ソート・ページング・ファセット・スマートフォルダー候補抽出をSQL化し、純粋関数を仕様の参照実装として残して同一fixture投入によるSQL結果との契約テストで一致を担保するハイブリッド。日本語部分一致のFTS化は tokenizer/照合の仕様一致テストが必須。→ 決定はTASK-71のADRに集約（DRAFT-25はその後実測判断）。

SQL移行の要否判断は「速くなった」ではなく数値基準で行う。測定候補: 5,000/30,000件での cold/warm 一覧・検索・各sort・深いページ・facets・スマートフォルダーの p50/p95、サーバー最大RSS、レスポンスbytes、SQL発行数。

## タスク分割レビュー（Codex）の要点

- 旧TASK-58は広すぎるため3分割: TASK-58（DTO+getAllWorks整理）→ TASK-73（通常ページング）→ TASK-74（スマートフォルダーページング）。通知系フック（dlsiteMissingRjCode/dlsiteFetchFailed/dlsiteUnlinked）が getAllWorks() 依存で、DTOからdlsiteを外す+デフォルトlimit導入で壊れる/誤カウントになるため専用API化が必須（TASK-58のAC）
- 旧TASK-62は「計算量・上限対策（TASK-62）」と「増分スキャン（TASK-75）」に分割
- TASK-59のTASK-73依存はハード依存ではないが、TASK-73だけ先行リリースすると残件へ到達できないため、追加読み込みUIはTASK-73側・TASK-59はDOM最適化専任と役割分担
- Zodスキーマで型からフィールドを落としても転送削減は保証されないため、生HTTPレスポンスのJSONキー検査テストが必要（TASK-58のAC）
- 推奨着手順: 60 → 61 → 62 → 57 → 58 → 73 → 74 → 59 → 75 → 63 →（76・77は適宜）→ DRAFT-25はTASK-57/58後に実測判断

## 規模感の補足（数百〜数千件の場合）

数百〜数千件（〜3,000件程度）なら、インメモリ純粋関数設計のままで問題なく、SQL移行（DRAFT-25）・仮想化（TASK-59）・スキャン計算量（TASK-62）の実害はほぼない。その規模で唯一実害が出るのはリスト表示の元画像eager取得（TASK-60、件数でなく画像サイズが支配的）で、次いでN+1（TASK-57、毎リクエストの定常コスト）とデバウンス（TASK-61、UX品質）。
