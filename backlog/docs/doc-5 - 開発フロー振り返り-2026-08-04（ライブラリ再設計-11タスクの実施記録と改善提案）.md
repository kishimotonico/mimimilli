ライブラリ再設計（DRAFT-50 → TASK-178〜188）をマルチエージェント運用で実施した記録と、そこで見えた開発フローの問題点・改善提案。改善の採否は別途検討する。統括担当（Opus）視点で書いているため、統括の判断ミスも含めて記録する。

## 実施したこと

DRAFT-50 の確定仕様をもとに ADR-0012 を起こし、タスク11本に分割して実装した。体制は統括=Opus、実装=Sonnetサブエージェント複数、検証=Sonnet、仕様レビュー=別ペインのFable、実装レビュー=Codex。

完了タスク: TASK-178（軸値ファセット契約拡張）/ 179（概要面廃止・ホームビュー化）/ 180（ドリル機構と中間カラムの廃止）/ 181（値一覧本実装）/ 182（オーバーレイ群）/ 183（階層タグと仕上げ）/ 184（擬似タグの予約文字分離）/ 185（スマートフォルダーのフィルタ適用）/ 186（値選択後の作品一覧遷移）/ 187（ファセット件数の自軸除外カウント）/ 188（スキャン後クラッシュ修正）

このうち 184・185・186・187・188 は当初計画になく、レビューと検証で見つかって追加されたものである。5/11 が後出しで生まれた点は、計画の精度として記録しておく。

## 問題点

### 1. 同一作業ツリーでの並行実装（最大の損失）

複数の実装担当を1つの作業ツリーで並行させた。git のコンフリクトはほぼ起きなかったが、別の形で3つの実害が出た。

- **テスト結果が信用できない**: A が編集中のファイルを抱えたまま B が `pnpm check` / `pnpm test` / Playwright を回すと、B は自分と無関係な赤を見る。impl-184 は `pnpm check` のフラップに何度も付き合わされ、impl-182 は「ビジュアルテスト6件中6件失敗」の切り分けに時間を使った（実際には他人の編集途中が原因の可能性が高い状態だった）
- **統括の誤判断**: 上記を受けて統括が「その失敗は汚染だろう」と判断したが、実際には真の回帰だった（impl-182 の切り分けのほうが正しかった）。汚染された環境は、本物の不具合も偽物に見せる
- **コミットの切り分けが手作業になる**: 2人分の変更が混ざるため、統括がファイル単位で帰属を判定してからステージする必要が生じた。`libraryPresentation.ts` のように1ファイルに両者の変更が入ると判定不能になり、片方のコミットにもう片方のヘルパーが混ざった

後半で git worktree に分離してからは干渉がゼロになった。最初から分離すべきだった。

### 2. git コミット操作で他タスクの変更を巻き込んだ

TASK-178 のコミット時、`git add` でパス指定したにもかかわらず、既にステージ済みだった TASK-179 の削除4件が `git commit` に含まれた。`git commit` はインデックス全体をコミットするという基本を見落としている。復旧はできたがコミットの作り直しが発生した。

### 3. タスクの粒度が大きすぎた

TASK-183 は受け入れ条件12項目で、階層タグ表現・不要コード削除・インスペクタ統合・docs 追記・テスト追加が一体になっていた。AGENTS.md 自身が「1〜数PRで完結する見通し」を基準にしているのに守れていない。進捗が外から見えず、人間から「沼にはまっているのか」と確認が入る状態を作った。

### 4. 未検証の前提を引き継いだ（実害バグの見逃しにつながった）

「ビジュアルテスト3件は再設計前から失敗している既知の障害」という実装担当の報告を、根拠を確かめずに以降のタスク指示へ書き写した。実際にはその根拠が再設計後のコミット（TASK-179 適用済み）での確認であり、**再設計が埋め込んだスキャン後クラッシュ（TASK-188）がその中に隠れていた**。実利用でアプリがエラーバウンダリに落ちる実害バグである。

起点を遡って調べさせて初めて判明した。「既知の障害」「元から壊れている」という報告は、真のベースラインまで遡った根拠がなければ受け取ってはいけない。

### 5. ビジュアルテストが常時赤く、回帰検知能力を失っていた

上記クラッシュは `scan result dialog` の失敗として現れていたが、他が赤いために埋もれた。`library shell` は再設計着手前から30%の差分があり放置されていた。ベースラインのずれを放置すると、スイート全体が「常に赤いので誰も見ない」状態になり、新しい回帰を検知できなくなる。

### 6. レビューが遅く、手戻りになった

Codex レビューを3コミット積んでから回した。結果、指摘4件（うちP1が1件）が出て TASK-184・185 という手戻りになった。特に year 擬似タグの実タグ衝突（`year/2025` は ADR-0005 がユーザー定義タグの例として明示している）は統括の仕様判断の穴で、着手前にレビューしていれば TASK-180 の中で吸収できた。

### 7. 受け入れ条件に確定仕様を落とし損ねた

「値選択 → 結果面が作品一覧へ」は DRAFT-50 に明記されていたが、統括が受け入れ条件に書かなかった。実機検証で発覚し TASK-186 として作り直しになった。

### 8. 実機確認が後回しになった

dev server が落ちていたため、TASK-179〜184 の実装中は誰もブラウザで確認していなかった（実装担当は「起動済みのことが多い」という前提で動き、落ちていることに気づかないまま単体テストで代替した）。統括が起動し直して検証担当を立てるまで、実機確認ゼロで4タスクが積まれていた。

### 9. エージェントが報告を返さず、統括が状態を polling した

完了報告なしで待機に入るケースが繰り返し起き、そのたびに統括が `git status` やタスクの AC を見に行った。途中から「終わった AC は随時チェックを入れる」と指示して改善したが、最初からルール化すべきだった。

### 10. 統括が検証を自分でやっていた

`pnpm check` / `pnpm test` / Playwright を毎回統括が実行していた。AGENTS.md は統括担当が原則テスト実行をしないと定めているのに、コミット前確認を例外扱いしていた。人間に指摘されるまで気づいていない。検証の独立性も損なわれる。

## 改善提案

採否は検討に委ねる。効果が大きいと考える順に並べる。

### A. 実装担当は1タスク1 worktree を既定にする

同一作業ツリーでの並行実装を禁止する。統括が `git worktree add` でパスを用意し、実装担当にパスを渡す。統合は統括がマージで行う。

補足: Agent ツールの `isolation: "worktree"` は古いベースから切られる・成果が自動削除されるといった罠があるため、手動で worktree を作ってパスを渡す方式が安全（既存メモリ参照）。

### B. レビュー担当（Sonnet）を常設し、コミット前に必ず挟む

Fable への相談は頻繁にはできないため、日常のレビューは自前で持つ。今回 Codex が見つけた4件は、いずれも差分を丁寧に読めば出る類で、Sonnet で十分届く水準だった。

観点は「受け入れ条件の充足」ではなく **「報告に書かれていない副作用」** に絞る。実装担当は自分の変更が壊したものを構造的に見つけにくいため、そこだけを別の目でやらせる。

役割の使い分け:
- Fable（別ペイン）: 仕様判断・設計方針の妥当性。着手前に1回
- レビュー担当（Sonnet）: 実装差分の副作用。1タスク完了ごと
- Codex: 節目での敵対的レビュー。複数タスクの統合後

### C. ビジュアルテストのスイートを2つに分ける

現状は1つのスイートが性質の違う2つの仕事を兼ねており、片方（ピクセル比較）が死んだせいでもう片方（実ブラウザでの動作確認）も埋もれた。

- **ブラウザのスモークテスト**（残す・強化）: role ベースのセレクタで「画面が開く・操作が通る・コンソールエラーが出ない・4xx/5xx が出ない」を見る。見た目に依存しないためレイアウト変更で壊れない。今回の実機検証で使った10項目はほぼそのまま変換できる
- **ピクセル比較**（縮小 or 廃止）: 全画面スクリーンショットをやめ、単体で安定しているコンポーネント（チップ、値一覧行、カバーコラージュ）に限定する

判断材料として、今回失敗していた4件の内訳は「ベースラインが古いだけ」2件と「テストの期待値が実装とズレているだけ」2件で、プロダクトのバグを示すものはゼロだった。一方でスキャン後クラッシュを捕まえたのは実ブラウザ経路のみだった。

関連: TASK-189（ビジュアルテスト正常化）、TASK-108（ビジュアルテストのフォント依存解消）

### D. 受け入れ条件は7項目程度を上限にする

超えるならタスクを割る。起票時に確定仕様（ドラフト・ADR）を1行ずつ受け入れ条件に対応付ける手順を踏めば、TASK-186 のような落とし漏れも防げる。

### E. 進捗は受け入れ条件のチェックで表現させる

実装担当は項目が終わるたびに `backlog task edit --check-ac <n>` を叩く。統括は polling せず、これを進捗信号として使う。完了報告はテキストで必須とする。

### F. 「既知の障害」報告には真のベースラインを要求する

「元から壊れている」という主張は、変更着手前のコミットまで遡った実測を根拠として添えさせる。根拠のない既知扱いは受け取らない。

### G. 実機確認の前提を毎回確認する

タスク着手時に dev server の生死を確認する手順を入れる。「起動済みのことが多い」という前提で動かない。

### H. 統括は検証を自分でやらない

`pnpm check` / `pnpm test` / ブラウザ操作は検証担当に委譲し、統括はコミット判断だけ持つ。

### I. 実機検証は実データに対して行わない

後日（2026-08-05）のオーバーレイ検証で判明した運用リスク。dev server がフィクスチャではなく実データの DB を指しており、検証担当が件数耐性を確かめるために実データの作品1件のタグを2007件へ差し替えて、終了後に元へ戻すという操作を行った。復元はされたが、実データに対して破壊的な検証ができてしまう状態自体が危険である。

同じ DB には `_verify166_a`（status: missing）という、過去の検証で作られたと思われる作品が残骸として混入していた。実データが検証で汚染された痕跡である。

対応の方向: 検証は必ずフィクスチャアダプタに対して行う。件数耐性のような大量データを要する検証は、フィクスチャ側に大量データを生成する手段を用意する。実データを指す dev server で検証させない。

### J. 共有の仕組みを個別実装で置き換えたときの喪失に注意する

TASK-191 で右側表示にする際、`AxisQuickOverlay` が共有フック `useAnchoredPopover` への依存を外して位置計算を自前実装した。その結果、共有フックが持っていた `ResizeObserver` によるサイズ追従が失われ、オーバーレイが画面外へはみ出す不具合（TASK-195）になった。

指示を出した統括の側も「右側に出す」としか言っておらず、共有フックを拡張するのか外すのかを示していなかった。共有されている仕組みを個別実装へ置き換える判断が入るときは、その仕組みが提供していた機能を列挙して失わないことを確認する手順が要る。指示側も、拡張なのか置き換えなのかを明示する。

同種の事例がもう1件ある。TASK-192 の仮想化導入は、見出し行に nowrap が無いという既存の潜在バグを実害（レイアウト崩壊）に変えた（TASK-193）。「新しい仕組みの導入が、既存の穴を顕在化させる」という型は繰り返し起きている。
