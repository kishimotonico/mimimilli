## 何を比べたか

仮想化された作品一覧の右クリックメニューなど、同じ題材を Base UI と Ark UI で作り、挙動と書きやすさを比べた。試作は捨てる前提で master には入れない。

| 題材 | 内容 | fixture |
|---|---|---|
| S1 | 作品一覧（リスト・グリッド）の右クリックメニュー。サブメニュー、チェック・ラジオ項目、複数選択、背景メニュー | large |
| S2 | ネイティブ dialog（ScanModal）の中の行メニュー | scan-review |
| S3 | 自作ポップオーバー（GroupValuePopover）の中のソート切替メニュー | large |
| S4 | 登録解除の確認ダイアログ。ライブラリの Dialog とネイティブ dialog の比較 | large |

|---|---|---|

| worktree | `.worktrees/task-525-base-ui` | `.worktrees/task-525-ark-ui` |

結論の案は Ark UI の採用で、僅差。決め手は Esc の層の協調で、Ark は容器の種類（メニュー、ポップオーバー、ダイアログ、コンボボックス）やフォーカス位置によらず、入れ子の回避が 0 行（検証済み）。Base UI はメニューが容器と別の `FloatingTree` になるため、共通層（約 105 行）が要る。Ark の回避は、サブメニューの Esc の約 15 行だけ（第 1 世代）。ただし、どちらのコストも条件付きで、Base UI の利点（サブメニューの Esc の既定が APG どおり、`focus()` でメニューが閉じない、motion の公式手順）が残る。さらに、移行期間の混在では Base UI が有利になる。Ark は Esc を capture 段で先に取るので、自作の Esc 処理やネイティブ dialog と混ざると一段にならず、コンボボックスとダイアログを同じ統合ブランチでまとめて置き換える制約が付く。Base UI は bubble 段なので、部品ごとに段階的に置き換えられる。この結論は ADR の前にユーザーが確認する案で、確定ではない。

この doc の情報源は3種類ある。検証担当が実ブラウザで確かめた事実、実装担当の報告（未検証）、コードやライブラリのソースを読んだ推定。書き分けを付ける。「検証済み」の出典は、検証担当の結果（Base UI は S/verify-base-ui/、Ark UI は S/verify-ark-ui/ の結果ファイル。Ark の v4〜v6 は v5-v6-results.md、Ark と Base UI の v7 の結果は S/v7-results.md）。検証担当は、Base UI は追加試作（`Menu.Root` と仮想アンカー）と共通層（`c0c6a90b`）まで、Ark UI は第 1 世代の回避とコンボボックス（`ea1505da`）、フォーカス（v6）、window capture への移行と移行期間の混在（`e10318e9`）まで再検証した。再検証していない項目は、それより前のコミット（Base UI は追加試作の前、Ark UI は `00ce5b0c`）の結果。表と本文に、どの時点の結果かを書く。

検証担当が出した補足は次のとおり。

- Base UI は旧方式（modal の ContextMenu）では、メニュー表示中に wheel スクロールが効かなかった。追加試作（modal={false}）ではホイールで一覧がスクロールする。メニューは閉じず画面上の同じ位置に留まり、行には追従しない（検証済み）
- Base UI の追加試作で、開いたまま外を左クリックすると、メニューが閉じると同時にクリックが行に通り、その行が選択される。閉じた後のフォーカスは finalFocus で右クリックした元の行へ戻るため、選択行とフォーカス行が別になる（検証済み）
- Base UI の S3（旧版のメニューは modal）では、メニュー表示中に別の軸へホバーできず、サイドバー行をクリックするとメニューとポップオーバーの両方が閉じて B は開かない。メニューが modal で内部バックドロップがポインターを受けるため。本番では `Menu.Root` を `modal={false}` にする前提（S1 の新方式と同じ）なので、modal 時の事象として読む。modal={false} での挙動は未検証
- メニューを開いたまま dialog の外（バックドロップ）をクリックすると、Ark UI ではメニューと dialog が 1 クリックで同時に閉じた（検証済み。追加試作のガードは条件付きで効く。後述）。Base UI も同じだった（検証済み。`Menu modal={false}`、ポータル先は dialog、Ark と同じ座標・手順）。瞬間クリックでも押下 120ms でも、メニューと dialog が 1 クリックで両方閉じる（アプリ側のガードは入れていない状態）。dialog 内の空白やタイトルバーのクリックは、メニューだけ閉じて dialog は残る（フォーカスは dialog 要素へ移り、︙には戻らない）。ライブラリのメニューが pointerdown で閉じ、その後にネイティブ dialog の click 判定が走る仕組みで、Base UI・Ark UI 共通。Ark UI はアプリ側のガードで人間のクリックなら回避でき、Base UI も同じガードが要る（未試行）。Base UI の Dialog に寄せれば、`useDialogModal` の backdrop 判定ごと無くなる
- Ark UI の S2 の項目名は、仕様の「除外 ▸」ではなく「範囲を選んで除外」になっている

## 争点ごとの比較

### 右クリックの対象の渡し方と開き直し

| | Base UI | Ark UI |
|---|---|---|
| 公式の口 | `ContextMenu.Trigger` は領域に付ける部品で、座標以外に対象を渡す口が無い。modal 固定で、開いたまま別行を右クリックする口も無い | `ContextTrigger` を 1 つだけ包めば、開いたまま別行の右クリックでも開き直す |
| 採用した形 | 追加試作: `Menu.Root modal={false}` を open 制御し、Trigger なしで仮想アンカー（`getBoundingClientRect` を持つオブジェクト）を Positioner の `anchor` に渡す。公式の口だけで書けた | `ContextTrigger` をそのまま使う。回避なし |

| 失うもの | 追加試作の方式では、長押しと押したまま離して選ぶ操作、スクロール固定とバックドロップを失う。メニュー外の左クリックはメニューを閉じつつ行にも届く（仕様判断が要る） | メニュー外の左クリックの扱いは Ark の既定 |
| 対象の保持 | どちらも自前の jotai atom に作品 ID のスナップショットを持ち、メニューを開く前に確定する。退出中・一覧から消えた後もスナップショットで表示を保つ | 同じ |
| 行の再レンダー | 0 回。開く、開き直す、閉じる、試作選択のいずれも（検証担当が route 差し替えでカウンタを入れて計測。対照の通常クリック選択はリスト 84 回、グリッド 192 回） | 0 回（検証済み、`7725a53e`）。リストの WorkRow、グリッドの WorkTile とも、開く、閉じる、同じ行・別の行での開き直し、開いたまま別行の右クリック、Ctrl+クリック、サブメニューの開閉のすべて（対照の通常クリック選択はリスト 92 回、グリッド 216 回） |

### Esc の一段

サブメニューは次のとおり。

- Base UI: サブメニューだけ閉じる。回避コードなし（検証済み）。Esc で親も閉じるかは `closeParentOnEsc`（MenuRoot の型は boolean、既定 false。MenuRoot.js 50 行）で選べる。false のときサブメニューの Esc は子だけを閉じる（`useDismiss` の `bubbles.escapeKey: closeParentOnEsc && parent.type === 'menu'`）。ContextMenu.Root では型上 `@deprecated`
- Ark UI: ソース（menu.machine の `trackInteractOutside`、menu.utils の `closeRootMenu`）では、サブメニューの Esc でルートまで無条件に閉じる。止める prop も設定も無い。検証担当は、回避コードを外すとサブメニューの Esc 1 回でメニュー全体が閉じることを確かめた（回避前の ArrowLeft 再送版）。@zag-js/menu 1.49.0（npm の最新も同じ）の menu.machine.mjs 585〜589 行で、prop の `onEscapeKeyDown` を呼んだあと、サブメニューなら `preventDefault` して `closeRootMenu` を無条件に呼ぶ。prop の戻り値も `defaultPrevented` も見ず、型にも Esc の挙動を変える prop は無い（検証済み。CHANGELOG は同梱されておらず未確認）

Ark UI の回避は 2 世代ある。第 1 世代を採り、第 2 世代は採らない旧案とする。

第 1 世代（採る。`MotionMenuPopup.tsx` の `SubmenuEscapeStep`、約 15 行、`3d053bd4`）:

- 第 1 世代は document の capture 段で動いていたが、`b59a738f` で window の capture 段に移した（登録順に依存しない）。Esc かつ `[role=menu]:not([inert])` が 2 つ以上のとき、`stopImmediatePropagation` と `preventDefault` で Esc を止め、DOM 上で最後の、inert でないメニュー（最前面のメニュー）に ArrowLeft を dispatch する。孫の階層にも送れる作りだが、孫は未確認。`service.send` も `setTimeout` もない。メニューの open は非制御
- window の capture 段に移した版（`b59a738f`、検証担当が `e10318e9` で確認）でも、S1 の連続 Esc 0〜100ms の 21 回すべて正常、S1・S2 × ArrowRight とホバー × サブメニュー内と body で一段ずつ、ArrowRight の先頭ハイライトあり
- 検証結果（検証担当、`ea1505da`）: S1、S2、Ark Popover、S4 Dialog 内のメニュー、ArrowRight とホバー、サブメニュー内と body の全パターンで一段ずつ閉じる。ArrowRight で開いたサブメニューの先頭項目の自動ハイライトが付く。連続 Esc は、間隔 0〜100ms で S1・S2 各 21 回すべて取りこぼしなし

第 2 世代（採らない。`7725a53e`）:

- ルートの open を制御モードにし、サブメニューの `onEscapeKeyDown` で印を立てる。ルートの `onOpenChange` でそのときの close を捨て、サブメニューは `setOpen(false)` で閉じる。親へのフォーカス復帰に `service.send({type:"FOCUS_MENU"})`（文書化は未確認）。印の解除は `setTimeout 0`
- 競合: サブメニューの Esc から次の Esc までが約 10ms 未満だと、2 回目が断続的に失われる。検証担当は約 5ms で失われ、0・15・30・100ms では正常だった。Fable の実測では、0〜8ms の 12 回中 6 回で失われた
- 回帰（検証済み）: ArrowRight でサブメニューを開いたときの先頭項目の自動ハイライトが消える（ホバーで開いた場合は前後とも付かない）
- コード量は、`useMotionMenu` 約 25 行とサブメニュー用コンポーネント約 25 行

ネイティブ dialog の中や自作ポップオーバーの中の入れ子は次のとおり。

- dialog 内: どちらもサブメニュー → メニュー → dialog の順で、メニューを閉じた Esc で dialog は閉じない（検証済み）
- 一覧の選択解除（`useWorkResultsDismiss`）: Base UI は Esc を `preventDefault` するので、既存の `defaultPrevented` 判定と噛み合う。Ark UI でもメニューを閉じた Esc では選択が残り、3 回目の Esc で解除された（検証済み）
- 自作ポップオーバー（`usePopoverEscape`）との入れ子で、Base UI は不合格になる（旧版。Base UI の Popover の中に Menu を置いた場合は下記）。原因は Base UI の Esc の経路が 2 つあること（実装担当がソースを読んだ推定。登録順は未確認）
  - フォーカスがメニュー内: ポップアップの React `onKeyDown` が `preventDefault` と `stopPropagation` をするので、自作の document リスナーは走らない
  - フォーカスがメニュー外（body や検索欄）: document の keydown リスナー（`useDismiss`）だけが働く。これは `defaultPrevented` を見ない。自作の `usePopoverEscape` も同じ document の bubble リスナーで、先に登録されるため、ポップオーバーとメニューが両方閉じる
- Ark UI は `onEscapeKeyDown={e => e.stopPropagation()}` の 1 行で回避した。検証担当は、これを外すとフォーカスがメニュー内のとき両方閉じることを確認した。フォーカスが body のときは回避なしでもメニューだけ閉じた

Base UI の Popover や Dialog の中に Base UI の Menu を置いた場合の結果は次のとおり。素の状態と共通層なしの結果は実装担当の Playwright 実測で、共通層あり（`c0c6a90b`）は検証担当が確認した。

- 素の状態: フォーカスがメニュー内なら Esc 一段。body・検索欄では 1 回の Esc で両方閉じる（Popover の modal が false、true、trap-focus のいずれも）。原因は、`MenuRoot` が親がメニューでなければ自前の `FloatingTree` を作り（MenuRoot.js 約 572 行）、Popover の `hasBlockingChild` が子メニューを見つけられないこと（ソース読み）。Menu を Popover のツリーの子にする公開 API は無い
- 公式の口で解決: `Popover.Root` の `onOpenChange` の `eventDetails`（`cancel()`、`allowPropagation()`、`reason`）で、`reason === "escape-key"` かつ子メニューが開いていれば `cancel()` と `allowPropagation()` を呼ぶ。`allowPropagation` が要るのは、フォーカスが検索欄にあるとき、Popover が Popup の React `onKeyDown` で先に処理し、取り消しても `stopPropagation` してメニューの document リスナーに届かないため（`useDismiss.js` 117 行）
- 解決後の結果（modal が false、true とも）: メニュー内・body・検索欄のどれでも、1 回目でメニューだけ、2 回目でポップオーバーが閉じる。項目を選んでもポップオーバーは閉じない
- 検証担当は、手書きの配線版（`ProtoPopover`、`74853e51`、`effb8423` 時点）で、フォーカスがメニュー内・body・検索欄・トリガーの 4 状態すべてで、1 回目の Esc でメニューだけ、2 回目でポップオーバーが閉じることを確認した（検証済み）。共通層版と Dialog の入れ子の検証は、下記の最終検証を参照
- 共通層（`client/src/proto/nestedMenuGuard.tsx`。初版は 66 行、コメント・型込み）: 容器（Popover、Dialog）が、開いている子メニューの数を ref で数える。`onOpenChange` で reason が `escape-key` かつ子メニューが開いていれば、`cancel()` と `allowPropagation()` を呼ぶ。メニュー側は共通の `MenuPopupFrame` に 2 行（`isPresent` の間だけ登録。サブメニューも自動）。画面側は容器ごとに 4 行（guard の作成 1、Scope の開閉 2、`onOpenChange` の 1 行）
- 共通層なしの結果: Popover も Dialog も、フォーカスがメニュー外（body、検索欄、ダイアログ内の別ボタン）だと、1 回の Esc で容器ごと全部閉じる。Dialog の中の Menu でも同じ問題が出る
- 共通層ありの結果: どのケースでも容器が先に閉じない。Popover、Popover とサブメニュー、Dialog は一段ずつ閉じる。初版では、Dialog とサブメニューでフォーカスがメニュー外のときだけ、1 回の Esc でメニューとサブメニューが同時に閉じた（Dialog は残る）。`modal={false}` でも同じだった（`a96400ee`、実装担当の実測）。原因は modal ではない。ルートメニューが先に `escape-key` で閉じ、約 9ms 後にサブメニューが閉じる。ソースの差として、Popover は `FloatingTree` と `FloatingNode` を持ち、Popover 内の Menu はそのツリーに乗る（MenuTrigger.js 73〜77 行）。Dialog には `FloatingTree` が無く、Dialog 内の Menu は自前のツリーを作る。ルートの `useDismiss` の `hasBlockingChild` がサブメニューを見つけられないと推定している（どのノードが一致しないかは未確認）。Popover とサブメニュー（`modal={false}`）は全状態で一段ずつ、Dialog のサブなしメニューも全状態で一段だった。`modal={false}` の規約は Esc の一段には効かないが、S2 の背景クリックの問題のために維持する。
- 対策（`c0c6a90b`）: `GuardedMenuRoot`（`Menu.Root` の代わり）が、メニュー自身も容器として、開いているサブメニューを数える。`onOpenChange` で reason が `escape-key` かつサブメニューが開いていれば、`cancel()` と `allowPropagation()` を呼ぶ。`MenuLevel` で「メニューの内側」の印を付け、サブメニューの Popup は所属する `GuardedMenuRoot` へ、ルートの Popup は外側の容器へ登録を振り分ける
- 対策後の結果: Popover、Popover とサブメニュー、Dialog、Dialog とサブメニューのすべてで、フォーカスがメニュー内・body・検索欄や別のボタンのどれでも一段ずつ閉じる（サブメニュー → メニュー → 容器）。S1・S2 のサブメニューの一段も維持された
- 最終検証（検証担当、`c0c6a90b`）: Popover と Dialog、サブなしとサブあり、フォーカスがメニュー内・body・検索欄や別ボタンの全 12 条件で、一段ずつ閉じた（サブメニュー → メニュー → 容器）。一度に複数段閉じる状況はなかった。対照として共通層を切ると（`__protoNestGuard=false`、サブあり、body フォーカス）、Popover も Dialog も Esc 1 回でメニュー・サブメニュー・容器が全部閉じ、共通層が効いていることを確認した。S1（サブ「タグ」）と S2（ネイティブ dialog 内、サブ）も、フォーカスがサブメニュー内・body のどちらでも一段ずつ閉じ、S1 の開いたまま別行の右クリックと実行ログの一致も維持された
- 連続 Esc: 共通層に連続 Esc の競合はなかった（Fable の実測。S1、Popover、Popover とサブメニュー、フォーカスがメニュー内・body、間隔 0〜100ms のすべて正常）
- 行数: `nestedMenuGuard.tsx` は 105 行（コメント・型・import 込み）、`MenuPopupFrame` に 2 行。画面側は容器ごとに 4 行で、メニューごとの配線は 0 行（`Menu.Root` を `GuardedMenuRoot` に置き換えるだけ）
- 制限: 数えるのは 1 階層のサブメニューまで。孫の階層でフォーカスがメニュー外のときは未確認。`Menu.Root` を直接書くと効かないので、置き換え忘れが起きうる。`Menu.Root` の直接 import を lint で禁じるなどで防げる
- 注意点: 登録は `MenuPopupFrame` 経由で効くので、`Menu.Portal` を直接書くと効かない。子メニューが Esc で閉じる前提にも依存する

Ark UI は、自作ポップオーバーと Ark の Menu の組み合わせでは `onEscapeKeyDown` の `stopPropagation`（1 行）が要った。Ark の Popover の中に Ark の Menu を置いた場合は、回避コード 0 行だった（検証済み、`46a974cd`。メニューのポータル先が content 内・body の両方）。フォーカスがメニュー内・body・ソートボタンのどれでも、1 回目でメニューだけ、2 回目でポップオーバーが閉じる。Ark の dismissable layer のスタックが最前面の層だけに Esc を処理させるため、フォーカス位置に依存しない。項目を選んでもポップオーバーは閉じず、検索欄の IME 変換中の Esc でポップオーバーは閉じなかった（CDP の合成）。要ったのは z-index の調整だけ（試作パネルの都合）。

挙動の違いが 2 つある。Ark では、メニューを開いたまま `focus()` で外の要素（検索欄、キャンセルボタンなど）へ移すと、メニューが focus-outside で閉じ、フォーカスは移動先ではなくトリガーへ戻される（メニューの復帰が上書きする）。実マウスで検索欄をクリックした場合は、メニューが閉じてフォーカスは検索欄に付く。Base UI の非 modal メニューは `focus()` で移しても開いたままで、フォーカスは移動先に残る（検証済み。サブメニューありでも同じで、その後の Esc は一段ずつ）。閉じるのは外側クリックか Esc。プログラムからフォーカスを動かす場面で差が出る。もう 1 つは外側クリックで、Ark ではポップオーバーの外のクリックが 1 クリックで両方閉じ、ポップオーバー内の余白や検索欄のクリックはメニューだけ閉じる。両方同時に閉じるのを避ける公式の口は `onInteractOutside` / `onPointerDownOutside` の `preventDefault`（未試行）。

自作の document Esc リスナー（`useDialogModal` など）との入れ子は、移行が終わるまで残る。

TASK-248 の決定（フォーカス復帰は自前、FloatingFocusManager 禁止）との関係で、分かったことは次のとおり。

- Base UI の Dialog のライブラリの復帰は、退出完了の直前に動く（検証済み。`finalFocus` に関数を渡した場合）。試作の `inert={!isPresent}`（`UnregisterConfirm.tsx`）があると、約 35〜69ms で BODY へ移り、約 212〜239ms で行へ戻る。`inert` を外すと、BODY を経由せず dialog 内のまま約 198〜246ms で行へ戻る。約 35〜69ms の BODY は試作の `inert` がフォーカス中の要素を無効にしたためで、ライブラリの挙動ではない。トレードオフとして、`inert` で退出中の入力を止めると、finalFocus が効くまでの間フォーカスが失われる。`inert` を外すと、退出中にキーとポインターを受ける。自前（own）なら、この問題は起きない。検証担当が先に見た「退出中ずっと BODY」も、この `inert` の影響を含む
- ライブラリ任せの復帰が後から奪う事象は、S1 の新方式で実測で起きた。`finalFocus` に関数を渡すと、外側の別行をクリックしたとき、クリックした行にいったんフォーカスが移り、246ms 後に右クリック元の行に奪い返される（検証済み）。自前（own）は閉じる瞬間（Esc で 20ms）に確定し、外側の別行クリックはその行にフォーカスが残り、取り合いがない。default（finalFocus 未指定）は BODY を経て約 220〜250ms で行へ戻り、外側クリックはクリック先を維持した。fn は Esc・項目実行で約 170〜190ms の間 BODY になる。これも試作の `inert`（`menuParts.tsx:46`）が原因で、route で `inert` を外すと BODY を経由せず約 210〜275ms で行へ戻る（検証済み）。3 モードとも往復はない
- 一方、S3 の軸A→B切替（退出が終わった旧 A が新 B のフォーカスを奪う場面）では、ライブラリ任せの Base UI で 12 点、Ark UI で 3 通りとも奪取なし
- 項目実行後のフォーカスの戻し先は、試作の設計の都合で own では BODY のまま（item-press で戻さない）。本番の仕様は置き換えタスクで決める
- メニューの finalFocus が行へ戻す動きと、「登録解除…」で開いた dialog の初期フォーカスが競合した（実装担当の観測）。登録解除の要求時は finalFocus が false を返す形で解消した
- Ark UI は `finalFocusEl` のほうが自前より短く書けた（実装担当の観測）が、復帰が `isPresent` と無関係にライブラリ任せになる。Ark Dialog の復帰は、検証済みの実測（rAF）では閉じた瞬間に動いた。Esc で 19ms に inert、37ms に行へ復帰、219ms に DOM から消える。キャンセルは 60ms、dialog 内のメニューを閉じたあとの Esc は 29ms で復帰する。いずれも BODY を経由せず、退出完了の約 180ms 前に戻る。Base UI のライブラリ任せ（`finalFocus` の関数、default）は退出完了時なので、タイミングが大きく違う

ネイティブ版の閉じた後のフォーカスが BODY に落ちるのは、開いた元のメニューが先に消えていて、`useDialogModal` が復帰先として消えた要素を覚えるため。ライブラリの Dialog に寄せると、次の既存の仕組みが要らなくなる。

- `openModalDialogsAtom`
- Tab 循環の補完
- cancel の伝播止め
- トーストの付け替え

新たに要るものは次のとおり。

- z-index の階層管理。試作では Backdrop と Viewport を 50、メニューを 60 に手で決めた。既存の一覧との整合は未検討。top layer ではなくなる
- `dialog[open]` に依存する判定の書き換え（`useGlobalShortcuts`、`useWorkResultsDismiss`）
- Base UI の Dialog は、Popup（`tabindex=-1` の div）にフォーカスがあるときも再生中の Space が奪われた（実装担当の観測。ボタン上では漏れない）。ArrowRight が window に届かない件は原因未確認

S2 でネイティブ dialog の中にメニューを置くときの modal の悪影響は次のとおり。

- Base UI のメニューは既定で modal。メニューを開いたまま dialog 内の別の場所をクリックすると、dialog まで閉じた（実装担当の観測。2 回再現）。原因は、内部バックドロップが pointerdown で消え、click の target が dialog 要素になって `useDialogModal.handleBackdropClick` に掛かるためと推定。`modal={false}` で回避した。modal のままの悪影響は検証していない
- Ark UI は modal モードが無い。ただしメニューを開いたまま dialog の外をクリックすると、メニューと dialog が同時に閉じた（検証済み）。Ark の outside pointerdown でメニューが閉じ、その後の click で `handleBackdropClick` が dialog を閉じるため。追加試作では、`onPointerDownOutside` で target が `HTMLDialogElement` のときに印を立て、ScanModal の `canBackdropClose` に渡して直そうとした（`proto/menuBackdropGuard.ts`）。追加試作の検証結果は条件付き合格。押下から離しまで約 100ms の人間に近いクリックでは、1 回目でメニューだけ、2 回目で dialog が閉じる。瞬間クリック（約 1ms）ではガードが間に合わず、1 クリックで両方閉じる（`onPointerDownOutside` が pointerdown の約 7ms 後に走るため）。他の dialog にも同じ配線が要る。

- メニュー項目にフォーカスがある状態では、CDP の `imeSetComposition` は composition イベントを発火しない（両試作の実装担当が確認。検証担当も同じ）

## 受け入れ条件外の確認

- メニューキー、Shift+F10: Base UI は新方式でも合格（検証済み。フォーカス行の矩形の下端を起点に、その行が対象）。Ark UI も行を対象に開いた（検証済み）。どちらも CDP の実キーでは contextmenu が発火せず、`button: 0` の contextmenu を行の矩形から撃ち直す回避コードが要る
- contextmenu 抑止の順序: Base UI の `ContextMenu.Trigger` は `onContextMenu` で `preventDefault` と `stopPropagation` をするので、Trigger 内の右クリックは document の bubble リスナーに届かない（実装担当の実測）。抑止は window の capture 段に置く必要があった。Ark の `ContextTrigger` は `preventDefault` だけで伝播は止めない。どちらの試作も、例外判定（入力欄、contenteditable、選択範囲の上）を document の capture 段で行い、例外時は伝播ごと止めてブラウザのメニューに任せた。例外の挙動は両版とも検証済み
- Base UI の modal メニュー: 旧方式では、wheel スクロールが効かず、S3 で別軸へのホバーができなかった。S2 での悪影響は上記のとおり。追加試作の S1 は modal={false} で、ホイールスクロールは効く（検証済み）。S2、Dialog の中、Popover の中の試作はすべて `modal={false}` で、Esc の一段はその形で検証済み。未検証なのは、ポップオーバーの中のメニュー（`GroupValuePopover` 内の `SortRadioMenu`）を `modal={false}` にしたときの、外側クリックと別の軸へのホバーだけ
- キー漏れ: Base UI の新方式では、メニュー表示中の ArrowDown・Up・Right・Left、x、a、Space、Enter で再生状態は変わらなかった（検証済み。対照のメニューなしの body の Space では一時停止。シークは fixture で観測できない）。Ark UI の検証（`00ce5b0c`）では、再生中のメニュー操作（↓、Space、→、←）で再生状態は変わらなかった。先頭文字移動の「登」は 1 件・複数件とも「登録解除…」へ移動した。Base UI の先頭文字移動は `label` prop（件数と別）で実現し、Space でお気に入りが実際に切り替わった（実装担当の観測）。Ark の先頭文字移動は検証済み
- Pragmatic DnD: 作品一覧に無く、干渉の確認は対象外（調査済み）
- 行の再レンダー: Base UI は 0 回（検証済み）。Ark UI も 0 回（検証済み、`7725a53e`）。リストの WorkRow とグリッドの WorkTile とも、開く、閉じる、同じ行・別の行で開き直す、開いたまま別行を右クリック、Ctrl+クリック、サブメニューの開閉のすべてで 0 回。対照の通常クリック選択は、リストで 92 回、グリッドで 216 回
- Windows 実機: 未確認

## 結論の案

これは ADR を書く前にユーザーが確認する案で、確定ではない。推奨は Ark UI だが、僅差で、逆の結論も成り立つ。

### 土台は Ark UI（僅差）

決め手は、Esc の層の協調。doc-9 でも、共通層を貫通する争点とされていた。

- Ark は dismissable layer のスタックが、最前面の層だけに Esc を処理させる。フォーカス位置にも、容器の種類（メニュー、ポップオーバー、ダイアログ、コンボボックス）にもよらず、入れ子の回避コードは 0 行（検証済み）
- Base UI はメニューが容器とは別の `FloatingTree` になるので（ソース読み）、共通層が要る（約 105 行。`Menu.Root` を置き換える規約と lint。サブメニューは 1 階層まで確認）。コンボボックスは通常の状態では共通層なしで一段になるが、一致なしのときは `Combobox.Empty` を描画する規約が要る

どちらのコストも条件付きになる。Base UI の共通層が要るのは、メニューが開いたままフォーカスがメニューの外にある状態で、その頻度は分からない。Ark のサブメニューの Esc の回避は、サブメニューを持つメニューができて初めて要る。

Ark の回避は、サブメニューの Esc の約 15 行だけ（第 1 世代）。window の capture 段（`b59a738f`）で、開いているメニューが 2 つ以上のときの Esc を止め、最前面のメニューに ArrowLeft を送る。APG のキー操作どおりの動きになる。zag の既定は APG と異なり、上流に変える動きは確認できなかった（下記）ので、この回避は持ち続ける前提になる。第 2 世代（制御モードと `service.send`）は、回帰と競合が出たので採らない旧案。

Base UI の利点は次のとおり。僅差と言うのは、これが残るため。

- サブメニューの Esc の既定が APG どおりで、上流もその方向（PR #2493）
- プログラムの `focus()` で外へ移しても、メニューが閉じない
- motion の公式手順がある（Ark は `present` の配線が Root ごとに要る）
- Esc を bubble 段で処理するので、自作の Esc 処理やネイティブ dialog と混在しても一段になり、部品ごとに段階的に置き換えられる（次の節）

Base UI を選ぶ場合のコストは次のとおり。

- 共通層 105 行、`Menu.Root` を置き換える規約と lint、全メニューのラッパー化、サブメニューは 1 階層まで確認
- `ContextMenu` 部品は modal 固定で開き直しの口が無く使えない（仮想アンカーの `Menu.Root` で代える）。modal を全箇所で切る規約が要る

Ark UI を選ぶ場合の注意点は次のとおり。

- 退出中も `data-state="open"` のまま
- `present` の配線が Root ごとに要る（共通フックに 1 回）
- `focus()` で外へ移すと、メニューが閉じてフォーカスがトリガーへ戻される
- コンボボックスのリストに退出アニメーションは未適用（試作の範囲外）
- 1 クリックで 2 層が閉じる動作がある。ポップオーバーの中のメニューで外をクリックしたとき（検証済み）と、ダイアログの中のコンボボックスで backdrop をクリックしたとき（実装担当の観測）。Base UI 側は未計測で、差かどうかは分からない。S2 の backdrop の二重クローズ（メニューと dialog）は両ライブラリ共通
- Esc を capture 段で先に取るので、移行期間に自作の Esc 処理やネイティブ dialog と混ざると一段にならない。コンボボックスとダイアログを同じ統合ブランチでまとめて置き換える制約が付く（次の節）
- フォーカス復帰を `finalFocusEl` に任せる形は、ADR-0014 の原則 3 と TASK-248 の方針（旧 A が新 B のフォーカスを奪わないよう、自前で戻す）を改める側になる

2 つの欠点の出る頻度は、どちらも断定できない。Ark の欠点（サブメニューの Esc の回避）は、サブメニューを持つメニューがあって初めて効く。doc-8 の合意項目にサブメニューは無く、既存の 7 つのメニューにも無い（要件は「対応できること」）ので、予定のメニューでは出ないかもしれない。Base UI の入れ子の欠点（メニューが開いたままフォーカスがメニューの外にある状態）が、プログラムの `focus()` などに限られる、というのは推定で、検証は `blur()` と `focus()` でその状態を作っている。ADR では断定しない。

### 移行期間の混在

置き換えは段階的に進むので、自作の Esc 処理やネイティブ dialog と、ライブラリの部品が混在する期間がある。その組み合わせを試した。Base UI 側は検証担当が確認した（検証済み、`08dbd1f1`）。Ark 側（軸A→B切替、Ark Dialog の中の自作 TagCombobox、ネイティブ dialog の中の Ark Combobox）も検証担当が確認した（検証済み、`e10318e9`）。

| 組み合わせ | Ark UI | Base UI |
|---|---|---|
| ダイアログ（ライブラリ）の中の自作 TagCombobox | 候補が開いた状態の Esc 1 回目で、候補と Dialog が同時に閉じる（候補が無い状態では、Esc 1 回目で Dialog が閉じる）。Ark Dialog が document の capture 段で先に処理し（`preventDefault`、伝播は止めない）、その後 React の `onKeyDown` で TagCombobox も反応する。TagCombobox は `defaultPrevented` を見ない | 候補が開いている状態（文字入力後、ArrowDown 後）では、Esc 1 回目で候補だけ（入力値は残る）、2 回目で Dialog。候補が開いていない状態（クリックだけ、blur 後、選択済み）では、Esc 1 回目で Dialog が閉じる（候補が無いので一段で閉じる）。TagCombobox の `onKeyDown` が `preventDefault` と `stopPropagation` をし、Base UI Dialog の Esc は document の bubble 段なので届かない |
| ネイティブ dialog の中のライブラリのコンボボックス | 入力欄にフォーカスがある限り、何度 Esc を押しても dialog が閉じない（Esc 1 回目で候補だけ閉じる。リストを開いたまま blur しても、Esc 1 回目で入力欄にフォーカスが戻るので、以降閉じない。リストを閉じてから blur した場合と、入力欄にフォーカスしていない初期状態では閉じる。原因は、入力欄の `onKeyDown` が、リストが閉じていても Esc を `preventDefault` すること。`combobox.connect.mjs` の `getInputProps`） | 候補が開いている状態（入力なし、文字入力後、ArrowDown 後、blur 後）の Esc 1 回目で候補だけ（入力値は空になる）、2 回目で dialog（`useDialogModal` の cancel）。例外は、選択済みで候補が閉じているときの Esc で、選択クリアと dialog の close が同時に起きる（`ComboboxInput.js` 約 290 行が `stopPropagation` だけで `preventDefault` しないので、ネイティブ dialog の cancel が止まらない）。Base UI Dialog の中では、選択クリアだけで止まった |
| 軸A→B切替（Popover 2 つ） | `restoreFocus` の既定・false・guard × ホバー・クリック × 各 2 回の 12 通りすべてで、A のトリガーへの復帰は一度も起きず、最終フォーカスは B の検索欄。`restoreFocus` の既定でも、別のポップオーバーへ移った場合は復帰しない。ホバーでは、A の content が閉じた時点で約 17ms BODY を経て B の検索欄へ移る（実装担当の観測）。A を Esc で閉じたときは A のトリガーへ戻る | 検証済み（S3 の軸A→B切替。12 点） |

この結果、Ark を選ぶ場合は、コンボボックスとダイアログを同じ統合ブランチでまとめて置き換える必要がある。ダイアログだけ先に置き換えると、自作の TagCombobox が Ark Dialog の中に入る。コンボボックスだけ先に置き換えると、Ark のコンボボックスがネイティブ dialog の中に入る。どちらも一段にならない。Base UI は bubble 段なので、部品ごとに段階的に置き換えられる（ネイティブ dialog の中の選択済みコンボボックスだけ例外）。

### コンボボックスの入れ子

ダイアログの中のコンボボックス（doc-8 の「タグを追加…」に近い）で、Esc の一段を試した。Base UI の `@base-ui/react` 1.9.0 は、`FloatingTree` を使うのがメニューとポップオーバーだけで、コンボボックスにもセレクトにもダイアログにも無い（ソース読み）。コンボボックスはフォーカスが入力欄（ポップアップの外）にあるのが普通で、Ark の層スタックはフォーカス位置によらないので、Ark が有利になりうる、というレビューの指摘が出発点だった。セレクトは未検証。

| | Base UI | Ark UI |
|---|---|---|
| 通常の Esc | 1 回目でリストだけ、2 回目で Dialog。共通層は不要（検証済み、`28d5c210`） | 1 回目でリストだけ（入力値は残る）、2 回目で Dialog。回避 0 行（検証済み、`ea1505da`）。ハイライト後も同じ |
| 入力値と確定後 | Esc でリストを閉じると入力も消える（既定）。選択済みで Esc を押すと、選択がクリアされるだけ | 入力値は残る。確定後（リストが閉じているとき）の Esc は Dialog が閉じる |
| 一致なし | `Combobox.Empty` を出さないと、Esc 1 回でリストと Dialog が同時に閉じる。出せば一段。ソースで確認（AriaCombobox.js 593〜596 行。`allowPropagation()` を呼ぶ設計） | 一致なしも一段（検証済み） |
| `focus()` で別ボタンへ | リストが閉じ（入力も空）、Dialog は残る。Esc 1 回目で Dialog | リストが閉じ、フォーカスは別ボタンに留まる。Esc 1 回目で Dialog |
| IME 変換中（CDP の合成） | Esc は何も起きない。Enter はリストが閉じるだけで、選択も Dialog の close もない。合成の `isComposing: true` の Enter でハイライト項目があると選択される | Esc・Enter とも何も起きない |
| 連続 Esc | 実キーでは 0〜100ms の 21 回すべて正常。同一ティックで keydown を 2 回 dispatch すると 2 回目を取りこぼす（実キーでは通常起きない） | 未計測 |
| backdrop クリック | 未計測 | 1 クリックでリストと Dialog が同時に閉じる（対処なし。実装担当の観測） |

Base UI のコンボボックスは、入力欄の `onKeyDown` で Esc を処理し、`stopPropagation` するので、Dialog の document リスナーに届かない。候補はバーチャルフォーカスで、フォーカスは入力欄に残る。そのため通常の状態では、共通層の拡張は不要だった。

### 差になる点と差がない点

差になる点は次のとおり。

- 入れ子の Esc の協調（上記）。Ark は 0 行、Base UI は共通層が要る
- サブメニューの Esc。Base UI は `closeParentOnEsc`（既定 false）で選べて、回避が要らない。Ark は止める口が無く、第 1 世代の回避が約 15 行要る
- 移行期間の混在。Base UI は bubble 段で、段階的に置き換えられる。Ark は同時に置き換える制約が付く
- ライブラリ任せのフォーカス復帰のタイミング。Ark は閉じた瞬間、Base UI は退出完了時

差がないか小さい点は次のとおり。結論の根拠には使わない。

- 連続 Esc の取りこぼし。Base UI の共通層も、Ark の第 1 世代も、0〜100ms で取りこぼしがない（Ark の第 1 世代は検証済み。Base UI のメニュー共通層は Fable の実測。検証担当の Base UI の連続 Esc はコンボボックスのみ）。コンボボックスの連続 Esc は、Ark は未計測、Base UI は同一ティックの合成でだけ取りこぼす
- 公式の口だけで書けたか。右クリックメニューは、Base UI が `Menu.Root modal={false}` と仮想アンカー、Ark UI が `ContextTrigger` で、どちらも回避なしで書けた
- motion との組み方。Ark の `present` は公式の正規の口で、配線は共通フックにまとめれば済む。Base UI も Root ごとに境界が要る
- 一覧の選択解除（`defaultPrevented` 判定）との噛み合わせ。Ark でもメニューを閉じた Esc で選択は残った（検証済み）
- 変換中の Esc。Ark も `@zag-js/dismissable` 1.49.0 の escape-keydown.mjs に `isComposing` の return がある（ソース読み）
- 土台の置き換えで要らなくなる既存の仕組みと、Esc とフォーカスの 1 系統化（ダイアログの案を参照）。Ark の Dialog でも同様に得られる
- S2 の backdrop の二重クローズ。両ライブラリ共通（検証済み）
- ContextMenu の長押し、押したまま離して選ぶ操作を失う（モバイル対象外）。Base UI の仮想アンカー方式の場合
- バンドルは Ark が約 7 kB 小さい（+49 kB と +42 kB の gzip、どちらも試作コード込み。Ark は `00ce5b0c` 時点の計測）

### サブメニューの Esc の上流

サブメニューの Esc の既定は、WAI-ARIA Authoring Practices Guide（APG）の menu パターンに関わる。APG は Escape を「フォーカスのあるメニューを閉じ、そのメニューを開いた元（メニューボタンや親のメニュー項目など）へフォーカスを戻す」と定めている（https://www.w3.org/WAI/ARIA/apg/patterns/menu/ のキーボード操作の節。本文を確認した）。サブメニューの Esc で親まで閉じる Ark の既定は、これと異なる。

上流で変わる見込みは確認できなかった（調査担当が GitHub で確認）。

- zag の menu.machine は、main、1.49.0（npm 最新、2026-11-22）、v2 ブランチ（2.0.0-next）のいずれでも、サブメニューの Esc で `closeRootMenu` を無条件に呼ぶ。少なくとも 2025-08-28 から同じ。v2 ではサブメニューのフィルター入力欄の Esc だけ親へ戻す変更が入ったが、それ以外はルートまで閉じるまま（https://github.com/chakra-ui/zag/blob/main/packages/machines/menu/src/menu.machine.ts 、https://github.com/chakra-ui/zag/blob/v2/packages/machines/menu/src/menu.machine.ts）
- 「サブメニューの Esc で親へ戻るべき」という issue、PR、discussion は chakra-ui/zag と chakra-ui/ark のどちらにも見つからなかった。近いのは zag #1329（`onEscapeKeyDown` の追加要望。2024-03 closed。階層の挙動には触れていない）。CHANGELOG にもこの挙動の記述はない
- Base UI は PR #2493（2025-08-25 マージ、v1.0.0-beta.3）で `closeParentOnEsc` の既定を true から false に変えた。理由は、MDN の menu role の説明どおり、サブメニューの Esc はサブメニューだけ閉じてトリガーへ戻すべきだから（発端は issue #2490。https://github.com/mui/base-ui/pull/2493 、https://github.com/mui/base-ui/issues/2490）

### フォーカス復帰（AC5）: 戻し先はアプリが決め、タイミングはライブラリに任せる案

TASK-248 の決定（フォーカス復帰は自前、FloatingFocusManager 禁止）は、更新が必要になる。決定の根拠は、退出中の旧 A が、退出後に新 B からフォーカスを奪うのを防ぐことだった。

- Ark のライブラリ任せの復帰は、Dialog もメニューも閉じた瞬間に動く（検証済み）。Dialog は Esc で 19ms に inert、37ms に行へ復帰、219ms に DOM から消える。メニューは S1 の Esc で 14ms に inert、31ms に行へ（メニュー消滅 214ms）、項目実行は 76〜78ms に行へ（消滅 273〜276ms）、S3 のソートボタン起点の Esc は 22ms、S2 の︙ボタン起点の Esc は 12ms で戻る。いずれも BODY を経由せず、退出完了の前に戻る。ただし、メニューを Esc で閉じた 11 回のうち 1 回だけ、フォーカスが BODY を経由した（再現せず。Fable の実測）。置き換えタスクの受け入れ条件で、繰り返し測る。旧 A の復帰が新 B のフォーカスを奪うかは、実測の事実で書く。Ark Popover 2 つの軸A→B切替では、`restoreFocus` 3 通り × ホバー・クリック × 各 2 回の 12 通りとも、A の復帰は起きず奪い合いがなかった（検証済み）。S3（自作ポップオーバー内の Ark メニュー）でも奪取はなかった（検証済み）
- 案は、戻し先（右クリックした行、行が外れたら roving の行）をアプリが決めて `finalFocusEl` で渡し、タイミングはライブラリに任せる。Ark の `finalFocusEl` は、自前より短く書けた（実装担当の観測）。この案は、ADR-0014 の原則 3 と TASK-248 の方針を改める側になる
- Base UI のライブラリ任せの復帰は退出完了時に動く（Dialog は約 200ms、検証済み）。S1 の `finalFocus` に関数を渡す形では、外側の別行クリックのフォーカスを 246ms 後に右クリック元の行へ奪い返す事象が実測で起きた。自前（`finalFocus={false}` と自前 focus）は閉じる瞬間（Esc で 20ms）に確定し、取り合いがなかった（検証済み）。Dialog の自前も検証済み（Esc 9〜10ms）。自前の復帰は現行の規約（ADR-0014 の原則 3）そのもので、Base UI を選ぶ場合に新しく増える負担ではない
- 復帰先が仮想アンカーや消えた要素のとき、Base UI の既定は BODY に落ちる（検証済み）。復帰先の判断はどちらでもアプリ側に要る
- 外側の別の行を左クリックしたとき、クリックした行にフォーカスが移ってそのまま残り、メニュー側から奪い返さない（検証済み。`finalFocusEl` を渡していても、フォーカスできる外側要素のクリックでは復帰しない）。フォーカスできない領域（上部バーの空白）のクリックでは、約 33ms BODY に落ちたあと、右クリックした行へ戻す（検証済み）。Base UI の `finalFocus` に関数を渡す形のような取り合いは、Ark では起きなかった
- 項目実行後の戻し先は、Ark では行へ戻る（上記）。Base UI の自前の試作では BODY のままで、本番の仕様は置き換えタスクで決める
- メニューから dialog を開くとき、メニュー側の復帰が dialog の初期フォーカスと競合した（実装担当の観測。Base UI）。復帰先は開く側で決めるのが素直

### ダイアログ（AC6）: ライブラリの Dialog へ寄せる案

主な理由は、ライブラリに寄せると次の既存の仕組みが要らなくなり、Esc とフォーカスが 1 系統になること。

- inert 回避のためのポータル
- `openModalDialogsAtom`
- Tab 循環の補完
- cancel の伝播止め
- トーストの付け替え

新たに要るものは次のとおり。

- z-index の階層。ネイティブ dialog は top layer だが、Ark の Dialog は top layer を使わない（`@ark-ui/react` 5.40.1、`@zag-js/dialog`・`popover`・`dismissable` 1.49.0 の dist に `showModal`・`showPopover`・popover 属性がない。ソース読み）。z-index は決めず、dismissable の layer stack が `--layer-index`、`--nested-layer-count`、`--z-index` の CSS 変数を設定するだけで、値はアプリ側が決める。フォーカスは focus-trap で、modal のときは `preventScroll` と `aria-hidden`。Portal は既定で `document.body`（`container` で変更できる）
- `dialog[open]` に依存する判定の書き換え（`useGlobalShortcuts`、`useWorkResultsDismiss`）。ライブラリ版では body フォーカスで再生中の Space が背後に漏れた（Base UI・Ark UI とも検証済み）
- Base UI の Dialog は、Tab で focus guard に一瞬出る挙動の確認

補足として、試作でネイティブ dialog に出た問題がある。これらは既存コードの直せる不具合が主で、寄せる理由の主軸にはしない（下の節も参照）。

- 閉じた後のフォーカスが BODY に落ちる。原因は `useDialogModal` が、開いた元の消えたメニューを復帰先に覚えること。Base UI の Dialog も、`finalFocus` を指定しないと BODY に落ちる
- 変換中の Esc で閉じる（CDP の合成での観測。実機未確認）。原因は `useDialogModal` の `onCancel`
- メニューと backdrop クリックの二重反応。Base UI・Ark UI とも検証済み。ライブラリのメニュー全般で起きる。ライブラリの Dialog に寄せれば `useDialogModal` の backdrop 判定ごと無くなる
- dialog 内のメニューに container の配線と `modal={false}` が要る

移行は doc-9 の順どおり最後（ダイアログとトースト）。それまでのネイティブ dialog 内のメニューは、container を dialog にして、Base UI なら `modal={false}` とする。

### 置き換え順（AC7）

doc-9 の案どおり。

1. ボタン起点のメニューとポップアップの見た目を、モックで相談する
2. メニュー（右クリックとボタン起点で項目定義を共有）とポップオーバーを同じ統合ブランチで寄せ、`usePopoverEscape` を削除する。S3 の実測は、自作の `usePopoverEscape` を残したままではメニュー外のフォーカスで両方閉じることを示した。寄せたあと、Ark は層のスタックで追加の配線が要らない。Base UI は共通層が要る
3. ツールチップ → セレクト・スライダー・タブ → コンボボックス → ダイアログとトースト。Ark を選ぶ場合、コンボボックスとダイアログは同じ統合ブランチでまとめて置き換える（移行期間の混在の節）
4. DRAFT-53（作品の複数選択と右クリック）

## ユーザーに確認したい判断

1. 土台を Ark UI にするか Base UI にするか。推奨は Ark UI で、僅差。移行期間の混在では Base UI が有利で、その点は推奨を弱める。
   - Ark UI を選ぶと引き受けるもの: サブメニューの Esc の回避（約 15 行）を持ち続けること。zag の既定は APG と違い、上流に変える動きがない（サブメニューを使う予定がなければ、この回避は要らない）。コンボボックスとダイアログを同じ統合ブランチでまとめて置き換える制約。フォーカス復帰を `finalFocusEl` に任せる形で、ADR-0014 の原則 3 と TASK-248 の方針を改めること。1 クリックで 2 層が閉じる動作と、退出中の状態表示、`present` の配線、`focus()` で外へ移すとメニューが閉じることも、注意点になる。得るものは、入れ子の Esc の回避 0 行と、閉じた瞬間のフォーカス復帰
   - Base UI を選ぶと引き受けるもの: 共通層（約 105 行）と、`Menu.Root` を置き換える規約と lint。得るものは、既定が APG どおりで上流もその方向、`focus()` でメニューが閉じない、motion の公式手順、移行期間の混在でも部品ごとに段階的に置き換えられること
2. 右クリックメニューの外を左クリックしたとき、メニューを閉じるだけにするか、そのクリックを行にも届けるか。答えは置き換えタスクで使う。Ark で測った動作は次のとおり。外の別の行をクリックすると、クリックした行にフォーカスが移ってそのまま残る。フォーカスできない領域（上部バーの空白）では、約 30ms BODY を経て、右クリックした元の行へ戻る。Base UI の自前復帰でも、クリックした行にフォーカスが残る。`finalFocus` に関数を渡す形だけが、取り合いになる
3. ダイアログをライブラリへ寄せるか。寄せると、inert 回避のポータル、`openModalDialogsAtom`、Tab 循環の補完、cancel の伝播止め、トーストの付け替えが要らなくなり、Esc とフォーカスが 1 系統になる。代わりに、z-index の管理と、`dialog[open]` に依存する判定（再生中のショートカットが背後に漏れる）の書き換えが要る。ネイティブのまま残す場合は、既存の不具合の修正だけで済むが、Esc とフォーカスが 2 系統のままになる
4. フォーカス復帰の方針。案は、戻し先をアプリが決め、タイミングはライブラリに任せる（Ark の `finalFocusEl`）。Ark の実測では、メニューも Dialog も閉じた瞬間に戻り、外側クリックと取り合わず、Popover 2 つの軸A→B切替でも奪い合いがなかった（12 通り、検証済み）。TASK-248 の決定の文言と ADR-0014 の原則 3 を更新する。全部自前を維持する場合は、ライブラリの復帰を止める配線が要る
5. ダイアログを最後に置き換える順番でよいか。前倒しにすると、メニューとダイアログの Esc とフォーカスを同時に 1 系統にできるが、1 度に変えるものが増える。Ark を選ぶ場合は、ダイアログの前倒しでも、コンボボックスを同時に置き換える必要がある
6. 試作で見つかった既存の不具合 3 件を起票するか（下の節）
7. doc-8 の「ContextMenu で作る」の修正。試作では、Base UI の `ContextMenu` 部品は modal 固定で、開いたまま別行を右クリックする口が無いので使わなかった。メニュー本体に自前の contextmenu ハンドラ（Ark なら `ContextTrigger`）で作る形に、doc-8 を直すか
8. AC3 の実 IME の確認。実機（Windows の IME）で確かめるか、合成イベントでの確認で足りるとするか。確かめるなら、S3 の検索欄とダイアログ内のコンボボックスで、変換中に Esc と Enter を押す。別 PC では、試作ブランチを git 経由で取り込む（プッシュは人間が行う）
9. サブメニューを実際に使う予定があるか（背景メニューの「表示の切り替え」をサブメニューにするかなど）。使う予定がなければ、Ark の唯一の回避が要らなくなり、Ark の優位が増す
10. zag（Ark の土台）に、サブメニューの Esc について issue を出すか。出す価値はあるが、外部への投稿になるのでユーザー判断

## 試作で見つかった既存コードの不具合

ライブラリ選定とは無関係で、直せる不具合。AC6 の補足の問題の原因もここにある。ライブラリを置き換える前に直すか、起票する。起票はユーザー確認後に行う（統括がまとめて確認する）。

- `GroupValueQuickList` の検索欄の Esc が `isComposing` を見ない（`handleSearchKeyDown`、`handleListKeyDown`）。変換中の Esc でポップオーバーが閉じる。検証済み
- `useDialogModal` の cancel が `isComposing` を見ない。CDP の合成での観測で、実機では未確認
- ネイティブ dialog を、開いた元が消えた状態から開くと、閉じた後のフォーカスが BODY に落ちる。検証済み

doc-8 の「ContextMenu で作る」は、既存コードの不具合ではないが、試作の結果と合わない（修正の判断は「ユーザーに確認したい判断」の 7）。
