## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-428系の改修中、複数の担当から `server/tests/real/metaCasRace.test.ts` の「CASとrenameの間に並行書き込みがあっても後勝ち消失しない」がタイムアウト（5000ms）で落ちる報告が繰り返し上がった。各担当は他worktreeとのCPU競合と判断していたが、統括が統合ブランチ（ad27b63）で他に何も走っていない状態で単体実行したところ、5005msでタイムアウトして再現した。

切り分け結果:
- テストファイル自体も、CAS/renameのロジックも、統合ブランチでは一度も変更されていない（`git diff --name-only master..HEAD` で確認）
- したがって TASK-428系の改修由来ではない
- ただしベースライン計測（1c64eda、改修着手時点）では全パスと報告されていた

タイムアウトが5000msと短く、マシンの負荷状況で結果が変わる性質に見える。単に閾値を上げるのが正しいのか、テストの構造（並行書き込みの待ち方）に問題があるのか、あるいは実装側にタイミング依存の弱さがあるのかを切り分ける。

「負荷がかかると落ちるテスト」は、他の失敗の判定精度を下げる。実際この改修中、複数の担当が自分の変更由来かどうかの切り分けに時間を使っている。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
追加観測（2026-09-08）: 統合ブランチ b2e0344 での合成検証時、他worktreeとのCPU競合下だったにもかかわらず metaCasRace はパスした。一方、統括が他に何も走っていない状態で単体実行したときは 5005ms でタイムアウトして落ちている。負荷の有無と結果が対応していないため、単純な「負荷でタイムアウトする」問題ではなく、実行タイミングに依存して確率的に落ちるフレーキーテストと見られる。切り分けの際は、負荷条件を揃えるより、同じ条件で複数回繰り返して再現率を測る方が有効。

追加検証（2026-09-08、実装担当）: 修正前コード（a3e7039時点）で単体実行を30回連続計測（無負荷・他プロセス競合なし）。bun報告値で最小3.85s、最大4.68s、5000ms超過は0/30。統括が観測した5005msは同一条件下で直接は再現できなかった。

それでも「既定タイムアウト5000msに対する余白の薄さでランダムに超過する」という診断を採る根拠: (1) 修正前の分布の最大値4.68sは5000msまで残り320msしかなく、裾が5000msに肉薄している。統括が観測した5005msはこの分布のさらに外側の稀な裾と考えるのが自然。(2) 修正後の実行時間は2〜7倍の余白があり、仮に別要因が残っていたとしてもこの余白で吸収される。低確率事象の直接再現に追加コストをかけても判断は変わらないため、これ以上のサンプリングは行わなかった。

修正後の実測値（計測条件により差が出るため両方記録）:
- 実装担当（無負荷・単体10回）: 1.4〜2.2秒 / 高負荷（12coreをyesで飽和）: 2.1〜3.0秒
- レビュー担当: 無負荷 0.68〜0.76秒 / 高負荷 2.51〜3.78秒
いずれも既定5000msに対し2〜7倍の余白があり、環境間のばらつきを踏まえても十分な余裕がある。
