## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
@tanstack/react-virtual を使う仮想化リスト/グリッドの共通基盤が存在せず、必要になるたび各コンポーネントがゼロから配線を組み立てている。5箇所に散った重複は結果であって、原因は共通土台の欠如。

グリッド系2つ（client/src/features/library/ui/WorkGrid.tsx、AxisValueGrid.tsx）は「ResizeObserver でコンテナ幅計測 → 列数計算 → estimateSize → virtualizer 初期化 → resetKey で scrollToIndex(0)」という同じ5ステップを別々に書いている。

リスト系3つ（WorkListPane.tsx、AxisValueRows.tsx、AxisValueQuickList.tsx）は「virtualizer 初期化 → resetKey で scrollToIndex(0)」という同じ2ステップを別々に書いている。

個別の重複箇所:
- scrollToIndex(0) リセット: WorkGrid.tsx:221-226、WorkListPane.tsx:84-89、AxisValueRows.tsx:105-111、AxisValueGrid.tsx:103-108、AxisValueQuickList.tsx:108-124（WorkGrid と WorkListPane はコメント文言まで一致）
- docked bar 分の paddingEnd 計算と無限スクロール検知: WorkGrid.tsx:136-139,229-235 と WorkListPane.tsx:66-69,91-97（virtualScroll.ts に関数はあるのに useEffect の配線だけ共通化されていない）
- ResizeObserver によるコンテナ幅計測: WorkGrid.tsx と AxisValueGrid.tsx

docs/design-system.md 自身が「行・軸系コンポーネントを追加するときはこのパターンを踏襲する」と書いており、今後も同じ配線が増える前提になっている。複製は3件目の時点で共通化のタイミングを超えており、5件に達した現在は構造的負債。個別に scrollToIndex だけ切り出す対応では、6件目が増えたときにまた同じ議論になる。

TASK-176/177 のようなスクロール制御起因の不具合は、この配線の食い違いから生まれやすい。

## 方針

useVirtualList({ count, estimateSize, resetKey, gap, padding }) と useVirtualGrid({ items, tileSize, gap, resetKey })（列数計算・ResizeObserver 込み）を用意し、5コンポーネントすべてをこれに載せ替える。

段階: まず挙動が完全に同一なリスト系3つから useVirtualList を切り出す（低リスク・機械的）。次にグリッド系2つの列数計算・ResizeObserver を含む useVirtualGrid を切り出す。列数計算は WorkGrid が justified layout 分岐を抱えて複雑なので、AxisValueGrid 側の単純な square-only 実装をベースに justified 対応をオプションとして拡張する向きが素直。

なお TASK-200 で判明した通り、仮想化ラッパーは flex コンテナの子として flexShrink: 0 が無いと指定した高さが無視され paddingEnd が効かなくなる。共通土台側でこの前提を吸収すること。

あわせて、AxisValueList.tsx:62-66 と AxisValueQuickList.tsx:89-93 で「filter → sort → 階層化」の合成が再実装されている（コメントは「同じロジックを使い回す」と書いているが実際は再実装）。これも1本に切り出す。

判断の基準: 実装コストや影響範囲の広さを理由に見送らないこと。
