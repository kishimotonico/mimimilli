## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
smokeテスト「未登録タブでRJコードを編集でき、候補を1件ずつ除外して元に戻せる」が、単体実行時には再現性のある形で失敗し、フル実行（4ワーカー並列）では毎回パスする。

TASK-430 の実装担当が発見。切り分けとして、メインリポジトリ側の feat/uiux-audit HEAD（1a038b6、当該タスクの変更を含まない状態）でも同じ手順で同じ箇所が失敗することを確認済みで、特定のタスクの変更に由来するものではない。

テスト順序への依存が疑われる。フル実行では先行するテストが作った状態に依存して通っているだけ、という可能性がある。その場合、テストが検証しているつもりの内容と実際に検証している内容が食い違っている。

TASK-434（metaCasRace が単体実行では失敗し負荷下では通る）と現象の向きが逆だが、いずれも実行文脈に依存して結果が変わる問題なので、原因調査の際は関連を確認すること。

調査結果（2026-09-08）: テスト順序への依存ではなく、実装側のタイミング競合だった。

機序: scanJobManager が新規作品を自動登録すると server/src/app.ts の dlsiteJobs.enqueue("new", ...) が無条件に走り、DLsite一括取得が自動開始する。クライアントの ScanRuntime が dlsiteBulk.attach() で完了済みの結果を即座に atom へ反映し、GlobalToast が action付き（寿命10秒）のトーストを表示する。スキャンダイアログが開いているため、TASK-327 の仕様どおり useTopmostOpenModalDialog が検出したダイアログ配下へポータルされる。同時に UnregisteredTab がローカル宣言している別の Toast（「候補から外しました」「元に戻す」）も同じダイアログ配下へポータルされ、2つが同じ固定位置に重なって一方が他方のボタンを覆う。

フル実行で通っていたのは前提が整っていたからではなく、CPU競合で実測時間が伸びて10秒のトーストが「元に戻す」クリック時点で既に消えていたため。通っていたほうが偽陽性だった。これはテストだけの問題ではなく、実操作でも「元に戻す」が押せなくなるユーザーから見えるバグ。

design-system.md の「同時に複数のトーストを表示するキューは持たない。呼び出し側がif連鎖で1件だけ選んで描画する」（TASK-428.2 で明文化）は、GlobalToast 内部の if連鎖にしか当てはまっておらず、GlobalToast とローカル宣言の Toast が同時に可視化されるケースが想定外だった。

方針（2026-09-08、オーナー決定）: 契約「同時に1件だけ」を守り、ローカル宣言の Toast を無くして単一ホストへ集約する。スタック表示（契約変更＋モーダル内2段積み）と、局所対処（他画面に同じ衝突が残る）は不可。

設計指針:
- Toast はコンポーネントを各所に置くのではなく、単一ホスト（GlobalToast）へ表示要求を出す hook（useToast のような shared/ui の API。message / actions / lifetime / priority を持つ）に統一する。UnregisteredTab・WorkTagEditor 等の局所 Toast はその hook 呼び出しへ置き換える
- ポータル先の判定（useTopmostOpenModalDialog）はホスト1か所だけが持つ
- 優先順位はホストの if連鎖に「ユーザー操作の直接結果でアクション付き（元に戻す等）」＞「ジョブ結果など情報通知」の順で組み込む。今回の衝突は undo が勝つ
- 負けた情報通知はキューに入れず捨ててよいが、その情報が別の場所（DLsite一括結果なら GET /dlsite/bulk の直近結果と通知ベル）から辿れることを確認する。辿れない種類の通知が見つかったら「捨ててよい情報」ではないので報告すること
- design-system.md の記述を「呼び出し側の if連鎖」から「単一ホストの優先順位チェーン」へ書き換え、優先順位の規則を明文化する
- 偽陽性だった smoke は、単体実行で再現する形（トースト寿命を待たずに衝突を検出）に直して回帰を固定する

TASK-428.2（トーストの表示寿命・配置・操作契約の共通化）の受け入れ条件との重なりを確認し、428.2 側に「局所 Toast の撤去」が漏れていたなら related に記録すること。
