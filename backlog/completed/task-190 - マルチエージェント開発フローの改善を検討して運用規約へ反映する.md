## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
doc-5 提案A〜Jの採否（判断基準: 2026-08-07確定の高速イテレーション方針。CI/gitフックは当面導入しない・過剰なリグレッション検証は禁止・コード品質と設計は最重視で不変）

- A 採用: 実装担当は1タスク1worktreeを既定に。統括が手動 git worktree add でパスを用意（Agentツールのworktree隔離は罠があるため不使用）。理由: doc-5最大の損失（テスト汚染・統括の誤判断・コミット切り分け不能）を根絶。後半のworktree分離で干渉ゼロの実績
- B 採用: レビュー担当Sonnetを常設し、タスク完了ごとコミット前に「報告に書かれていない副作用」観点のみでレビュー。理由: Codexが見つけた4件はこの水準で届く。手戻り（TASK-184/185型）の予防コストとして軽い
- C 採用（実装済み・追加起票不要）: TASK-189でsmoke/visual分割は完了済み。運用ルール（visualはUI変更時のみ実行）のみAGENTS.mdへ反映
- D 採用: 受け入れ条件は7項目程度を上限、超えるなら分割。起票時に確定仕様を1行ずつACへ対応付け。理由: TASK-183の粒度肥大・TASK-186の落とし漏れ防止
- E 採用: 進捗は --check-ac で表現、完了時テキスト報告必須、統括のpolling廃止
- F 修正採用: 原案の「真のベースラインまで遡った実測を要求」は過剰リグレッション検証の禁止方針と衝突するため変更。『根拠のない「既知の障害」「元から壊れている」を理由に赤を放置しない。赤は今直すか即起票する』へ。放置しなければ遡り調査自体が不要になる
- G 採用: タスク着手時にdev serverの生死を確認（コストゼロの1行ルール）
- H 採用: 統括は check/test/ブラウザ操作をしない。コミット前確認も例外にしない
- I 採用: 実機検証は実データDBに対して行わず、フィクスチャ内蔵viteの一時起動（MIMIMILLI_MOCK_SCENARIO指定）で行う。手順をAGENTS.mdデバッグ節へ転記。fixture側の大量データ生成手段は要件未確定のため保留（必要時に起票）
- J 採用: 共有機構を個別実装へ置き換える際は提供機能を列挙し喪失がないか確認。指示側は「拡張」か「置き換え」かを明示
- 追加（提案外）: 検証軽量化ルールを新設。実装中ループは変更範囲に絞ったテストのみ、フル check+test はタスク完了時に1回、visualはUI変更時のみ。CI・gitフックはテスト高速化まで導入しない
<!-- SECTION:NOTES:END -->
