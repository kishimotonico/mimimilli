# 正本編集と検索の契約比較 2026-09-21

対象: master `119aef15fa640b97fcbd5c507ecbd98dde1db411`。[レビューTODO](review-todo-2026-09-20.md)のRV-04・RV-05を扱います。静的な設計比較であり、仕様決定・実装ではありません。前回の指摘を追加の欠陥として数え直すものでもありません。

## 編集の基準はsourceから取得する

編集値とrevisionを同じ読取りから返すことは、保存UIの方式に関係なく必要です。現行の `getWork` はcatalog値と現在sourceのrevisionを組み合わせます。この不一致を解消する二案を比較しました。

| 観点 | A. 編集専用source snapshot | B. catalog値と投影元revision |
| --- | --- | --- |
| 編集開始 | 一回のsource読取りから値とrevisionを取得 | catalogの値と記録済みrevisionを取得 |
| 外部編集後、scan前 | 現在の正本をそのまま編集できる | source不一致を確認し、再投影を要求する |
| 投影が失敗しているとき | 有効な正本とidentityを確認できれば編集できる | 投影を回復するまで編集できない |
| 閲覧との一致 | 背面のcatalog表示と一時的に異なり得る | 同じcatalog値を使える |
| 追加する責務 | 編集用の型・読取り契約 | 投影待ち・再投影後の編集再開 |
| 適する仕様 | 外部編集を認め、正本を編集の基準にする | 編集前に投影との一致を必須とする |

Aを推奨します。Bも整合した設計ですが、再構築可能な投影の失敗で正本編集まで止まる依存が強くなります。Aに必要な型は、概念上 `WorkEditSnapshot = { workId, title, tags, urls, sourceRevision }` で足ります。新たな汎用エンティティストアは不要です。

`readMetaSource` はbytes・検証済みmeta・そのbytesのrevisionを一体で返します（`server/src/adapters/real/meta.ts:81`）。編集snapshotはそこから作り、probe、playlistの解決済み尺、cover寸法、bookmark、resume、再生履歴を含めません。schemaによるタグの正規化は許容します。「同じ読取り」とはraw JSONをそのまま画面に見せる意味ではありません。

catalogは編集対象の場所を探す索引として使います。ただし、読み取ったmetaのIDと要求work ID、現在の管理rootと記録location、既知のidentity conflictを確認します。消失・不正・不一致はエラーにし、別の場所を推測して編集を継続しません。編集開始ごとに全ライブラリを走査して重複を探す必要はありません。

保存はbase revisionと変更フィールドを送り、成功応答の編集snapshotを一体で採用します。fieldごとのrevisionや配列の自動マージは追加しません。CAS、replace直前のbytes再確認、未知フィールドの保持は維持します。根拠は `meta.ts:259`、現行の問題となる読取りは `server/src/adapters/real/workMethods.ts:66` です。

bookmarkを編集snapshotから外すだけでは不十分です。更新APIもsource編集とuser状態の変更を分離し、同一要求で両方を確定させる契約にしません。現行PATCHはbookmarkを先にuser DBへ保存できるため、その経路を残すと新しい保存結果の外に部分成功が残ります（`workMethods.ts:159`、`shared/src/api.ts:179`）。

## 保存方式の比較

| 観点 | 一つのdraftを一括保存 | 項目別の即時保存 |
| --- | --- | --- |
| 保存の単位 | title・tags・urlsの変更を一回のCASで確定 | 項目の確定ごとにCAS |
| dirty・失敗 | 編集セッション全体に一つ | 項目ごとに保持 |
| タグ削除の取消 | 保存前はdraft内で戻せる | 既存の保存後undoを保ちやすい |
| revision更新 | 一回の保存後にsnapshotを交換 | 各成功後に次操作へrevisionを渡す |
| 部分成功 | 一つのmeta更新内では発生しない | 先に保存した項目は、後の失敗でも残る |
| 失う価値 | 編集途中で項目だけを先に永続化できない | 画面全体をまとめて破棄できない |

編集ダイアログでは一括draftを推奨します。一つの正本ファイルを編集する単位と、保存・競合・破棄の単位が揃うためです。ただしこれは製品上の選択であり、C1の是正に一括保存化は必須ではありません。タグを短い操作ごとに保存することを優先するなら、項目別保存も成立します。

一括案では、現行の「閉じる際にタイトルを保存し、返ったrevisionでURLを保存する」処理と、項目別のpending/error、draftをpropsへ追従させるeffectを減らせます。既存のPATCH schemaとmeta更新関数は複数フィールドを受け付けます（`shared/src/api.ts:179`、`workMethods.ts:156`、`client/src/features/library/ui/preview/WorkEditDialog.tsx:194`）。

入力検証、保護タグ削除の確認、未保存のまま閉じる確認は残します。保存前のローカルundoと、保存後にもう一度書き戻すundoは同じものではありません。既存のタグundoを当然に全て削除できるとは評価しません（`client/src/features/library/ui/preview/useWorkTagEditor.ts:93`）。

項目別案でも、テキスト・URLの入力途中には局所draftが必要です。Enter・blur・明示ボタンのどこで確定するかを定め、画面全体の保存／破棄は持たせません。共有revisionの競合を避けるには、一つのeditor内で保存を直列化するか、保存中は他の確定操作を止めます。アプリ全体の汎用コマンドキューは不要です。

FilesとLibraryは同じwork ID起点の編集契約を使い、セッション状態はそれぞれ開いたeditorの局所状態で構いません。global editor hostを必須にしません。詳細ペインのクイックタグ編集を残す場合もsource snapshotを基準にし、ダイアログ内のdraftとは別の明示的な操作にします。

## 保存結果と再取得の状態

以下は単体メタ編集の契約です。scan・DLsiteジョブ全体の結果型を統一する提案ではありません。

| 発生したこと | 保持するもの | 次に許す操作 |
| --- | --- | --- |
| 編集中に背景再取得 | baseとdraftを保持。勝手に上書きしない | 元データ変更の案内、明示的な読込み直し |
| 保存前の検証失敗 | draft | 入力修正 |
| CAS不一致 | draftと、編集に使ったbase | 最新sourceを確認してやり直す。自動マージしない |
| source保存・投影とも成功 | 確定snapshot | 閉じる、次の編集 |
| source保存済み・投影失敗 | 確定snapshotと未反映の表示 | 最新正本からの再投影、または明示scan |
| 応答喪失 | draftと結果不明の表示 | sourceを読み直して現在値を確認 |
| 再確認も失敗 | draftと結果不明の表示を維持 | 再確認。保存そのものを自動再送しない |

応答喪失後に希望した値が見つかっても、それは「現在その値になっている」と確認できたという意味です。当該要求の成功や投影完了の証拠ではありません。希望値と異なる場合も、未保存だったのか後から変更されたのかを推測しません。操作台帳なしで分かる範囲を超えて保証しない仕様にします。

再投影の対象は現在の正本です。保存後に外部編集が進んでいれば、古いrevisionのbytesを復元してはいけません。未反映の操作結果はその操作の記録であり、以後の全変更が未反映であると示す永続的な作品状態ではありません。

保存成功後の一覧再取得が失敗しても、draftを未保存へ戻しません。編集snapshot更新とqueryの更新は別の責務です。編集用snapshotを分離すると、resumeの表示を維持するためにWork応答を一部だけmergeする処理を、編集基準から外せます（`client/src/features/library/model/workPatchInvalidation.ts:93`）。閲覧cacheの更新方針まで自動的に不要になるわけではありません。

## 再投影を再試行するための前提

現行の `projectMetaFile` をそのまま再投影APIへ公開する案は推奨しません。`scanner.ts:538` から `scanRegister.ts:112` を通り、`syncDetectedRjCode` が正本を書き換える場合があるためです（いずれも `server/src/adapters/real/` 配下、検出処理は `meta.ts:354`）。

投影は、検証した正本と観測したmediaからcatalogを更新するだけにします。推定RJコードを正本へ保存する判断は、登録や明示編集に移します。これは既存レビューS3と同じ改善であり、C1の別タスクとして重複計上しません。保存後の再投影でrevisionがさらに変わる設計を残したまま、「確定snapshotを返す」APIだけを追加しても契約は揃いません。

最小の構成は、編集snapshotの読取り、revision付き更新、source確定と投影成否を区別した応答です。作品限定の再投影操作は利便性のための選択肢であり、既存の明示scanによる回復でも構いません。自動リトライ、旧revision保管、永続ジョブ台帳、汎用補償処理は要件に含めません。

独立反証レビューで、次の成立条件も確認しました。

- 投影の入力も一つのsource snapshotに固定する。現行の単作品経路は、`prepared.meta` からplaylist尺を解決した後にsourceを再読込みします（`scanRegister.ts:411`・`:112`）。正本非変更化だけでなく、meta値・解決したplaylist・投影revisionを同じ入力に揃え、公開直前に変化を検出した場合は古い入力を最新扱いで公開しない契約が必要です。full scanの確認は `scanner.ts:413`、単作品公開は同 `:466` にあります。変更が続く場合の無制限再試行はせず、反映未完了として次の明示操作へ渡せます。
- catalog公開と、その後の応答構築を分ける。現行は `publishWork` の後にlive probe付きWorkを取得するため、その取得が失敗しても `projectMetaFile` 全体がrejectします（`scanner.ts:484`、`workRefresh.ts:8`）。すべての例外を「投影失敗」と表示してはいけません。編集応答はCAS結果から作り、probeを保存成功の条件から外す案が単純です。
- scanによる回復は対象作品だけの再試行ではない。他作品、missing、診断も更新する広い操作なので、狭い即時回復は保証せず、該当作品の反映が確認できるまで未反映の案内を残します。

ここで求める一致は、読み取って投影した版についてのものです。確認直後を含め、外部ツールによる将来の変更まで止める保証ではありません。

## 検索契約の比較

分類値一覧を「現在の対象の分類」とする案Aと、「全作品への独立した入口」とする案Bを比較しました。現行は、全体から分類値を取得する経路と、選択後にview・qを残す経路が混在しています。個別の条件追加だけでなく、この二つのどちらを選ぶかを先に決めます。

案Aを推奨します。お気に入りやsmart folderを選んだ状態で、そこに含まれる作品を別の分類で絞る操作を一貫させやすいためです。「すべての作品」への切替を明示操作として残せば、全体の分類を見る用途も維持できます。

| 操作 | A. 現在の対象内で分類（推奨） | B. 全作品への独立した入口 |
| --- | --- | --- |
| お気に入り＋qからタグ追加 | fav・qを維持し、操作後のタグ条件で件数を出す | 分類へ移る際にfav・qを外す。現在対象への追加を残すなら別の入口が必要 |
| smart内でq・一時sort変更 | 保存ルールにqを追加。保存sortを既定にし、一時sortは表示だけ変更 | 分類入口の選択とは別判断。smartで禁止するなら入力とURLにも無効な値を残さない |
| タグの置換／追加 | 対象とqを維持。タグ条件だけを操作の意味に従って変更 | 分類へ移った時点で文脈を解除し、全体からの選択として扱う |
| 分類値名を絞って作品へ戻る | qは作品の絞込み、値名検索は表示用。対象は維持 | 値名検索だけ使い、作品検索の文脈はブラウザー履歴で戻す |
| 編集で作品が集合から外れる | 表示中の一覧と対象に応じたfacetを再評価 | 全体facetは比較的単純だが、以前の対象の一覧更新は別途必要 |
| URLから復元 | 対象・作品条件・分類表示を区別して復元 | 分類URLから適用しないq・view等を除去し、入力欄にも残さない |

現行の根拠: `shared/src/api.ts:81`・`:114`、`client/src/features/library/model/libraryPresentation.ts:119`、`useAxisFacetsQuery.ts:17`、`useLibraryQueries.ts:161`・`:211`、`client/src/entities/library/model/navigationActions.ts:19`・`:57`、`client/src/features/navigation/model/navigationUrl.ts:151`・`:219`。

案Aが失うのは、狭い対象に留まったまま全作品の分類分布を眺める性質です。候補値も少なくなります。案Bは全体の分類ブラウザーとして明快ですが、お気に入りやsmart folderを段階的に絞る連続性を失います。どちらを採る場合も、表示中の検索条件を効かないまま保持する中間状態は避けます。

### 必要な分離と、増やさない仕組み

概念上は、対象を `all / view / smartFolder`、追加条件を `q / tags・year`、表示を `works / facet(axis)` に分ければ足ります。viewとsmart folderは相互排他です。URLとquery keyはこの意味を表し、APIを必ず一つにする必要はありません。

スマートフォルダーの保存ルールは残します。OR・除外の表現力を通常のタグANDへ平坦化せず、既存の評価関数を使います。値名検索も作品検索とは別のローカル表示処理として残します。作品sortと値一覧sortは別物であり、表示方法を分けることで無理に共通のenumへ揃える必要はありません。

件数は「その入口の主操作後の集合」を表すと決めます。通常タグの追加は現在タグへのAND、置換は選択タグ全体の置換です。ただし `@year` は一つしか選べず、追加でも既存年を置き換える現行仕様を維持します。一律に「現在条件 AND 候補値」と計算せず、ナビゲーションと件数計算で同じ操作後条件を使います。根拠はADR-0012の年の単一選択と `client/src/entities/library/model/navigationActions.ts:26` です。

一つの件数で、主クリック・Ctrl/Cmdによる反転・追加ボタンの全結果を同時に表そうとはしません。主操作の件数であることを入口の表示契約にします。

この定義を採るなら、smartの作品queryへqと任意の一時sortを渡し、facetにも対象viewまたはsmart folderとqを渡します。有限のunionや相互排他の検証で足り、汎用AST、query compiler、全条件のSQL化は必要ありません。

### 編集後の再評価

現行の `getWorkPatchInvalidationTargets` は、作品が集合に属するかを完全に判定するものではなく、再評価が必要かを判定する保守的な影響分類です（`client/src/features/library/model/workPatchInvalidation.ts:30`）。これを検索エンジンの重複実装だと断定しません。

対象内facetを導入すると、タイトル検索やお気に入りなど、タグ以外にも集計へ影響する条件が増えます。最初は検索に影響し得る編集の完了時に、表示中一覧・facetを再評価し、非表示queryをstaleにする方針で構いません。表示中一覧のresetはスクロール位置を失う場合があるため、即座に全ての局所更新を削除する判断もしません。

再生中のresume保存ごとに全queryを更新する意味ではありません。履歴・再生位置の鮮度は別に定義し、再生終了や画面への再入場など、どの境界で検索結果へ反映するかを選びます。リアルタイムで常に全件数が一致する保証は要求しません。

## 仕様決定へ渡す判断

まず編集用source snapshotを採るかを決めます。これはダイアログの保存方式や検索UIの大幅変更を待つ必要がありません。投影でsourceを変更しない境界も同時に定めます。

その後、一括draftか項目別保存か、分類を現在対象内で行うかを製品仕様として選びます。いずれも本書の推奨は一案であり、採用済みの仕様ではありません。新APIや共有部品を先に増やしてから、その意味を後付けする順序は避けます。
