# コア設計レビューの調査方針 2026-09-20

状態: 調査完了。[調査結果](core-design-review-2026-09-20.md)に根拠・推奨する契約・反証をまとめました。この文書は、ユーザーの依頼により並行調査するエージェント向けに先に公開した方針です。実装計画や仕様決定ではありません。

## 対象と目的

対象はmaster `119aef15fa640b97fcbd5c507ecbd98dde1db411`。既存のレビュー文書と、その作成に伴う未コミット変更は保持します。別エージェントの調査・変更には触れません。

今回は、ユーザーが「作品を変更した」「取得した」「検索した」と認識する操作と、内部の状態が一致する設計になっているかを調べます。現行仕様を最適と仮定せず、保証を絞ることで処理を減らせるか、逆に明確な保証が不足していないかを評価します。

前回のレビューでは責務の分散や仕様の単純化候補を確認しました。今回はそれらの指摘を増やすことではなく、アプリの中心となる契約を横断して確かめることを目的にします。

## 調査の順序と分担

調査は次の順に結論を組み立てます。独立したコード追跡は並行して行います。

| 領域          | 追跡するもの                                                                        | 判断したいこと                                                         |
| ------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 1. 変更の反映 | meta・実ファイル → catalog → API → Queryキャッシュ → 表示・編集中の値・再生中の状態 | どの時点の値か、誰が更新するか、古い状態を保持してよいか               |
| 2. 操作の結果 | 登録・編集・DLsite取得／適用・登録解除・取消                                        | 成功が確定する境界、部分成功の意味、失敗後の再試行が何をするか         |
| 3. 検索の意味 | 通常検索、ビュー、タグ・擬似タグ、保存ルール、facet、一覧更新判定                   | 同じ条件の意味が保たれるか、別々のモデルで同じ判断を繰り返していないか |
| 統合・反証    | 上記の契約と、ユーザーが理解する操作単位                                            | 単純化で失う機能、必要な複雑さ、提案が別の同期処理を増やさないか       |

細部の追跡はSol(medium)またはLuna(max)、横断的な判断と文書の統合は主担当が行う方針で開始しました。初回は委譲した全担当が利用枠エラーで停止したため、主担当が静的調査を実施しました。その後Sol(medium)による独立反証レビューを実施し、指摘の限定と仕様案の位置付けを調査結果へ反映しました。コード編集・テスト実行・ブラウザー操作は行っていません。

ユーザーから混乱した例としてスキャン→DLsite取得が挙がりましたが、この導線は別途大幅に見直す予定です。そのため調査対象をそこへ限定せず、作品編集・検索・再生を含む共通の契約を評価しました。

## 代表的な追跡シナリオ

- 外部でmetaのタイトル・タグを変え、scan前に詳細を開き、その後アプリで編集する。
- 音声やカバーを外部で変更し、一覧・詳細・再生でいつ変化を認識するかを追う。
- アプリで作品を保存し、正本の確定後に投影または画面の再取得が失敗した場合を、コード上の分岐として読む。
- DLsiteを取得しただけの状態と、正本に適用した状態を区別し、取消・部分成功後の表示を追う。
- 登録・解除の途中で後段が失敗したとき、既に成立した効果と再試行対象を確認する。
- 通常一覧、スマートフォルダー、facetで同じ条件を指定したときの対象集合・検索語・並び順・件数の意味を比較する。
- 一覧で表示対象の所属が変わる編集をしたとき、clientがサーバーの検索規則をどこまで再現しているかを追う。

これらは静的な経路追跡であり、障害の再現手順ではありません。特定のバグや競合窓の発見を目的にはしません。

## 根拠と評価方法

各領域で、読み取り元、書き込み先、revisionの意味、確定点、失敗後に残る効果を表にします。仕様文書・ADRと実装が異なる場合は区別し、コードだけからユーザーの意図を断定しません。

提案には、現状、推奨する契約、不要になる責務、残すべき検証、失う利便性、反証を含めます。「すべて最新にする」「すべて共通化する」といった一律の方針は置きません。推測的な自動復旧より、状態を説明して再読込みや再試行を選べる仕様も検討します。

メタファイルの正本性、user DBの独立、Filesからの未登録再生などは現行の利用目的を理解するための基準とします。変更案がその価値を失わせる場合は明記します。互換維持や実装量を理由に、現行設計を無条件に維持する判断はしません。

## 対象外と完了条件

UIの見た目、ブラウザーでの動作確認、個別不具合の網羅、性能測定、依存更新、CI・配布基盤の全体監査は対象外です。実DB・外部サイトへの書き込み、仕様変更、実装、コミット、タスクの起票・更新は行いません。

3領域の代表経路を追い、既存対策と反証を確認し、推奨する契約と未決の製品判断を別エージェントへ渡せる文書にできた時点で調査を完了します。指摘件数を目標にはしません。
