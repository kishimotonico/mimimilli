# ADR-0025: 正本の変更・投影・閲覧を責務として分離する

- ステータス: 承認
- 日付: 2026-09-21
- 関連: [ADR-0017](0017-meta-source-projection-and-work-identity.md)、[ADR-0008](0008-persistence-topology-query-ownership-playback-ids.md)、[ADR-0015](0015-client-error-contracts.md)、[設計レビューの引き継ぎTODO](../review-todo-2026-09-20.md)、backlog TASK-452〜456

## 文脈

ADR-0017 は正本と投影を分離し、作品編集を source-first にした。書込み順序は決まったが、読取り側と観測側の契約は残っていない。その結果、同じ経路が複数の責務を持っている。

`getWork`（`workMethods.ts:66`）は、タイトル・タグ・URL を catalog の行から取り、`sourceRevision` を同じ呼び出しの中で `readMetaSource` によるファイル直読みから取る。1 つの `Work` の中で値と revision の出どころが違う。catalog は外部編集を検知して自動再投影しないため、外部ツールが `mimimilli.json` を書き換えると、応答は古い値と最新の revision を組にして返す。

この応答を基準に編集すると正本が壊れる。タグを例にとる。

1. source `tags = ["A","B"]`、catalog も同値、revision は `R1`。
2. 外部ツールが `["A","B","C"]` へ書き換える。revision は `R2`。catalog は `["A","B"]` のまま。
3. 編集ダイアログが `tags ["A","B"]` と `sourceRevision R2` を受け取る。
4. タグ `D` を追加する。`buildTagsWithAdded(["A","B"], "D")` は `["A","B","D"]` を作る。`C` は考慮されない。
5. PATCH を送る。ファイルは手順 2 以降変わっていないため CAS は一致し、通過する。
6. `patchMetaFileCas`（`meta.ts:270`）は `raw.tags = patch.tags` の全置換で書き込む。`C` が失われる。

`patchMetaFileCas` の CAS は、呼び出し側が渡した基準 revision と現在の source を比較するため、リクエスト受理前の外部変更も検出できる。検出できないのは、渡された revision が編集値を表していない場合である。値と revision を別の読取りから組にすると、revision が最新であることと、編集値がその版のものであることが区別されない。パス単位ロック（TASK-419）は同時書込みを直列化するもので、この基準ずれには関与しない。

同種の混在が他にもある。

- 更新 API の `WorkPatch`（`shared/src/api.ts:179`）は、meta 正本のフィールドと user 状態の `bookmarked` を 1 つのコマンドで受ける。`workMethods.ts:156` は user DB へ先に書いてから meta を CAS 書込みする。現行のクライアントは 4 つの mutation に分かれて 1 フィールドずつ送るため混在送信は起きないが、契約は混在を許したままになっている。
- `syncDetectedRjCode`（`meta.ts:354`）は scan と単作品投影の途中で正本へ RJ コードを書き戻す。既存値が空のときだけ埋める補完動作だが、正本を観測する処理が正本を書き換える構造になっている。単作品登録・投影・復元は `full: true` を指定するため必ずこの経路を通る。
- `resolveWorkWithLiveProbe`（`workRefresh.ts:8`）は、メディアの観測・詳細 DTO の組み立て・catalog の総時間更新をまとめている。詳細を開くだけで一覧の時間ソートや smart folder の所属が変わる。
- 単作品投影は catalog 公開のあとに live probe を含む Work 取得を続ける。この後段の例外まで投影失敗として分類すると、保存済みの変更を失敗として表示する。

## 決定

正本の変更、投影の生成と公開、閲覧を別の責務として分ける。「すべての読取りは catalog を経由する」という原則にはしない。編集用 snapshot の取得は正本を読む正当な経路である。

### 5 つの契約

| 責務         | 契約                                                                                                                                         |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 編集用読取り | 同じ source 読取りから編集値と revision を返す。両者を不可分の型として扱う                                                                   |
| 正本変更     | 対象の identity・location と revision を検証し、意図した変更を確定する。別の正本に属する状態を混ぜない                                       |
| 投影         | 1 つの source snapshot を入力とし、source を変更せずに catalog を作る。古い入力を最新として公開しないため、公開前の確認を設計に含める         |
| 閲覧         | 公開済みの投影と user 状態を読む。最新 source を混ぜて編集の基準を偽装しない                                                                 |
| 結果         | source の確定・catalog への反映・その後の応答生成と再取得を区別する                                                                          |

### 編集用読取り

正本を書くすべての入口が、編集値と revision を同一の source 読取りから得る。作品編集ダイアログ、インラインタグ編集、DLsite 適用の preview が対象である。

`getWork` から、最新ファイルを読み直して `sourceRevision` を付ける処理を外す。投影の由来を示す revision を閲覧 DTO に残す場合は `projectedSourceRevision` のように用途が異なると分かる名前にし、閲覧値と最新 source の revision を合成しない。ハッシュ計算そのものは編集 snapshot、CAS、投影入力の確認に残る。

一覧・詳細は、メタデータについては catalog の投影を読み、bookmark・resume などは user 側の状態を読む。全フィールドを 1 つの `sourceRevision` で代表させない。編集画面の source 値が背後の一覧より新しいことは許容する。正本が壊れている場合も、閲覧できる投影と編集できない状態を区別できる。

### 正本変更

更新 API は meta 正本の変更と user 状態の更新を別のコマンドに分ける。`WorkPatch` が `bookmarked` を meta フィールドと同時に受ける契約を廃止する。user 状態の更新は `sourceRevision` を要求しない。

### 投影

投影は source を書き換えない。`syncDetectedRjCode` を scan と再投影の経路から外す。コード候補の検出そのものは残す。登録仕様で自動採用する場合は、登録コマンドが一度の正本確定に含め、その確定済み snapshot を投影へ渡す。既存作品の通常 scan では候補の提示までに留め、適用は正本変更として扱う。投影の途中で書いてから読み直す形には戻さない。

### 閲覧

`syncTotalDurationSec` を GET から外す。これは正本への書込みではなく派生値の catalog 更新であるため、「投影は正本を変更しない」だけからは導かれない。閲覧が公開済みの検索・ソート用状態を変える隠れた契機をなくすために外す。GET が呼ぶ別 helper へ移すだけでは責務は分離しない。総時間の更新は、メディア観測を受けた投影更新として明示した経路で計算・公開し、関連する query を更新する。

`resolveWorkWithLiveProbe` の組合せを、通常の `getWork` と正本保存の成功応答から外す。probe 能力は廃止しない。現在のメディア確認は再生準備と、明示的なメディア再確認・投影更新の責務として残す。詳細で最新の技術情報を見せる場合は、独立した live observation として返す。閲覧を契機に総時間や検索所属が変わる契約にはしない。probe cache のメモ化は禁止しない。内部キャッシュへの書込みと、検索・ソート・集計に使う公開済み catalog 値の変更を区別する。

### 結果

保存結果には確定した編集 snapshot を使う。Work の再取得成功を source 保存成功の条件にしない。catalog 公開後の応答構築で起きた失敗を投影失敗として表示しない。通信断は結果不明として扱い、操作の成功も失敗も推測しない。現在値の確認に留める。

### 編集 UI の保存方式

作品編集ダイアログは一括 draft 保存にする。対象は title・tags・urls とする。設定、bookmark、DLsite の重い操作は含めない。背景取得で dirty な入力を消さない。閉じる際の保存・破棄をこの方式に揃える。

### 移設の一覧

| 現在の処理                        | 外す場所                                       | 残す責務                                                       |
| --------------------------------- | ---------------------------------------------- | -------------------------------------------------------------- |
| `getWork` の `readMetaSource`     | 通常閲覧                                       | 編集 snapshot、CAS、投影入力の確認                             |
| `resolveWorkWithLiveProbe`        | 通常閲覧、保存成功応答                         | 再生準備、明示的なメディア再確認、独立した live observation    |
| `syncDetectedRjCode`              | scan、再投影                                   | コード候補の検出、登録・明示的な編集コマンドでの確定           |
| `syncTotalDurationSec`            | GET                                            | メディア観測を受けた投影更新での総時間の計算と公開             |

## 帰結

- 受入条件は 4 つに分ける。編集値と revision の同一読取り、投影の非変更性、GET の副作用除去、結果分類である。依存はあるが一括実装は必須ではない。
- CQRS フレームワーク、永続イベントログ、永続コマンド履歴、グローバル editor host、全体イベントバスは導入しない。
- 編集画面の値が一覧より新しくなる場面が生まれる。一覧は次の投影更新まで古い値を表示する。これを不整合として扱わない。
- `WorkPatch` の分割により、bookmark の更新が `sourceRevision` に巻き込まれなくなる。現行クライアントは既に 1 フィールドずつ送っているため、呼び出し側の破壊的変更は小さい。
- scan が RJ コードを自動で正本へ書かなくなる。空欄のまま残る作品が増えるため、登録時の自動採用か、明示的な取得操作のどちらで埋めるかを DLsite 側の導線で決める必要がある。
- 詳細画面を開いても総時間が更新されなくなる。総時間が未解決の作品は、scan または明示的なメディア再確認まで未解決のまま表示する。
- 性能を理由とした設計変更はこの決定に含めない。smart folder の計算量、facet の `statSync`、scan 結果の件数切り詰めはいずれも静的な見積もりであり、閾値を判定していない。変更する場合は想定する規模と媒体を決めて実測する。
- scan から DLsite 取得へ至る導線そのものは別途見直す。共有する source・cache・投影の境界はこの ADR の契約に従う。
