# ADR-0019: メディア配信の接続寿命を設計で管理する

- ステータス: 承認
- 日付: 2026-08-14
- 関連: ADR-0018（transport統一）、TASK-339（idleTimeout切断修正）、TASK-340（上限付きRange）、TASK-337（transport smoke）

## 文脈

Windowsドッグフーディングで、長時間再生（15分前後）すると音声が無音で停止し、再操作で「音声の読み込みが中断されました」となる不具合が発生した。本番ビルドでも再現し、Chrome media internalsには `DEMUXER_UNDERFLOW` → `BUFFERING_HAVE_NOTHING` のみが記録され、`kError` は出ない。

ローカルの最小構成（`media.ts` と同じ `createReadStream` → `Readable.toWeb` → `Response` を `Bun.serve` に載せ、クライアントが読み取りを一時停止する）で再現・対照実験を行い、原因を確定した。

1. `Bun.serve` の `idleTimeout` は配信中のストリーミング接続にも適用される（Bun公式ドキュメントに明記）。Chromeのメディアローダーは先読みバッファが満ちると接続を保持したまま読み取りを止める（defer）ため、無通信と判定され90秒（`server/src/index.ts` の設定値）で正常FINにより切断される。Content-Length宣言との不一致はHTTPエラーにならず、Chromeはエラーを上げないままバッファ枯渇で永久に停止する。
2. 副産物として、開放端Range（`bytes=N-`）に対し残り全体を1本のストリームで返す現行実装では、バックプレッシャーがファイル読み取りへ伝わらず、クライアントの受信量と無関係に要求範囲の全量が即座にメモリへ読み込まれることを実測で確認した。

`idleTimeout` の値を上げる案は、上限が255秒でありChromeのdefer（10分超になりうる）を超えるため解決にならない。

## 決定

メディア配信は「接続は切られる・長寿命接続は前提にしない」を設計原則とし、2段で対応する。

- メディア配信ルートではリクエスト単位でidle timeoutを無効化する（`server.timeout(req, 0)`。Bun公式の長寿命ストリーミング対処）。サーバー全体の `idleTimeout` はDLsite同期fetch用の設定として維持する（TASK-339）
- 開放端Rangeは上限チャンクサイズで打ち切った206で返し、クライアントに次のRangeリクエストで続きを取らせる。1接続の転送量と寿命を有界にし、バックプレッシャー不全によるメモリ使用も同時に解消する（TASK-340）

## 帰結

- 長時間再生がタイムアウト起因で停止しなくなり、経路上のタイムアウト（プロキシ等）への感度も下がる
- メディア1リクエストのメモリ使用がチャンク上限で有界になる
- 「defer中の接続維持」はTASK-337のtransport smokeで回帰検証できる
- 接続切断がエラーとして観測できない問題（Chromeが正常FINを異常と扱わない）はサーバー側では解決できない。クライアント側の停滞検知・通知は別途扱う
