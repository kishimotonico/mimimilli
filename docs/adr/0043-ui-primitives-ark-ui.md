# ADR-0043: UIプリミティブの土台に Ark UI を使う

- ステータス: 承認
- 日付: 2026-11-26
- 関連: [ADR-0014](0014-motion-reintroduction-presence-removal.md)（motion と AnimatePresence。原則3の「閉じたときの復帰」の担い手を本ADRで改訂）、[ADR-0006](0006-mobile-ui-strategy.md)（モバイル対象外）、[design-system.md](../design-system.md)、backlog TASK-525（試作）、TASK-248（フォーカス復帰の決定を本ADRで読み替える）、doc-8（右クリックの全体方針）、doc-9（候補の評価）、doc-10（試作の比較）

## 文脈

採用前は client の UI プリミティブ（メニュー、ポップオーバー、ダイアログ、コンボボックス、セレクト、ツールチップ、トースト、スライダー、タブ）を `shared/ui` 配下で自作し、位置決めだけ `@floating-ui/react` を使っていた。メニューには矢印移動・先頭文字移動・サブメニュー・チェック項目がなかった。DRAFT-53 の右クリックメニュー（doc-8）はこれらを要する。自作のまま足すと、サブメニューのホバー判定、入れ子の Esc、フォーカス管理を保守し続けることになる。

候補は Base UI と Ark UI に絞れた（doc-9）。両方で同じ題材（仮想化された作品一覧の右クリックメニュー、ネイティブ dialog の中の行メニュー、ポップオーバーの中のメニュー、確認ダイアログ）を試作して比べた（doc-10）。右クリックメニューの対象の確定、motion の退出、開閉で行を再レンダーしないことは、どちらでも満たせた。

争点は Esc の層の協調だった。このアプリはメニュー、ポップオーバー、ダイアログ、コンボボックスが入れ子になり、Esc は内側の層から一段ずつ閉じる必要がある。

- Ark UI は dismissable layer のスタックを持ち、最前面の層だけが Esc を処理する。ポップオーバーやダイアログの中のメニュー、ダイアログの中のコンボボックスは、フォーカスがどこにあっても一段ずつ閉じ、入れ子のための回避コードは要らなかった
- Base UI はメニューが容器（ポップオーバー、ダイアログ）と別のツリーになり、フォーカスがメニューの外にあると1回の Esc で容器ごと閉じた。防ぐには、すべてのメニューと容器を共通の部品に通して子メニューを数え、Esc を取り消す配線が要った。確かめられたのはサブメニュー1階層までだった。ダイアログの中のコンボボックスは配線なしで一段ずつ閉じたが、一致なしの表示を出さないと最初の Esc でダイアログまで閉じた
- セレクトの入れ子は、どちらでも確かめていない

一方、Ark UI はサブメニューの Esc でルートのメニューまで閉じる。WAI-ARIA APG の menu パターン（Esc は開いているメニューを閉じ、開いた元へ戻す）と異なり、止める設定は無い。調べた範囲では、上流に変える issue や PR は見つからなかった。ただし、サブメニューの Esc を先に受けて「サブメニューを閉じる」操作に置き換える回避は、共通のメニュー部品に1つ置くだけで済み、試作で一段ずつ閉じた。この回避が効くのはサブメニューを持つメニューだけで、doc-8 で合意した項目と既存のメニューには今のところサブメニューが無い。

Esc の層の協調はすべてのプリミティブの入れ子に関わり、Base UI の回避は全メニュー・全容器に規約を課す。Ark UI の回避はサブメニューを持つメニューだけに効き、部品の内側で閉じる。この差を決め手にした。差は僅かで、Base UI の利点（採らなかったものを参照）を重く見れば逆の結論も成り立つ。どちらのコストも条件付きで、Base UI の配線が効く状態（メニューが開いたままフォーカスが外にある）がどれだけ起きるかは分かっていないし、Ark UI の回避はサブメニューができて初めて要る。また、移行期間に自作の部品と混在させるときは、Esc を bubble 段で受ける Base UI の方が有利になる（決定の「置き換えの順番」を参照）。

## 決定

### 土台

UIプリミティブの土台に Ark UI（`@ark-ui/react`。試作は 5.40.1、本番は公開から7日以上の 5.40.0。中身は Zag.js）を使う。メニュー、ポップオーバー、ダイアログ、コンボボックス、セレクト、ツールチップ、トースト、スライダー、タブを順に載せ替え、自作の実装は置き換えたものから削除する。

### 薄い共通層

- ライブラリの props を全部通す汎用ラッパーは作らない。ADR-0014 原則5（汎用 Presence ラッパーの禁止）と同じ理由で、各所で Ark UI の部品を直接組む
- 共通にするのは次の役割に限る。置き場所は `client/src/shared/ui/` の `layer/`（メニューとポップオーバーに共通の処理）・`menu/`・`popover/`
  - 退出アニメーションの間 Ark UI の部品の寿命を延ばすフック（後述の motion との組み方）
  - メニュー部品（`useMotionMenu` ほか）とポップオーバー部品（`useMotionPopover` ほか）。上のフックと motion 化したポップアップを持つ。サブメニューを使い始めたら、サブメニューの Esc の置き換え（後述）もメニュー部品に入れる
  - 見た目のクラス、motion の variant（`useMotionVariants`）。右クリック起点のメニュー（DRAFT-53）は、作るときにボタン起点と同じ項目定義を使う
- 画面へ Ark UI の状態（`useMenu` などが返す api や machine）を渡さない。画面が読むのは共通層のハンドル（`open`・`closeAndReturn` など）だけ。ポップオーバーの開閉はアプリの状態で持ち、メニューの開閉は Ark UI に任せる（制御すると閉じるときのフォーカスの規則を失う。帰結を参照）

### Esc

- ポップアップ系の層（メニュー、ポップオーバー、ダイアログ、コンボボックス、セレクト）の Esc は、Ark UI の dismissable layer に一本化する。自前の document の Esc リスナーで層を閉じない
- 層以外で Esc を受ける処理（一覧の選択解除、再生中の層など）は `defaultPrevented` を見て、層が閉じた Esc には反応しない。試作では、メニューを閉じた Esc で一覧の選択解除は走らなかった
- Ark UI は Esc を capture 段で先に受ける。自作の Esc 処理を持つ部品と Ark UI の層を入れ子にすると一段にならないので、入れ子になる部品は同じ統合ブランチでまとめて置き換える（「置き換えの順番」を参照）。自作のポップオーバーの中に Ark UI のメニューを置くと、回避なしの状態では、フォーカスがメニューの中にあるとき1回の Esc で両方閉じた
- 自作の Esc 処理を Ark UI の層の中に残すときは、その処理が `defaultPrevented` を見て、ライブラリが処理した Esc に反応しないようにする

### サブメニューの Esc

- Ark UI の既定（サブメニューの Esc でルートまで閉じる）は使わず、Esc でサブメニューだけを閉じて親へ戻す
- 今のメニューにサブメニューは無いので、この処理は今は入れない。サブメニューを使い始めるときに、共通のメニュー部品へ入れる
- 共通のメニュー部品が、window の capture 段で Esc を受ける処理を1つ持つ。Ark UI の document のリスナーより必ず先に走り、登録順に依存しない。操作できる（inert でない）メニューが2つ以上開いているとき、その Esc の伝播と既定動作を止め、最前面のサブメニュー（DOM 上で最後の、inert でないメニュー）へ ArrowLeft を送る。孫の階層では試していない。ArrowLeft でサブメニューを閉じて親の項目へ戻るのは Ark UI の標準の動作
- サブメニューの Esc には、open を制御して close を捨てる方式や、`service.send` のような文書化されていない口は使わない。試作の旧案でこれらを使うと、ArrowRight で開いたときの先頭項目の自動ハイライトが消え、約10ms 未満の間隔の連続 Esc で2回目が断続的に失われた。window の capture 段で ArrowLeft を送る方式では、0〜100ms のどの間隔でも失われなかった（試作で検証済み）

### motion との組み方

ADR-0014 の基盤（`AnimatePresence` と条件レンダー）をそのまま使う。Ark UI の Presence は CSS アニメーションしか検知しないので、motion の退出の間は寿命を外から延ばす。

- Root に `present={open || !exitDone}` を渡し、`AnimatePresence` の `onExitComplete` で `exitDone` を立てる。この配線は共通のフックに1回書き、各所では使うだけにする
- Content は `asChild` で motion 要素にする。ルート要素を直接 motion 化するので、原則6（ラッパー DOM を被せない）に沿う
- `AnimatePresence` の内側の子はコンポーネントとして切り出し、`useIsPresent()` で退出中に `inert` を付ける（原則3の用途 a）。退出中のポップアップの上をクリックすると、inert を素通りして背後の要素に当たる。これは意図どおりの動作とする
- 表示する対象は、退出中も変わらないように props で渡すか、閉じても消さないアプリの状態から読む
- この方式では退出中も `data-state` が `open` のままになる。スタイルやテストの条件に `data-state` を使わない

### フォーカス

- 閉じたときの復帰は、戻し先をアプリが決める。ダイアログ・ポップオーバーは `finalFocusEl` で Ark UI に渡す。メニューには `finalFocusEl` が無く、Ark UI の既定（トリガーへ戻す）に任せ、戻し先を変えたい場面（外へ移ったフォーカス、項目から開いたダイアログ）は共通のメニュー層とダイアログ側で扱う（下記）。Ark UI の復帰は閉じた直後に動き、退出アニメーションの完了を待たない。試作では、メニューは Esc でも項目の実行でも12〜78ms、ダイアログは Esc の37ms後・キャンセルの60ms後に戻り、退出の完了（約200ms）より前だった。メニューの外のフォーカスできる要素（別の行など）をクリックしたときは、クリックした要素にフォーカスが残り、メニュー側は奪い返さなかった
- 閉じるのと別の層が開くのが同時に起きる場面（軸A→Bの切替など）では、A の復帰が B の初期フォーカスの後に走りうる。試作では、Ark UI のポップオーバー2つで軸を切り替えても、A の復帰は起きなかった（ホバーとクリック、復帰の設定の違いを合わせた12通りで検証済み。A を閉じた後に別のポップオーバーへフォーカスが移っていれば、既定の設定でも A は復帰しない）。本番の部品（`GroupValuePopover`）でも、ホバー・ArrowRight・50ms の往復の各方向で20回ずつ、奪い合いは起きなかった
- 戻し先はアプリが決める。右クリックした行が仮想化で外れていれば roving tabindex の行へ戻す、など
- ボタン起点のメニューの戻し先は、Esc・項目の実行・フォーカスできない領域への外側クリックではトリガー、フォーカスできる要素への外側クリックではその要素（Ark UI の既定）。プログラムの `focus()` でメニューの外（別のメニューのトリガーを含む）へ移ったフォーカスは、トリガーへ戻さず移動先に残す。自分のツリー（自分の中身から開いたサブメニュー、自分の右クリックのトリガー）への移動は閉じず、zag の判定に任せる。別のメニューのトリガーは押してもフォーカスを受けない（Ark UI が pointerdown を止める）ので、閉じるメニューが先にそのトリガーへフォーカスを移す。Ark UI 5.40.0 は、閉じる途中のメニューが残っているあいだ（pointerdown の次フレームまで）に別のメニューが開くと後から開いた方も閉じる（zag 1.47 の入れ子判定。1.49 で直っている）ので、押してすぐ離す操作は未対応。
- ポップオーバーの戻し先は、(1) フォーカスがすでに層の外へ移っていれば動かさない、(2) 開く前の要素へ戻す。その要素がメニューや別のポップオーバーの中にあれば、層の連鎖をたどって戻し先を解決する、(3) 戻し先がなければトリガーへ戻す、の順で判定する。確定時は `closeAndReturn` が同じ戻し先へフォーカスを移してから閉じる。
- メニュー項目からダイアログやポップオーバーを開くときは `MenuLayerItem` を使う。メニューはフォーカスを戻さず閉じ、開いた層の初期フォーカスを奪わない。メニューのトリガーを戻し先にする判定は `resolveFocusReturnTarget` の一か所にまとめる。
- ADR-0014 原則3は、閉じたときの復帰を「`activeElement` を検査して reason を渡す close ハンドラ」の責務としていた。Ark UI の部品については、復帰の実行をライブラリに任せ、戻し先の判断だけをアプリが持つ形に改める。`useIsPresent()` を復帰に使わない禁止はそのまま残す
- TASK-248 の「フォーカス復帰は自前、FloatingFocusManager 禁止」は、「閉じたときの復帰を、退出の完了時に動く仕組みに任せない」と読み替える。Ark UI の復帰はこれに当たらない
- 開いたときの初期フォーカスは、部品ごとに仕様として決めて `initialFocusEl` で指定する

### 右クリックメニュー

- `Menu.ContextTrigger` を一覧の外枠に1つだけ置き、行ごとには置かない。メニューも一覧に1つだけ置く
- 対象は、メニューを開く前にアプリの状態で確定する。capture 段の `contextmenu` ハンドラで、右クリックした作品（複数選択の中ならその全体）の ID を状態に入れる。開いている間の再取得・スクロール・選択変更では対象を変えない。対象が一覧から消えたら閉じる。開いたまま別の行を右クリックしたときは、`ContextTrigger` が開き直し、対象もその行に替わる
- アプリ全体でブラウザのコンテキストメニューを止める（doc-8）。例外は入力欄・編集可能領域と、選択中のテキストの上で、このときは伝播を止めてブラウザのメニューに任せる。例外の判定は、対象の確定と `ContextTrigger` より先に capture 段で行い、例外のときは対象も確定しない
- メニューキーと Shift+F10 では、フォーカス中の行を対象にし、その行の矩形を起点に開く
- 右クリックメニューの外を左クリックしたときは、メニューを閉じつつ、そのクリックを行にも届ける（Ark UI の既定）。フォーカスはクリックした行に残り、メニュー側からは戻さない

### ダイアログ

- ダイアログはネイティブ dialog から Ark UI の Dialog へ寄せる。次の既存の仕組みが要らなくなり、Esc とフォーカスがほかの層と1系統になる: inert を避けるためのポータル、`openModalDialogsAtom`、Tab 循環の補完、cancel の伝播止め、トーストの付け替え、backdrop クリックの判定
- 置き換えは最後の段階で行う。それまでのネイティブ dialog の中のメニューとポップオーバーは、ポータル先を dialog の中にする
- ネイティブ dialog の backdrop では、1クリックで内側の層と dialog が両方閉じないよう `useDialogModal` でガードする。dialog 自身への pointerdown を capture 段で受け、その時点で操作できる（`inert` でない）メニューまたはポップオーバーが dialog 内にあれば、続く click では dialog を閉じない。メニューでの動作は実ブラウザで確認済み。ポップオーバーのガードは単体テストと実ブラウザ（作品編集ダイアログのタグ追加ポップオーバーを開いて backdrop を押す。5回）で確認済みで、ポップオーバーだけ閉じ、dialog は残った。
- Ark UI の Dialog は top layer を使わない（`showModal()` も popover 属性も使わず、既定で `document.body` へポータルする。ソースで確認）。ライブラリは z-index を決めず、層の順番を CSS 変数で渡すだけなので、重なりの階層はアプリ側で決める。置き換えのときに design-system.md の階層表へ組み込み、`dialog[open]` に依存する判定（`useGlobalShortcuts`、`useWorkResultsDismiss`）を書き換える

### 置き換えの順番

1. ボタン起点のメニューとポップアップの見た目・振る舞いを、モックで相談する
2. 完了: メニューとポップオーバーを Ark UI に置き換え、`usePopoverEscape` を削除した。メニューとポップオーバーの共通処理は `layer/` に置く。
3. ツールチップ → セレクト、スライダー、タブ
4. コンボボックスとダイアログとトーストを、同じ統合ブランチでまとめて置き換える
5. DRAFT-53（作品の複数選択と右クリック）

コンボボックスとダイアログを別々に置き換えると、移行期間に Esc が一段にならない組み合わせができる。試作で次のことを検証した。

- Ark UI の Dialog の中に自作の `TagCombobox` を置くと、Ark UI が Esc を先に処理し、候補が開いていれば1回の Esc で候補とダイアログが同時に閉じた
- ネイティブ dialog の中に Ark UI の Combobox を置くと、入力欄にフォーカスがある限り、Esc で dialog が閉じなかった

コンボボックスとダイアログを置き換えるまでは、ネイティブ dialog の中に Ark UI のメニューとポップオーバーを置く。試作の S2（ネイティブ dialog の中の行メニュー）では、サブメニュー → メニュー → dialog の順に一段ずつ閉じた。

コンボボックスは `TagCombobox` が IME と Esc の規約を作り込んでいる。ダイアログの中の Esc の一段と、リストを閉じる Esc で入力が残ることは試作で確かめたので、置き換えのときは残りの規約（候補の確定、退出アニメーションなど）を確かめる。

## 帰結

- 右クリックメニューとボタン起点のメニューを、サブメニュー・チェック項目・先頭文字移動付きで同じ項目定義から作れる
- メニューとポップオーバーの Esc は Ark UI の層にまとめ、自作の Esc スタックと `@floating-ui/react` への直接依存は外した。ネイティブ dialog の補完は Dialog の置き換えまで残る。
- サブメニューを使い始めると、サブメニューの Esc はライブラリの既定に逆らう回避に依存する。Ark UI の更新でキーの扱いが変わると壊れうる（下の依存点を参照）。孫の階層のサブメニューは試していない
- 退出中も `data-state` が `open` のままなので、退出中かどうかは `useIsPresent()` で見る
- Ark UI の内部挙動に依存している点。更新のたびに実ブラウザで確かめる（手順は TASK-530 の実装メモ）
  - `restoreFocus: false` の CLOSE を `service.send` で送る（外へのフォーカス移動と `MenuLayerItem`）。メニューの open を制御しないのも、制御モードの閉じる遷移が無条件にトリガーへフォーカスを戻す（`CONTROLLED.CLOSE` の `focusTrigger`）ため
  - トリガーが `defaultPrevented` と `data-disabled` を見て開かない（無効と `interceptOpen`）
  - 出現の起点を、zag が positioner に出す `--transform-origin` に頼る
  - `useDialogModal` がダイアログの中のメニューの Tab を循環させず、メニューの Tab の処理に任せる
  - サブメニューの Esc の置き換え（使い始めたとき）。別のメニューが開くと閉じる途中のメニューのせいで後から開いた方も閉じる件（zag 1.47、1.49 で直っている）
- メニューを開いたままプログラムの `focus()`（⌘K での検索欄など）で外の要素へ移すと、Ark UI の閉じ方がトリガーへ奪い返す。共通のメニューフックは、外へのフォーカス移動を `onInteractOutside`（`defaultPrevented` は zag のツリー判定の結果）で受け、`restoreFocus: false` の CLOSE で閉じて移動先のフォーカスを保つ。`restoreFocus` を付けられるのは `service.send` だけなので、メニューの CLOSE の送信（外へのフォーカス移動と `MenuLayerItem`）にはこれを使う。スクロールで閉じるときは公開の `api.setOpen(false)` で、トリガーへ戻る
- ポップオーバーは軽い層なので、外側をクリックしたら内側のメニューごと閉じ、クリックされた要素の操作は通す。ネイティブ dialog の backdrop は操作要素ではないので、メニューだけを閉じて dialog は残す。ポップオーバーを開いている dialog でも、同じガードで dialog を残す。
- メニューの外のフォーカスできない領域をクリックすると、メニューは閉じてトリガーへ戻る。ボタン起点のメニューで、Esc・外側クリック（フォーカスできる要素とできない領域）を各10回、項目の実行を主要なメニューで測り、フォーカスの記録（focusin と activeElement の変化）で body を経由しなかった。ただしフォーカスできない領域のクリックでは、ブラウザの既定動作が mousedown で約10ms だけフォーカスを body へ移してから Ark UI がトリガーへ戻す。focusin は発生せず最終状態は正しいので、この例外は受け入れる。項目の実行でトリガー自体が消える場合（未登録の候補の除外・追加、作品の登録解除）も、body を経由しない
- メニューの位置は `strategy: "fixed"` にする。`hideWhenDetached` で隠すと Chrome がフォーカスを外して body に落ち、矢印も効かなくなるので使わない。代わりに、トリガーを含む領域がスクロールしたらメニューを閉じる（フォーカスはトリガーへ戻る）。配置の結果（reference hidden）は、Ark UI の positioning から取れない（zag の menu が `onComplete` を上書きする）
- 項目の実行でトリガーが消える・無効になるときは、状態を変える側が、操作の前に移し先を決め、状態を変えた直後に明示的にフォーカスを移す。他の機能の状態遷移を外から観測して後から動く補正（フレーム待ち、body に落ちたかの監視、inert のタイミング頼み）はしない。入れ替わる要素を自分で描く部品（スキャンの開始・中止のボタン）は、自分の描画の切り替わりでフォーカスを引き継いでよい。移すのは、フォーカスがどこにも無いか消える側の中にあるときだけで、ユーザーが他へ移したときは動かさない。処理中の操作要素は `disabled` 属性ではなく `aria-disabled` とハンドラ側のガード（`Button` の `softDisabled`、メニュー・ポップオーバーのトリガーはフックの `disabled`）で無効にし、フォーカスを落とさない。部品名と手順は、未登録候補の除外・追加（`UnregisteredTab`）、スキャンの開始・中止（`ScanSidebar`）、作品の登録解除（`WorkDetailPatchScope`・`WorkDetailPage`）のコードに任せる。
- メニュー内の Tab は Ark UI が抑え、メニューは開いたまま動かない（メニューに tabbable な要素が無いと preventDefault する）。ダイアログの中でも同じになるよう、`useDialogModal` の Tab 循環はメニューの中のキーを扱わない。WAI-ARIA の「閉じて次へ進める」にするには、キーの横取りとフォーカス移動の補正が要るので、Ark UI の挙動を受け入れた
- ラジオを持つメニュー（ソート、再生速度）は、キーボードで開いたときだけ現在値をハイライトする。マウスで開いたときは何もハイライトしない。日本語ラベルの先頭文字移動は、IME 中のキーが Process になるので対応しない
- セレクトの入れ子の Esc は確かめていない。セレクトを置き換えるときに確かめる
- IME 変換中の Esc・Enter を無視する動作は、CDP で合成した入力でしか確かめていない（メニュー、ポップオーバーの検索欄、ダイアログの中のコンボボックス）。メニューキーと Shift+F10 も、実キーでは `contextmenu` が発火せず、行の矩形から撃ち直して確かめた。どちらも実機では確かめていない
- バンドルは増える。試作途中（`00ce5b0c`）の計測でメインチャンクが gzip で +42.2 kB（試作コードを含む。Base UI は +49.3 kB）
- 移行で消えた `popoverEscape.test` の「背面のダイアログのメニューは前面のダイアログの Esc を奪わない」「ダイアログの外のメニューはダイアログ内の Esc を奪わない」は、Ark UI ではダイアログを開いた時点でフォーカスが外れてメニューが閉じ、前提が成り立たないので移していない
- メニューの open は制御しない。zag 1.47 は制御モードで親が open=false を返すと、閉じる遷移で無条件にトリガーへフォーカスを戻し（`CONTROLLED.CLOSE` の `focusTrigger`）、`restoreFocus: false` の CLOSE が効かない。外へ移したフォーカスが奪い返され、`MenuLayerItem` の「戻さずに閉じる」もタイミング頼みになる。開く操作を呼び出し側が止めたいときは、`useMotionMenu` の `interceptOpen`（閉じているときのポインター・Enter・Space・ArrowDown・ArrowUp で呼び、true を返すと開かない）を使う。未登録タブの▾が、項目選択を開いているときは項目選択を閉じるだけにするのに使っている
- Ark UI のメニュー項目は、テストで `fireEvent.click` を使っても実行されず、`userEvent.click` が要る
- Ark UI の Dialog では、body にフォーカスがあると再生中の Space がダイアログの背後に漏れた。`dialog[open]` に依存する判定を書き換えるときに直す
