# ADR-0036: DLsiteカバーを適用しなかった理由を応答で返し、候補一覧を登録状況から取り直す

- ステータス: 承認
- 日付: 2026-11-20
- 関連: [ADR-0028](0028-work-management-mutation-ownership.md)（必須更新の定義。候補の扱いを本ADRで置き換え）、[ADR-0033](0033-dlsite-fetch-before-register.md)（追加・適用でのカバーの扱いを本ADRで置き換え）、[ADR-0035](0035-dlsite-cover-name-from-placement.md)、backlog TASK-512

## 文脈

カバーの保存手順は、キャッシュに無い・画像として読めない・作品フォルダーをルート内に解決できないとき、カバーだけ外して成功としていた。利用者にもログにも何も残らず、選んだカバーが付かなかったことに気づく手段がなかった。

未登録の候補一覧は、サーバーが読むたびに作品の登録状況と突き合わせる形になった（TASK-512.1）。一方クライアントは、登録・除外した候補を `scanCandidateHiddenPathsAtom` で別に隠していた。真実の源がサーバーとクライアントで二重になり、候補から追加した作品の登録を解除しても、次のスキャンまで候補に戻らなかった。候補のクエリは明示的な取得でしか更新されないため、必須更新（ADR-0028）に候補を含めない限り、解除後に取り直す経路もなかった。

## 決定

### カバーを適用しなかった理由を返す

- 選んだカバーを適用しなかったとき、適用・Files登録・候補からの登録は成功のまま、応答の `coverSkipped` に理由を返す。理由は `not_cached`（キャッシュに無い）・`unreadable`（画像として読めない）・`outside_root`（作品フォルダーをルート内に解決できない）。
- カバーを選んでいないとき、DLsite側にカバーが無いときは `null`。フィールドは省略せず、必ず `null` か理由を持つ。
- 書き込みの失敗は従来どおり失敗（502）。
- `unreadable` と `outside_root` はサーバーの警告ログに理由と場所を残す。`not_cached` は通常の状態なのでログに出さない。
- クライアントは理由を出し分けず、既存の結果の通知に「カバーは適用できませんでした」を添える。利用者の次の行動が理由で変わらないため。
  - 作品詳細の適用: 成功の代わりに警告を1つ出す。
  - Files登録: 登録後に警告を出す。
  - 候補の追加: 件数に「うちK件はカバーを適用できませんでした。」を添える。全件成功でもこの一文があるときは、新規作品タブへ移りつつ警告を出す。

### 候補一覧は登録状況の派生として取り直す

- 候補一覧は登録状況の派生なので、登録の集合を無効化する操作（登録・解除・スキャン完了・作品の読み直し・ID再採番）の後に、サーバーから取り直す。取り直しの失敗は操作の成否に影響させない。
- クライアントは候補の非表示集合を持たない。楽観的な行の削除もしない。取り直しの応答を待ち、行が消えるまで操作中の表示を続ける。
- 除外・除外の取り消しも、応答後に取り直す。

## 帰結

- カバーが付かなかったことが、応答・ログ・通知で分かる。
- 候補から追加した作品の登録を解除すると、再スキャンなしで候補に戻る。スキャン前から登録済みだった作品のフォルダーは、直近のスキャンの候補に入っていないので、次のスキャンまで戻らない。
- 登録・解除のたびに候補の取得が1回増える。

## 既存ADRのうち置き換える箇所

- [ADR-0033](0033-dlsite-fetch-before-register.md)「新しい候補は『追加』を承認とする」の「キャッシュにカバーが無いときは、カバーだけ反映せず、ほかの項目は反映して追加を続ける」を、本ADRの「カバーを適用しなかった理由を返す」に置き換える。カバーだけ外して続行する点は同じで、理由を応答で返し通知に添える。作品詳細の適用も同じ。
- [ADR-0028](0028-work-management-mutation-ownership.md)「画面側に残すもの」の `scanCandidateHiddenPathsAtom` の項目を削る。必須更新の表の下の「scan 候補は必須更新に含めない。…画面側の非表示集合で揃える」の段落を、「登録の集合の無効化に、未登録の候補の取り直しを含める」に置き換える。
