# ADR-0037: スキャン結果の持ち主をサーバー層の1つの集約にし、直したRJコードをスキャン完了で消さない

- ステータス: 承認
- 日付: 2026-11-20
- 関連: [ADR-0033](0033-dlsite-fetch-before-register.md)（直したRJコードの寿命を本ADRで置き換え）、[ADR-0034](0034-scan-modal-restructure.md)（スキャン結果の寿命を本ADRで置き換え）、[ADR-0002](0002-mock-as-fixture-adapter.md)、[ADR-0039](0039-scan-modal-current-problems-and-explicit-states.md)（記録の項目から行方不明・データ不整合を外す）、backlog TASK-512

## 文脈

スキャン中に候補のRJコードを直しても、完了時に候補のセッションが丸ごと差し替わり、直した値が消えていた。直した値の持ち主が、完了のたびに作り直される入れ物の中にあったことが原因である。

同じ「直近のスキャンの結果」の片割れである記録（新規作品・更新済み・行方不明・データ不整合）は、別の流儀で持っていた。登録解除や再採番のたびに、ルートから記録へ手で「この作品を外す」と伝えていた。候補の規則（可視性・RJコードの上書き・登録の集約）も、real と fixture の両 adapter に別々に書かれ、片方だけ意味が変わる食い違いが起きていた。

## 決定

### 持ち主

- 候補プール・直したRJコード・スキャンの記録は、サーバー層の `ScanSession` が持つ。adapter は規則を持たず、素材だけを返す。素材は、rootの同一性、除外と登録済みの判定、DLsite状態と行方不明作品、候補フォルダー1件の登録である。
- adapter の `scan()` と `rebuildCatalogForRoot()` は、結果・候補プール・走査したrootの同一性を返す。`ScanSession` は、スキャン完了時にプールの差し替えと記録の置き換えを、await を挟まない1か所で行う。どちらか片方だけが古いまま公開されることはない。
- rootの変更を伴う再設定の開始時に、候補と直したRJコードを捨てる。adapter が rootの変更の有無を返し、設定を書く側の意図で判断する。同じ rootでの再設定は、記録だけを捨て、直したRJコードを残す。
- 候補のスキャンが完了したか（候補一覧の応答の `scanCompleted`）は、`ScanSession` の候補プールの有無で決まる（プールが無いのが未スキャン）。`scanCompleted` が false のとき候補は空で、完了して0件のときとは別の状態になる。記録の完了時刻（`finishedAt`）とは別の事実で、同じ rootでの再設定は記録の完了時刻を空にするが、プールは残るので候補はスキャン完了のまま出る。

### 直したRJコードの寿命

- 直したRJコードは、サーバープロセスの寿命で持つ。完了時に引き継ぐ・コピーする処理は持たない。
- root の変更を伴う再設定とサーバー再起動を除いて、スキャンをまたいで持つあいだに消えるのは次の2つだけ。
  - 候補から登録したとき。登録中にスキャンが完了しても消える。
  - 次のスキャン完了で、候補のプールから外れたとき。プールは走査で見つかった未登録フォルダーの集合で、作品情報ファイルのあるフォルダーは入らない。Files から登録したフォルダーの直しも、登録解除して候補に戻ったとき直した値が戻らないよう、この刈り込みで消える。
- 除外では消えない。除外は可逆で、プールにも残るため、解除すると直した値のまま戻る。
- サーバー再起動では消える。プール自体がメモリだけにあり、プールの無い直しは意味を持たないため。
- 前回のスキャン後に直して、追加しないまま再スキャンしても、フォルダーがプールに残っていれば直した値は残る。

### 記録は読むときに照合する

- 記録は、登録解除や再採番でルートから外さない。読むとき（`GET /api/scan/last`）に、catalogと照合して存在しない作品を落とす。`GET /api/works` の `scanRecord` 絞り込みは、作品をIDで引くので、存在しない作品は自然に落ちる。
- 項目ごとの照合条件は次のとおり。
  - 更新済み、データ不整合: 作品が存在すること。データ不整合で一覧から除かれた作品も、catalogには存在する。
  - 新たな行方不明: 作品が存在し、かつ行方不明のままであること。同じIDの作品が復元されて見つかるようになれば、もう行方不明ではない。
  - 新規作品: 作品が存在すること（作品一覧をIDで引く）。
- 同じIDの作品がcatalogに戻ると（孤立した作品情報ファイルの復元）、記録の項目に再び現れうる。同じ作品がそのスキャンで見つかったという事実は変わらないので、これを許容する。
- スキャン実行中の引き継ぎの履歴は、2つだけ残す。実行中に候補から登録した作品（`added`）はスキャン結果に入らず、読み直しで直ったデータ不整合（`integrityResolved`）は存在の照合では判別できない。どちらもcatalogとの照合からは導けない。

## 帰結

- スキャン中に直したRJコードが、完了後も候補に残る。
- 登録解除・再採番・一括解除のルートは、記録に何も伝えない。`replacedWorkId` と、記録のためだけに返していた `deletedWorkIds` は無くなる。
- 登録側のメタファイルを再採番すると、新IDの投影と旧IDの行の移動は、1回の公開（同じトランザクション）で行う。旧IDの行は、旧IDを宣言している残りのメタファイルのうち、読める先頭のものへ移る。ユーザー状態（ブックマーク・レジューム）は旧IDに紐づいたまま行と一緒に移り、新IDの行は空で始まる。次のスキャンが行う「移動」と同じ結果になる。残りのメタファイルが無い、または読めないときは、旧IDの行を次のスキャンと同じく行方不明にする。公開が成功したときは、同じフォルダーを指す行が2つ残ることはない。公開に失敗したときは、メタファイルは書き換え済みのままで、応答はエラーになる。失敗の形は2つある。投影が例外で失敗したときは、カタログはトランザクションごと元に戻り、競合の診断も残る。公開の前に対象のメタファイルが外部で書き換えられた（`source_changed`）ときは、変わった項目だけが公開から外れ、残りは公開される。たとえば残りのメタファイルが書き換えられると、新IDの行は公開され、旧IDの行は登録側を指したまま残る。どちらも、次のスキャンが再採番後の宣言に揃える。記録の旧IDの項目は、移った作品を指して残る。
- fixture はスキャン前の候補を持たない。real と同じく、先にスキャンしたあとで候補が出る。`dev:fixture:new-work` で未登録を見るには、先にスキャンする。

## 既存ADRのうち置き換える箇所

- [ADR-0033](0033-dlsite-fetch-before-register.md)「新しい候補は「追加」を承認とする」の「未登録の候補でRJコードを直した値は、サーバーのメモリにある候補一覧の中だけで持つ。寿命は候補一覧と同じく、次のスキャンかサーバー再起動まで（ADR-0034）。…追加しないまま次のスキャンをした場合は、フォルダー名から検出し直す。」のうち、寿命と「検出し直す」を、本ADRの「直したRJコードの寿命」に置き換える。追加すると作品情報ファイルに書かれる点は変わらない。
- [ADR-0034](0034-scan-modal-restructure.md)「スキャン結果の寿命はサーバーのメモリだけ」の1項目目のうち「未登録の候補一覧（直したRJコードを含む）…寿命は、次のスキャンかサーバー再起動までとする」を置き換える。候補プールと記録の寿命は次のスキャンかサーバー再起動まで。直したRJコードの寿命は、本ADRのとおり。記録は、読むときにcatalogと照合して消えた作品を落とす。
