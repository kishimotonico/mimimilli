# ADR-0033: DLsite情報は登録前に明示取得し、追加を承認とする

- ステータス: 承認
- 日付: 2026-11-19
- 関連: [ADR-0017](0017-meta-source-projection-and-work-identity.md)（meta正本と投影）、[ADR-0027](0027-dlsite-meta-state-type-separation.md)（DLsite状態の型）、[ADR-0028](0028-work-management-mutation-ownership.md)（変更後のキャッシュ更新。DLsite関連の一部を本ADRで置き換え）、[ADR-0029](0029-root-reconfiguration-workflow.md)（root再設定。新規作品のDLsite取得への受け渡しを本ADRで置き換え）、[ADR-0030](0030-job-progress-sse-current-state.md)（ジョブ進捗SSE。DLsiteの契約を本ADRで置き換え）、[ADR-0034](0034-scan-modal-restructure.md)（スキャン画面の再構成）、backlog TASK-451（2026-09-22方針）・TASK-511（実装）、DRAFT-74（本ADRで解消）

## 文脈

2026-11-08のドッグフーディングで、DLsite連携まわりに次の問題が出た。

- スキャンモーダルで候補を登録すると「取得待ち」のまま変わらず、進んでいる気配がない。取得はスキャン完了時（`server/src/app.ts:76`）、候補の登録時（`app.ts:94`）、作品の登録時（`app.ts:98`、`POST /works/projection`・`POST /works`・`POST /works/identity-conflicts/reassign`）に暗黙に積まれ、登録経由は1件ごとの単発ジョブになる。クライアントはこれらのジョブIDを受け取らないため、進捗も完了も画面に出ない。
- 取得が終わっても、カバーとタイトルを反映する出口がスキャン画面にない。取得ジョブはHTMLをキャッシュへ保存するだけで（`server/src/adapters/real/dlsiteBulk.ts`）、`DlsiteStatus` には「取得済み・未適用」を表す値がない。
- ベルの「まとめて取得」は対象を指定しない。そのため、RJコードがあって未適用（`none`・`not_found`・`error`）の全作品が対象になり（`selectDlsiteBulkTargets`）、TTLの切れた既存作品の数だけ実HTTPを出す。
- 完了トーストの「未設定項目を適用」は、全作品の差分を1回のリクエストで同期計算する（`POST /dlsite/apply-missing/preview`）。「適用対象の差分を取得できませんでした」は、Bunの `idleTimeout` 90秒（`server/src/serve.ts:5`）で切れているものと推測している（未検証）。
- 適用時に初めてカバーを取りに行くため（`server/src/adapters/real/dlsiteApply.ts:80-89`）、適用にもHTTPが混ざる。差分計算はクライアント（`client/src/entities/work/dlsitePreview.ts:61`、タイトルを置き換える）とshared（`shared/src/dlsite.ts:354` `computeMissingDiff`、未設定項目だけでタイトルなし）の2系統に分かれている。適用のbodyはクライアントが送った `info` を信用している。
- 「ライブラリに追加 → あとでDLsite連携」という順序そのものが分かりにくい。追加直後は「フォルダー名のまま・未連携」の作品が残る。一方、Filesの作品登録ダイアログは「取得してから登録」の順になっていて、入口によって順序が逆になっている。

TASK-451で2026-09-22に採用した方針（暗黙取得をしない、登録時の明示選択、差分確認後の明示適用と一括承認、DLsite専用管理ビュー）は実装されておらず、旧方式（自動取得・未設定項目の自動補完）と混ざったまま残っている。

## 決定

### 取得は「未登録」の候補に対して、ボタンを押したときだけ行う

- スキャン、候補の登録、作品の登録のいずれも、DLsite取得を暗黙に積まない。root再設定後の構築でも積まない。
- まとめての取得の起点は、スキャン画面の「未登録」タブにある「DLsiteから取得」ボタンだけとする。対象は、選択した候補のうちRJコードがあって未取得のものだけにする。対象を指定しない全件取得は置かない。
- 候補はまだ作品ではなくWork IDを持たないため、取得ジョブはRJコード（product code）を単位とする。結果はproduct codeをキーとする既存のDLsiteキャッシュに残る。
- 取得のとき、カバー画像も先取りしてキャッシュに置く。取得済みの候補のカバーをプレビュー表示するため、キャッシュ済みのカバーを配信する経路を用意する。DLsiteのURLをブラウザから直接読まない。
- 取得はサーバーのジョブで進め、ブラウザやモーダルを閉じても続く。DLsiteへのアクセスは既存のスケジューラ（1秒に1件）に従う。
- 単発の同期取得（`POST /dlsite/fetch-by-code`、`POST /dlsite/:id/fetch`）は、ユーザーが1件の結果を待つ操作なので同期のまま残す。ここでもカバーをその場で先取りしてキャッシュに置く。

### 取得ジョブ

- 取得ジョブは同時に1本だけ動かす。実行中に別の取得（再試行、RJコードを直したあとの取得、別の選択での取得）を受けたら、新しいジョブは作らず、実行中のジョブのキューへ合流させる。
- 起点（まとめて／単発）は、ジョブではなくproduct codeごとに持つ。合流しても、コードごとの起点は変わらない。
- ツールバーの進捗枠（「取得中 n / N」）と上のバーの入口の輪は、起点がまとめてのコードだけを数える。単発の取得は、その候補の行の状態だけで見せる。
- 中止は、起点がまとめてで待機中のコードをキューから取り除く。単発のコードは止めない。
- 再試行とRJコードを直したあとの取得は、失敗の記録（該当なし・失敗）を無視して取り直す（force）。
- サーバー再起動やアプリ終了で取得が途中になった場合、再開はしない。取得できた分はキャッシュに残り、途中だった候補は未取得に戻る。もう一度取得すれば、キャッシュ済みの分は通信せずに済む。
- 取得したまま追加しなかった候補の情報は、既存のキャッシュの仕組みにそのまま任せる。このための専用の保持・掃除の仕組みは作らない。

### 候補の状態はキャッシュから導く

- 未登録の候補の状態（未取得・取得済み・該当なし・失敗）は、そのRJコードについて既存の `DlsiteCache.resolve` が返す結果から導く。取得中はジョブの状態から出す。キャッシュの意味は変えず、TTLを無視してsnapshotを読む経路も足さない。
- `resolve` は、有効な失敗の記録があればそれを返し、なければTTL内のsnapshotを返し、どちらもなければmissを返す（失敗と解析失敗の優先順位も既存どおり）。TTL（成功30日、該当なし3日、通信エラー・解析失敗1時間、`shared/src/dlsite.ts` の `DEFAULT_DLSITE_CACHE_TTLS_MS`）を過ぎた記録とsnapshotはmissになり、その候補は未取得に戻る。 `resolve` が `html` を返したときは、`outcome` が `ok` なら取得済み、`parse_error`（解析失敗のsnapshot）なら失敗とする。解析失敗のsnapshotを取得済みにはしない。
- そのため、まとめての取得の対象「未取得」には、TTLの切れた候補も含まれる。候補と、同じRJコードの既存作品の表示（`not_found`・`error` の投影）も一致する。
- 期限切れの行は、DLsiteキャッシュCLIの期限切れ掃除（`DlsiteCache.cleanupExpired`）で物理的に消える。カバー画像には期限も自動削除もない。

### 新しい候補は「追加」を承認とする

- 未登録の候補を追加する操作を、DLsite情報を反映する承認とみなす。新しい候補には、上書きされて困る既存の値がないためである。候補ごとの差分確認は置かない。
- 反映する項目（タイトル・カバー・タグ・URL）は既定ですべて反映する。項目を絞りたいときだけ、追加ボタンの詳細操作（▾）で選ぶ。
- 追加時には、そのRJコードについて `resolve` がTTL内で `outcome` が `ok` のsnapshotを返したときだけ、その内容を使う。TTLの切れた候補、キャッシュに無い候補、取得中の候補、該当なし・失敗の候補、RJコードのない候補は、DLsite情報なし（フォルダー名のまま）で追加される。取得中の候補は追加の対象から自動で外す。
- 追加と適用の処理では、DLsiteへHTTPを出さない。キャッシュにカバーが無いときは、カバーだけ反映せず、ほかの項目は反映して追加を続ける。
- 取得が終わる前に追加した作品へ、あとから自動で反映する仕組み（予約）は作らない。追加したあとに、届いた情報で作品が黙って書き換わることはない。
- 追加の取り消し（undo）は作らない。追加後の修正は、新規作品タブでのタイトル編集、作品詳細、登録解除で行う。
- 未登録の候補でRJコードを直した値は、サーバーのメモリにある候補一覧の中だけで持つ。寿命は候補一覧と同じく、次のスキャンかサーバー再起動まで（[ADR-0034](0034-scan-modal-restructure.md)）。追加すると作品情報ファイル（`mimimilli.json`）に書かれる。追加しないまま次のスキャンをした場合は、フォルダー名から検出し直す。

### 追加と適用の契約

DLsite由来の情報（DLsiteのタイトル・タグ・URL・カバー）は、サーバーがキャッシュから読む。クライアントから取得結果（`info`）を受け取らない。入口ごとの契約は次のとおり。

- 未登録の候補の追加: 候補のパスとRJコード、反映する項目のフラグ（タイトル・カバー・タグ・URLの真偽値）だけを受け取る。タイトルを反映するときは、DLsiteのタイトルに置き換える。
- Filesの作品登録ダイアログ: 編集フォームのまま残す。bodyは、RJコード、タイトルとタグ（ユーザーの入力値）、カバーとURLを反映するかのフラグ（`applyCover`・`applyUrl`）とする。DLsite由来のカバーとURLは、サーバーがキャッシュから読む。`dlsite.appliedTags` は、サーバーが「キャッシュ上のDLsiteのタグ」と「ユーザーが入力したタグ」の共通部分として決める。
- 作品詳細の適用: タグ単位の選択（配列）を受け取る形を維持する。DLsite情報はサーバーがキャッシュから読み、作品が変わっていないこと（`sourceRevision`）を確かめてから書き込む。
- 大量の追加（100〜1000件程度）は、クライアントが分割して送る。1リクエストの件数の上限は、リクエストのschemaに持たせる。

### 既存の作品は作品詳細から、差分を確認して反映する

- すでに作品になっているものへのDLsite情報の反映は、作品詳細のDLsite欄で、差分を確認してから行う。この経路は残す。
- 作品詳細の差分計算は1つの実装にまとめ、sharedに置く。
- 将来、ライブラリで複数の作品を選び、右クリックから選択的に再スキャン・取得する機能を検討している。それまでは、既存作品をまとめて取得・反映する入口は置かない。

### 廃止するもの

- ベル（スキャン関連の上のバーの入口は1つにまとめる。[ADR-0034](0034-scan-modal-restructure.md)）と、そのメニュー（要対応・DLsite未連携の「まとめて取得」・直近のスキャン結果）。
- 対象を指定しない一括取得（`POST /dlsite/bulk` の現行の契約）と、設定画面のDLsite節（まとめて取得・まとめて適用）。
- `POST /dlsite/apply-missing/preview` と `POST /dlsite/apply-missing`、未設定項目をまとめて適用するダイアログとその実行。
- DLsite通知モーダル3つ（RJコード未検出・取得失敗・パース失敗）と、その件数・一覧を返す `GET /dlsite/notifications`。
- 一括取得の完了・中断トースト。
- TASK-451で採用していたDLsite専用管理ビュー。作らない。

### 取得の終端で無効化するもの

取得はキャッシュに書くだけで、作品の正本（`mimimilli.json`）は変えない。ただし作品の `not_found`・`error` はキャッシュからの投影なので（[ADR-0027](0027-dlsite-meta-state-type-separation.md)）、同じRJコードの既存作品があると、その表示は取得で変わる。取得の終端では、取得したRJコードを持つ候補の表示と、同じRJコードを持つ既存作品の表示（詳細・一覧）を無効化する。作品が変わる追加のときの更新は、通常の登録と同じく [ADR-0028](0028-work-management-mutation-ownership.md) に従う。

### 既存ADRのうち置き換える箇所

- [ADR-0030](0030-job-progress-sse-current-state.md): 「DLsiteの契約」節と「DLsite一括取得の終端でのキャッシュ更新」節を置き換える。取得ジョブは、対象のproduct codeの集合（またはforce付きの単発）を受け取り、開始時にジョブIDを返す。中止は、起点がまとめてで待機中のコードを取り除く操作とする。進捗の配信と、再接続のときに確定に使うGETは、ジョブIDと、product codeごとの起点と状態（取得中・取得済み・該当なし・失敗）を返す。DLsiteの進捗SSEにも、scanと同じ15秒間隔のheartbeatを送る（今は送っていないので、無音が90秒続くと `idleTimeout` で切れる）。「進捗＝現在状態」「完了を失わない規則」「古い接続の上書き防止」の原則は、そのままDLsiteにも適用する。また、「scanの完了結果の中身」節が現在の状態の取得経路として挙げる `GET /api/dlsite/notifications` は廃止する。
- [ADR-0028](0028-work-management-mutation-ownership.md): 必須更新の表のうち、「DLsite 未設定項目の一括適用」と「DLsite 一括取得の完了」の行は、廃止と前節の無効化で置き換える。通知キー（`["dlsiteNotifications"]`）は、通知の廃止とともになくなる。「DLsite の無効化経路」節にある `DlsiteBulkRuntime` と `dlsiteBulkStore` は、新しい取得ジョブの追跡に置き換える。scan候補（`["scan", "candidates"]`）は、取得の終端で無効化する対象に加える。
- [ADR-0029](0029-root-reconfiguration-workflow.md): 再設定の開始時に実行中のDLsiteジョブを取り消して待機キューを捨てる手順は維持する。ジョブが1本になり、合流したコードはそのジョブ内のキューに入るので、「待機キューを捨てる」は「ジョブ内のキューを、起点を問わずすべて捨てる」と読み替える。手順6の「新規作品はスキャン完了時と同じくDLsite取得（`new`）へ渡す」は廃止する。

### 2026-09-22の方針（TASK-451）から変えたところ

- 新しく追加する作品は、追加の操作を承認とみなす。差分を確認してから適用するのは既存の作品だけにする。
- DLsite専用管理ビューは作らない。
- 取得の起点を「登録時の選択」から「未登録タブのボタン」に変える。

暗黙に取得しないこと、未設定項目の自動補完と外部情報への自動追随をしないこと、作品詳細の単体取得・差分確認・適用を残すことは、9/22の方針のまま変えない。

DRAFT-74の6論点は次のとおり解消した。

1. 登録時取得選択の初期値と記憶: 登録時の選択は置かない。取得は未登録タブのボタンで行い、反映項目は既定ですべて反映する。
2. 管理ビューの入口と配置: 管理ビューは作らない。
3. 適用方式: 新しい候補は追加が承認。既存作品は作品詳細の差分確認。未設定項目の自動補完と自動追随は不採用のまま。
4. サーバー再起動後: 再開しない。取得済みはキャッシュに残る。予約がないため、自動で再送する適用操作もない。
5. 直近結果の保持上限: 取得結果は既存のDLsiteキャッシュの寿命に従う。ジョブ結果の履歴は持たない。
6. 一括承認の粒度: 未登録タブで選んだ候補を追加する操作が承認であり、項目は追加ボタンの詳細操作で選ぶ。

## 帰結

- スキャンしただけではDLsiteへのアクセスは発生しない。数千件のスキャンでも、ボタンを押すまで外部アクセスはゼロになる。
- 追加する前に、DLsiteのタイトルとカバーで追加後の姿を確かめられる。RJコードの誤検出にも追加前に気づける。
- 「追加したのにDLsite情報が反映されない」状態がなくなる。追加後に黙って作品が書き換わることもない。
- 大量の候補は、取得に時間がかかる（1件あたり約2秒で、1000件なら30分を超える）。待てない場合はDLsite情報なしで追加し、あとで作品詳細から反映する。複数作品をまとめて反映する手段は、将来のライブラリの選択操作まで用意しない。
- ベル、通知モーダル、まとめて適用、設定のDLsite節がなくなり、DLsite関連の画面はスキャン画面と作品詳細に集約される。既存作品のRJコード未検出や取得失敗は、作品詳細の警告で知る。
- 取得結果がproduct code単位のキャッシュなので、同じRJコードを持つ別フォルダーの候補は同じ取得結果を共有する。
- 候補の状態は既存のキャッシュの意味から導くため、取得から30日を過ぎた候補（失敗は1時間〜3日）は未取得に戻る。追加する前にもう一度取得すれば、DLsite情報つきで追加できる。
- docs/dlsite.md と docs/requirements-v4.md の該当箇所は、実装と同時に書き換える。
