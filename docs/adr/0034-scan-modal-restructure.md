# ADR-0034: スキャン画面は今回のスキャンで見つかったものだけを扱う

- ステータス: 廃止（[ADR-0039](0039-scan-modal-current-problems-and-explicit-states.md)により置換）
- 日付: 2026-11-19
- 関連: [ADR-0017](0017-meta-source-projection-and-work-identity.md)（meta正本と投影）、[ADR-0028](0028-work-management-mutation-ownership.md)、[ADR-0029](0029-root-reconfiguration-workflow.md)（root再設定）、[ADR-0030](0030-job-progress-sse-current-state.md)（scanの完了結果の中身を本ADRで置き換え）、[ADR-0033](0033-dlsite-fetch-before-register.md)（DLsite取得と追加）、backlog TASK-511（実装）・DRAFT-70・DRAFT-72・DRAFT-77

## 文脈

スキャン・DLsite関連の表示は、スキャンモーダル、ベル、通知モーダル3つ、まとめて適用ダイアログ、設定のDLsite節、トーストに分かれていた。同じ件数が3〜4か所に重複して出ていた。

スキャン結果（`ScanResult`、`shared/src/scan.ts:63`）は `insertedWorkIds`・`updatedWorkIds` と件数しか持たない。

- `updatedWorkIds` には、移動、作品情報ファイルの変更、音声やカバーの差し替え、エラーからの復帰、「すべて読み直す」で読み直しただけの作品が区別なく入る（`server/src/adapters/real/scanRegister.ts:48-51`）。
- `insertedWorkIds` は「catalogに無かった」という意味でしかない（`scanRegister.ts:422`）。初回セットアップやルート変更では全作品が新規になる。
- スキャン結果はサーバーのメモリにしか無い（`server/src/scanJobManager.ts:46`）。候補から追加した作品のIDはモーダルの `useState` に溜めているだけで（`client/src/features/scan/ui/ScanModal.tsx:50`）、閉じると消える。表示は200件で切れる（`client/src/features/scan/ui/scanModal/scanResultWorkIds.ts:14`）。
- 「要対応」は、DLsite系の件数とスキャンの問題（ID重複・読み取り失敗）を同じ表に並べていて、何をすればよいかが分からない。`unreadablePaths` は画面に出ていない。
- 「再スキャン」と「すべて読み直す」が並んでいて、違いが画面から読み取れない。

ユーザーの意図は、スキャン画面ではライブラリ全体を管理せず、今回のスキャンで新しく見つかったもの、移動したもの、作品情報ファイルが変わったものに集中することである。既存作品の選択的な操作は、将来のライブラリの選択＋右クリックで扱う。

## 決定

### タブは4つ

並びは「未登録 / 新規作品 / 要対応 / 更新済み」とする。左の縦タブ（既存の `ScanSidebar`）を使う。

| タブ     | 入るもの                                                                                             | ユーザーがすること                                                                                               | そのあと                 |
| -------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------ |
| 未登録   | まだ作品になっていないフォルダー（候補）                                                             | DLsite情報を取得し、中身を見て追加する（[ADR-0033](0033-dlsite-fetch-before-register.md)）。不要な候補は除外する | 追加すると新規作品に移る |
| 新規作品 | 今回作品になったもの（候補から追加した作品と、作品情報ファイルがあってスキャンで自動登録された作品） | 基本なし。その場でタイトルを直せる                                                                               | 次のスキャンで入れ替わる |
| 要対応   | スキャンが片づけられなかった問題                                                                     | 推奨アクションを行う                                                                                             | 直ると消える             |
| 更新済み | 前からある作品で、変化を自動で取り込んだもの                                                         | なし。見るだけ                                                                                                   | 次のスキャンで入れ替わる |

- 要対応と更新済みは重ならない。更新済みはスキャンが自動で取り込んだものの記録、要対応は取り込めなかったものである。要対応を片づけても、更新済みに移ることはない。
- 一覧には、行ごとの文字の操作ボタンを置かない。パスを押すとFilesで開き、作品タイトルを押すと作品詳細ページを開く（スキャンモーダルは閉じる）。例外は、未登録の行の「修正」「再試行」と、要対応の作品内で完結する操作（後述）である。
- 未登録の「除外」は残す。行ごとのボタンではなく、選択した候補に対するツールバーの操作にする。既存の除外のAPIと、設定の除外フォルダー画面はそのまま使う。
- UIに説明文を置かない。件数は、操作が要るタブ（未登録・要対応）のサイドバーにだけ出し、開いているタブには出さない。現行サイドバーの集計行（更新なし・ライブラリ全体）は削除する。

### スキャン結果の寿命はサーバーのメモリだけ

- 未登録の候補一覧（直したRJコードを含む）、新規作品と更新済みの記録、要対応のうちスキャンの実行ごとの項目（新たな行方不明・アクセス不可・データ不整合）は、すべてサーバーのメモリに持つ。寿命は、次のスキャンかサーバー再起動までとする。再起動したあとは、次のスキャンまで空になる。
- モーダルを閉じても消えない（サーバーが持つため）。件数で切らない。
- スキャンの実行中に候補から追加した作品は、そのスキャンが完了したあとの新規作品の記録にも残す。
- DLsiteの取得結果はキャッシュにあるので、再起動のあとにもう一度スキャンすれば、TTL内の候補は取得済みとして見える。
- ID重複と読み取り失敗は、今までどおりcatalog DBの診断投影（`GET /api/scan/diagnostics`）から読む。これらは再起動をまたいで残り、スキャン完了時に全置換される。

### スキャン結果は作品ごとに変化の種類を返す

- サーバーは、既存作品ごとに変化の種類を返す。種類は「移動」「作品情報」（作品情報ファイルの変更）「ファイル構成」（音声・カバー等の増減や差し替え）の3つとする。移動は旧パスを、ファイル構成は音声の増減数を持つ。1つの作品が複数の種類を持ちうる。
- 実際に変化した作品だけを更新済みに出す。エラーからの復帰や、「すべて読み直す」で読み直しただけの作品は入れない。
- スキャンを始めた時点でcatalogに作品が1件もない場合、そのスキャンの新規作品の記録は空にする。初回セットアップでも、root再設定（[ADR-0029](0029-root-reconfiguration-workflow.md)）やcatalogの再構築のあとでも、この規則で同じ扱いになる。
- 更新済みは、反映の前に承認を求めない。作品情報ファイルとフォルダーが正本で（[ADR-0017](0017-meta-source-projection-and-work-identity.md)）、スキャンした時点で反映済みだからである。一覧は「作品 / 変更内容」の2列とし、変更内容は変化1つにつき1行で短く書く（例: 「移動 旧パス → 新パス」「作品情報ファイルを更新」「音声ファイル +3」）。値の差分は出さない。種類ごとに絞り込める。フォルダー単位の移動をまとめて表示するような特別扱いはしない。

### 要対応は5種類

| 種類         | 起きていること                                                                                                         | 推奨アクション                                                      |
| ------------ | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| ID重複       | 同じ作品IDの作品情報ファイルが複数ある                                                                                 | どちらかを消すか、Filesで別の作品として取り込む（各パスへのリンク） |
| 読み取り失敗 | 作品情報ファイルが壊れている・形式が違う。行番号と原因まで出す                                                         | ファイルを直す（パスへのリンク）                                    |
| アクセス不可 | フォルダーを開く権限がない（`unreadablePaths`）                                                                        | アクセス権を確認（パスへのリンク）                                  |
| データ不整合 | catalog DBの値が壊れていて、その作品を表示から外している（`dataIntegrityWarning`）。対象には作品IDを出す（リンクなし） | 「この作品を読み直す」ボタン                                        |
| 行方不明     | 今回のスキャンで新しくフォルダーが見つからなくなった作品                                                               | 「登録を解除」ボタン                                                |

- 「起きていること」は、作品情報ファイルの中身まで踏み込んで具体的に出す。このアプリは物理ファイルと作品情報ファイルの管理をユーザーが担い、アプリはそれを支える立場だからである。読み取り失敗の行番号と原因を出せるよう、サーバーが返すメッセージを改める。
- データ不整合は、全作品を読み直さずに、その作品だけを作品情報ファイルから読み直して直す。作品単位で読み直す入口を用意する。catalogは作品情報ファイルの投影だからである。
- 行方不明は、今回のスキャンで新しく行方不明になった作品だけを出す。以前から行方不明の作品は、ライブラリのエラー表示（既存の一括登録解除）で扱う。登録解除は既存の `DELETE /works/:id` を使う。
- 要対応の並びは、直すもの（あなたの番の色）を先、行方不明を後にする。サイドバーの件数は直すものだけを数える。
- DLsite関連（RJコード未検出・取得失敗・パース失敗）は要対応に入れない。候補のものは未登録タブの行の状態で扱い、既存作品のものは作品詳細で扱う。
- 用語は「行方不明」にそろえる。ライブラリの作品の状態ラベル「ファイル欠損」も「行方不明」に変える。

### 未登録タブの候補の状態

- 「DLsite」列の状態は、空欄（未取得）、取得中、取得済み、該当なし、失敗の5つとする。該当なしはDLsiteにその作品が無い（コードの誤りを疑い、行の「修正」でRJコードを直す）。失敗は通信エラー・タイムアウト・解析失敗で、行の「再試行」で取り直す。RJコードがない候補はRJコード欄を「—」にする。
- 色は4区分とする。完了（取得済み）、作業中（取得中、くすんだ色）、あなたの番（該当なし・失敗、エラーの色）、対象外（色なし）。状態の詳細はアイコンと文字で区別する。
- 見つからなくなった作品と同じRJコードの候補は、その行で知らせる。引き継ぐかどうかはユーザーが明示的に選ぶもので、自動では引き継がない。引き継ぐ操作そのものは backlog DRAFT-77 で契約を決めてから作る。
- 「RJコード」という呼び方は今回は変えない（VJコードも受け付けている）。別サイトの作品コードを扱うときに、データの持ち方と合わせて決め直す。

### 入口とスキャン操作

- 上のバーのスキャン関連の入口は1つにする。件数は出さない。スキャン中と、起点がまとめての取得が残っているあいだは進捗の輪を出す（[ADR-0033](0033-dlsite-fetch-before-register.md)）。前回開いてから新しい候補や問題が出たときだけ点を付け、開けば消える。「前回開いたとき」はクライアント（ブラウザ）に記憶する。ベルは廃止する（[ADR-0033](0033-dlsite-fetch-before-register.md)）。
- 件数つきのスキャン完了トーストは廃止し、入口の点で知らせる。スキャン自体が失敗したときのトーストは残す。
- サイドバー下に「最終スキャン」と年入りの日時を出す。主操作は「スキャン」1つで、詳細操作（▾）に「すべての作品を読み直す」を置く。スキャン中は「スキャンを中止」に入れ替わる。

### 既存ADRのうち置き換える箇所

- [ADR-0030](0030-job-progress-sse-current-state.md): 「scanの完了結果の中身」節と、「残す要素」の完了結果を置き換える。新規作品・更新済みの記録と、要対応の実行単位の項目は、候補の追加や登録解除で変わる現在の状態なので、ジョブの完了結果には載せない。`GET /api/scan/last` が現在の記録を返し、未スキャンのときも空の記録を200で返す。`GET /api/scan/:id` とSSEの `state` は結果を持たず、SSEの `completed` は完了時刻だけを運ぶ。クライアントは終端を `GET /api/scan/:id` で確定したあと、記録を取り直す。新規作品と更新済みの作品本体は、`GET /api/works` の絞り込みで件数の上限なく取る。
- [ADR-0028](0028-work-management-mutation-ownership.md): 必須更新のうち、登録・登録解除・スキャン完了の集合に、スキャンの記録（`["scan", "last"]`）を加える。

## 帰結

- スキャン画面に入るのは今回のスキャンで見つかったものだけになる。初回セットアップやルート変更で、新規作品タブが全作品で埋まることもなくなる。
- 更新済みには実際に変化した作品だけが出て、変化の種類と旧パスが分かる。このためにアダプタが返すスキャン結果（`ScanResult`）を拡張し、画面はサーバーの記録（`GET /api/scan/last`）から読む。
- 新規作品と更新済みの記録は、モーダルを閉じても見返せる。サーバーを再起動すると、次のスキャンまで空になる。永続化の保存先は持たない。
- 要対応から、何をすればよいかが読み取れるようになる。データ不整合と行方不明は、その場で片づけられる。
- 以前から行方不明の作品はスキャン画面に出ないので、気づく場所はライブラリのエラー表示になる。
