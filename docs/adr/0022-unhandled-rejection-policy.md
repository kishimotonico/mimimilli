# ADR-0022: unhandledRejectionではプロセスを終了せずログのみで継続する

- ステータス: 承認
- 日付: 2026-08-18
- 関連: [ADR-0011](0011-logging-logtape-jsonl.md)、[ADR-0007](0007-bun-distribution-runtime.md)、TASK-349

## 文脈

2026-08-17のWindowsでのドッグフーディング中、`try`/`catch` により捕捉済みのはずの fs ENOENT（`thumbnailCache.ts` の `statSizeOrNull` 内）が `unhandledRejection` として観測され、`index.ts` の `unhandledRejection` → `shutdown(1)` によりサーバープロセスが終了した。

高負荷再現テスト3種と精読でコード構造の欠陥は反証済みで、Bun 1.3.14（Windows）のPromise rejection追跡の誤検出が最有力仮説（未確定）。2026-08-18時点で 1.3.14 が latest stable、リリースノートに該当修正はなく、更新による回避先は存在しない。

上流issueの実在確認結果:

- [oven-sh/bun#37474](https://github.com/oven-sh/bun/issues/37474) 実在・Open。`Bun.write` / `server.fetch` / `Bun.resolve` の早期rejectionが rejection tracker に登録されず**報告されない**側の不具合。今回の症状（捕捉済みのものが報告される）とは逆方向だが、Bun内部promiseのrejection追跡が現在も変更途上であることを示す
- [oven-sh/bun#13456](https://github.com/oven-sh/bun/issues/13456) 実在・Closed。macOS・Bun 1.1.25 で `fs.readFile` のrejectionが `.catch()` を素通りする報告。症状が異なり今回の直接の根拠にはならない

今回の症状に一致する上流issueは確認できなかった。つまり本システムは、**ランタイム側の誤検出を排除できない前提で終了ポリシーを決める**必要がある。

現行ポリシーは Node.js の既定（`--unhandled-rejections=throw`）に倣った即時終了だが、本システムはユーザーのローカル環境で単独プロセスとして動き、プロセスマネージャによる自動再起動が無い。1発の誤検出がサーバー全体を落とし、ユーザーは再起動するまで一切操作できない。

## 決定

`unhandledRejection` ではプロセスを終了せず、構造化ログを残して継続する。`uncaughtException` は従来どおり `shutdown(1)` を維持する。

- **終了しない理由の非対称性**: `uncaughtException` は同期実行フローが途中で破綻した状態で、以後のプロセス状態の健全性を仮定できない。対して `unhandledRejection` は「rejectionにハンドラが付かなかった」という観測であり、Bunでは実際にはハンドラが存在するケース（今回）が起こりうる。プロセス状態の破綻を意味しない
- **ログレベルは `error`**。放置してよい事象ではないため、ログから消さない
- **ログ洪水対策**: rejectionを `errorKind` / `code` / `message` からなるシグネチャで集約する。同一シグネチャの1回目・10回目・100回目…（10のべき乗）でのみ出力し、常に累積 `occurrences` を添える。ループでrejectionが発生してもログとディスクを埋め尽くさない
- **シグネチャ保持数の上限**: `message` にはパス等の可変値が入るため、保持するシグネチャは256件を上限とする。上限到達後の新規シグネチャは `errorKind` / `code` のみのオーバーフローシグネチャへ集約し、ログ自体は失わない。カウンタはプロセス内メモリのみで、TTLによる期限切れは設けない
- **診断情報**: reasonが非Error・falsy でも型と内容が判別できること、fsエラーの `code` / `errno` / `syscall` / `path` が出ることまでを `formatError` の責務とする。循環参照・Proxy等への網羅的な防御はしない
- **起動途中の確実な終了**: `uncaughtException` 経路が起動途中でも exit code 1 に到達するようにする。`shutdown` 内で `app`（`const`）をTDZ参照していた穴を解消し、クリーンアップが失敗しても `finally` で `process.exit` に到達させる
- 整形処理とprocessイベント登録は副作用のない関数へ切り出し、テスト可能にする

| 代替案                       | 却下理由                                                                                                                               |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 現状維持（即 `shutdown(1)`） | ランタイム誤検出を排除できない以上、自動再起動の無い環境ではユーザーがサーバーを失う。今回観測された不具合そのもの                     |
| Windows限定で継続            | プラットフォーム分岐は根拠が「今回Windowsで観測されたから」でしかない。誤検出がWindows固有である証拠は無く、分岐は将来の判断を誤らせる |
| 短時間に反復したら終了       | 閾値に根拠を置けない。誤検出が高頻度で起きた場合に、健全なプロセスを閾値だけの理由で落とす。落とした先に自動再起動が無いのは同じ       |

## 帰結

- 本物のプログラム欠陥に由来する `unhandledRejection` も、プロセスを落とさず継続する。検知はログ経由になり、ユーザーが即座に異常に気づく手段は失われる。トレードオフとして受け入れる（開発時はログを見る運用）
- Bunのrejection追跡が将来修正されても、この決定は変えない。終了しない根拠はランタイムの不具合ではなく「自動再起動の無い単独プロセス」という配布形態にあるため
- ログ集約はプロセス内メモリのカウンタで、再起動でリセットされる。永続化はしない
