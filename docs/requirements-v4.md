# ローカル音声作品管理・再生アプリ 要件定義

> **注記:** 本書の要件（機能・UX）が正。技術スタックの記述は 2026-07-03 に現行実装（TypeScript / Hono、[ADR-0001](adr/0001-typescript-api-server.md)）へ更新済み。アーキテクチャの現行は [ARCHITECTURE.md](ARCHITECTURE.md)、開発の現状は [HANDOFF.md](HANDOFF.md) を参照。

## 1. 概要

### 1.1 背景

DLsiteやDMMのWebプレイヤーが使いにくく、横断的な検索ができない。ローカルに保存した音声作品を快適に管理・再生するアプリが必要。

### 1.2 コンセプト

**タグによる分かりやすい検索性**と、**物理的なフォルダーによる手動での管理性**の両立。

### 1.3 ターゲットプラットフォーム

- v1: Windows / macOS / Linux でローカル起動する Web アプリ（ブラウザ + ローカル API サーバー）
- 将来: リモート端末（iPad等）からの LAN ストリーミングを視野に入れる

### 1.4 技術スタック

- **フロントエンド:** React 19 + TypeScript + Vite
- **バックエンド:** TypeScript + Hono + Node（ローカル HTTP API サーバー）
- **音声再生:** HTML5 Audio + Web Audio API（フロントエンド完結）
  - 将来的に高度な機能（ギャップレス再生等）が必要になった場合、サーバー側への移行余地を残す
- **データベース:** SQLite（Drizzle ORM / better-sqlite3）
- **設計方針:** ルート（HTTP ハンドラ）は薄く保ち、ドメインロジックは core、データの出どころはアダプタ（real / fixture）に分離する（[ADR-0002](adr/0002-mock-as-fixture-adapter.md)）。ローカルUIとリモートUIで同じ API を共有できる設計。

### 1.5 対応音声フォーマット

HTML5 Audio（ブラウザの Chromium エンジン）のサポート範囲に準拠する。

**対応フォーマット:** MP3, AAC/M4A, WAV, OGG (Vorbis), FLAC, WebM/Opus

**非対応（将来検討）:** WMA, ALAC, DSD 等

DLsite作品の大半はMP3かWAV、FANZAはM4Aが多いため、上記で実用上ほぼカバーできる。非対応フォーマットのファイルはトラックリスト上でグレーアウト＋非対応アイコン表示とし、再生しようとした場合はエラーメッセージを表示する。

## 2. 作品の管理

### 2.1 作品の形式

作品は以下の2形式をサポートする。

**フォルダー形式:** 販売サイトからダウンロードしたファイル一式が1フォルダーにまとまった形式。フォルダー内には複数の音声ファイル、画像ファイル、PDF、テキストファイルが含まれる。1つの作品内にSE有無やフォーマット違い（mp3/wav）など複数のバリアントが存在するケースがある。

**単一ファイル形式:** 音声作品の全トラックを結合した1ファイル（mp3, m4a等）。チャプター情報に基づきトラックごとに再生する。

### 2.2 フォルダー構造

ユーザーが指定したルートフォルダー以下を管理対象とする。ルート直下に全作品がある必要はなく、ユーザーが自由なフォルダー構造で保存できる。

```
root/
├── dlsite/
│   ├── genre-a/
│   │   └── RJ1234/              ← フォルダー形式の作品
│   │       ├── SE有り/mp3/
│   │       ├── SE無し/mp3/
│   │       ├── cover.jpg
│   │       └── .meta.json
│   └── genre-b/
│       └── RJ5678/
└── fanza/
    ├── d00001.mp3                ← 単一ファイル形式の作品
    └── d00001.meta.json
```

### 2.3 作品の認識とスキャン

作品フォルダー内、または単一ファイルと同階層に**メタファイル（`.meta.json`）**を配置することで作品として認識する。スキャン時にメタファイルを検出し、内部DBと同期する。

### 2.4 作品IDと移動追従

メタファイル内にUUID形式の作品IDを保持する。ユーザーがフォルダーやファイルを物理的に移動・リネームした場合、スキャン時にIDで突合しDBのパス情報を更新する。DB上に存在するがスキャンで見つからない作品は「行方不明」ステータスとする。

## 3. メタデータ

### 3.1 二重管理方式

メタファイル（`.meta.json`）をSource of Truthとし、内部DB（SQLite）は検索・一覧のパフォーマンス用キャッシュとして運用する。DB側で編集した場合はメタファイルに即時書き戻す（DB編集とメタファイル更新を同一操作内で行う）。

アプリが起動していない間にユーザーがメタファイルを手動編集した場合、次回スキャン時にメタファイルの内容でDBを上書きする（メタファイルが常に勝つ）。

複数のメタファイルに同一UUIDが存在した場合、後に検出された方を新規UUIDで再採番し、ユーザーに通知する。

### 3.2 メタファイル フォーマット

```jsonc
{
  "id": "uuid-xxxx-xxxx-xxxx",
  "title": "作品タイトル",
  "urls": [
    { "label": "DLsite", "url": "https://www.dlsite.com/..." },
    { "label": "FANZA", "url": "https://www.dmm.co.jp/..." },
  ],
  "tags": ["R-15", "バイノーラル", "cv/ひなたゆか", "サークル/ほげふが"],
  "coverImage": "cover.jpg",
  "playlists": [
    {
      "name": "default",
      "tracks": [
        { "title": "導入", "file": "SE無し/mp3/01_導入.mp3" },
        { "title": "本編", "file": "SE無し/mp3/02_本編.mp3" },
      ],
    },
  ],
  "defaultPlaylist": "default",
  "createdAt": "2025-01-01T00:00:00Z",
}
```

`urls` は作品に関連するURLの配列。販売ページ（DLsite, FANZA）、作者のSNS、公式サイトなどを複数登録できる。通常は1〜2件、多い場合で3〜5件を想定。`label` はUI表示用の短いラベル。空配列の場合はURLなしとして扱う。

### 3.3 トラック定義

トラックのスキーマはフォルダー形式・単一ファイル形式で統一する。各トラックは「どのファイルのどの区間を再生するか」を表す。

```jsonc
// フォルダー形式: ファイルパスのみ（区間省略 = ファイル全体）
{ "title": "導入", "file": "SE無し/mp3/01_導入.mp3" }

// 単一ファイル形式: 同一ファイルに対して区間指定（秒）
{ "title": "導入", "file": "d00001.m4a", "start": 0, "end": 180 }
```

`start`/`end` が省略されている場合はファイル全体を再生する。これによりプレイヤー側のロジックは常に「指定ファイルの指定区間を再生する」の1つで統一される。単一ファイルのチャプター情報のソースは、ファイル内蔵のチャプターマーカーまたはユーザー手動設定とする。`tracks` が未定義の場合は1トラック（ファイル全体）として扱う。

チャプターの自動読み取りと手動設定UIは現在提供しない。単一ファイル形式を使う場合は、メタファイルのトラック定義で区間を指定する。

### 3.4 作品内プレイリスト

`playlists` 配列により、1作品に対して複数のトラック構成を持てる。SE有無やフォーマット違いなどのバリアントに対応する。

```jsonc
"playlists": [
  {
    "name": "SE無し",
    "tracks": [
      { "title": "導入", "file": "SE無し/mp3/01_導入.mp3" },
      { "title": "本編", "file": "SE無し/mp3/02_本編.mp3" }
    ]
  },
  {
    "name": "SE有り",
    "tracks": [
      { "title": "導入", "file": "SE有り/mp3/01_導入.mp3" },
      { "title": "本編", "file": "SE有り/mp3/02_本編.mp3" }
    ]
  }
],
"defaultPlaylist": "SE無し"
```

大半の作品ではプレイリストは1つのみの想定。データ構造は複数プレイリストに対応するが、管理UIは現在提供せず、プレイヤーは `defaultPlaylist` を再生する。

### 3.5 メタファイルの自動生成

スキャン時にメタファイルが存在しないが音声ファイルを含むフォルダーを検出した場合、メタファイルの自動生成を行う。自動生成はあくまで下書きであり、ユーザーが後から修正する想定。

**自動生成の内容:**

- `id`: UUID自動採番
- `title`: フォルダー名から取得（RJコードがフォルダー名に含まれる場合はDLsiteの作品コードとして認識・保持する）
- `urls`: 空配列（手動追加またはDLsite情報の適用時に設定する）
- `tags`: 空配列（手動追加に委ねる）
- `coverImage`: フォルダー内の画像ファイルを探索し、あれば最初の1枚を設定（なければnull）
- `playlists`: フォルダー内の音声ファイルをファイル名の自然順ソートで列挙し、`default` プレイリストとして生成。サブフォルダーが複数ある場合（`SE有り/`, `SE無し/` 等）は、最もファイル数が多いサブフォルダーの音声ファイルを `default` プレイリストとする

単一ファイル形式（ルートフォルダー直下等にある単独の音声ファイル）については、自動生成の対象外とする。ユーザーがUI上から手動でメタファイルを作成する。

### 3.6 DB固有の情報（メタファイルには保存しない）

以下の情報はDBのみで管理する。

- 作品の物理パス（スキャン時に更新）
- 再生位置と対象トラック（レジューム情報）
- 作品のステータス（正常 / 行方不明 / エラー）
- デフォルトプレイリストの合計再生時間（スキャン時またはメタデータ更新時に算出しキャッシュ）
- ブックマーク状態
- 最終再生日時

## 4. タグシステム

### 4.1 タグの種類

**フラットタグ:** 単純な文字列。ジャンルや属性を表す。例: `R-15`, `バイノーラル`, `触手`, `耳かき`

**Annotatedタグ:** スラッシュ区切りで構造的に管理するタグ。`カテゴリ/値` の形式。最初のスラッシュでのみ分割する（値にスラッシュが含まれる場合でも正しく処理される）。例: `cv/ひなたゆか`, `サークル/ほげふが`, `シリーズ/○○物語`

### 4.2 タグの運用

タグは作品の唯一の属性機構とする。サークル名、CV、ジャンル等も専用の属性ではなくタグとして管理し、1つの作品に多数のタグが付くことを前提とする。属性の構成はシステムが固定せず、ユーザーがフラットタグとAnnotatedタグを自由に追加・削除できる。

Annotatedタグの表示や操作上の特別扱いは、ユーザーが編集できるprefix定義で管理する。保護されたprefixのタグも編集できるが、削除時には確認ダイアログを表示する。

### 4.3 DB設計とパフォーマンス

DBは `works` / `tags` / `work_tags` の多対多リレーションでタグの永続化を行い、prefix定義はSQLiteの `tag_prefixes` テーブルで管理する。タグ検索・軸ファセット集計・スマートフォルダー評価そのものはSQLクエリに寄せず、アダプタが全件取得したデータをcoreの純粋関数（`applyWorksQuery` 等）に渡して処理する設計になっている。設計判断の経緯は[ADR-0004](adr/0004-core-functions-over-sql.md)を参照。数千作品規模ではこの全件メモリ処理で十分なパフォーマンスを確保できる。

### 4.4 DLsiteからのタグ自動取得

DLsiteの作品ページからスクレイピングしてタグを自動取得する。DLsiteのジャンルタグはprefix付きで変換する（例: `genre/耳かき`, `genre/バイノーラル`）。取得対象はタイトル、サークル名、CV、ジャンルタグ、カバー画像など。RJコードがフォルダー名に含まれる場合、DLsiteの作品コードとして扱う。

### 4.5 prefix定義（タグ設定）

prefix定義はAnnotatedタグの表示ラベル、色、軸レールへの表示、削除時の保護を表す設定データである。設定モーダルの「タグ設定」で追加・変更・削除でき、作品データに存在する未登録prefixも候補一覧から登録できる。APIは `GET/POST /api/tag-prefixes`、`PATCH/DELETE /api/tag-prefixes/:prefix`、`GET /api/tag-prefixes/candidates` を提供する。コードに特定prefixの分岐は持たせない。

初回のみ、次のprefix定義をseedする。`cv`（ラベル: CV、保護、軸表示）、`サークル`（保護、軸表示）、`シリーズ`（軸表示）、`カテゴリ`（軸表示）、`genre`（ラベル: ジャンル、軸非表示）。seed後の追加・変更・削除はユーザーの自由であり、すべて削除しても再seedしない。

分類軸は、軸表示がONのprefix定義を定義順に並べ、組み込みのタグ軸と追加日軸を加えて動的に構成する。追加日軸（軸ID: `year`）はタグ由来ではなく、作品の `addedAt` の年から導出する。

タグ保存時は `normalizeTag` により、prefixをtrimして小文字化し、値をtrimする。prefixの比較は大文字小文字を無視し、値は区別する。タグ絞り込みと軸ドリルはタグ全体の完全一致、グローバル検索ボックスだけは部分一致とする。

保護は編集禁止ではなくソフトガードである。保護されたprefixのタグを削除するときだけ確認ダイアログを表示し、ユーザーが確認すれば削除できる。設計判断の詳細は[ADR-0005](adr/0005-tags-as-sole-attribute.md)を参照。

## 5. プレイヤー機能

### 5.1 現在の再生機能

- 基本再生: 再生 / 一時停止 / 停止
- シーク（再生位置の移動）
- 音量調整
- トラック切り替え（前へ / 次へ）
- 作品内の連続再生
- ±10秒ジャンプ（ASMR作品では再生位置の微調整が重要なため、標準コントロールとして提供）
- ループ再生（現在のトラックをリピート）
- 再生速度変更
- L/R入れ替え
- A-Bリピート。A点とB点は再生中のトラックで設定し、トラック切り替え時に解除する。ポイントは永続化しない
- レジューム。再生位置とトラック番号をDBへ5秒間隔、一時停止時、停止時、トラック切り替え時に保存し、作品詳細の「続きから」で再開する
- Media Session API。対応ブラウザーでは作品・トラック情報、カバー、再生状態、再生位置をOSへ公開し、再生、一時停止、前後トラック、前後シーク、位置指定を受け付ける

### 5.2 プレイヤーの表示モード

プレイヤーは以下の3つの表示モードを持つ。

**プレイヤーバー（固定）:** 画面下部に固定表示されるコンパクトなコントロール。再生中のトラック情報、シークバー、基本操作、再生速度変更を備える。再生中は全画面で常駐する。

**プレイヤーバー（フローティング）:** 画面右下にフローティング表示し、ドラッグで位置変更できる表示方式。現在は提供しておらず、将来候補とする。

**フル画面プレイヤー:** プレイヤーバーの拡大操作で展開する。カバー画像、トラックリスト、L/R入れ替え、A-Bリピートを含む再生操作を表示し、閉じるとバーに戻る。

### 5.3 再生モード

**トラックモード:** メタファイルのプレイリスト（`defaultPlaylist`）に基づき、音声ファイルをトラックリストとして表示。トラック単位の再生が可能。

プレイヤー内のフォルダービューは現在提供せず、File Explorerモードを別画面として提供する。

### 5.4 将来候補

- フォルダービュー（作品フォルダーの物理構造を表示し、音声・画像・PDFを閲覧）
- A-Bリピートのポイント保存
- バックグラウンド再生 + グローバルホットキー
- ギャップレス再生（サーバー側での実装を検討）
- プレイリスト（作品横断）

## 6. エラーハンドリング

### 6.1 方針

エラーが発生した作品はライブラリ一覧のカバー画像上にエラーアイコンを重ねて表示し、ユーザーに修正を促す。作品詳細画面でエラーの具体的な内容を表示する。

### 6.2 検出するエラー

- **メタファイル不正:** JSONパースエラー、必須フィールドの欠落
- **音声ファイル欠損:** メタファイルで定義されたトラックの参照先ファイルが存在しない
- **音声ファイル破損:** 再生時にデコードエラーが発生した場合
- **非対応フォーマット:** サポート外の音声フォーマットのファイルがトラックに含まれる
- **カバー画像欠損:** `coverImage` で指定されたファイルが存在しない（この場合はデフォルトのプレースホルダー画像を表示）

## 7. UI / 画面構成

> UIの詳細デザインは実装済みのフロントエンド（`client/`）が正。`docs/design-system.md` はカラートークン等のデザインシステム規約として参照する。以下は画面構成・機能の要件。

### 7.1 画面一覧

**初期セットアップ画面:** 初回起動時のみ。ルートフォルダー選択→初回スキャン→Libraryモードへ遷移。

**Libraryモード（メイン画面）:** 固定4行グリッド（トップバー / アドレスバー / 本体 / 再生バー）＋左ナビの共通シェル。リスト表示は軸レール、コンテンツ列、プレビューの3ペイン、グリッド表示は軸レールと作品グリッドで構成する。詳細は7.2〜7.7節。

**設定モーダル:** ルートフォルダーの変更、フルスキャンの実行。

**新規作品検出ポップアップ:** 新しい作品が検出された際にタイトル確認・登録を行うダイアログ。

**フル画面プレイヤー:** プレイヤーバーの拡大ボタンで展開。カバー画像大表示、再生コントロール、トラックリスト全体。

### 7.2 共通シェル

ルートは固定4行グリッド。左ナビは本体・再生バーの左に縦に通る。

**トップバー（48px）:** ブランドマーク＋アプリ名 / 再生中インジケータ（パルス緑ドット＋ch数＋トラック名、再生中のみ）/ グローバル検索ボックス（⌘K・最小幅280px）/ スキャン・通知・設定の3ボタン。

**左ナビ（64px幅）:** Library / File Explorerのモード切替＋横断サーフェス（再生中 / 履歴 / お気に入り / ピン留め）＋ユーザーボタン。現在モードのボタンはアクセント淡色背景で表示。

**アドレスバー（38px）:** 戻る/進む/再読込 / パンくずナビゲーション / ビュー切替 / 並び替え。Libraryモードではリストとグリッドを切り替える。グリッド表示中は正方形タイルと原寸比率を保つジャスティファイド配置を選び、タイルサイズまたは行高さを調整できる。File Explorerモードはカラム表示を使う。

### 7.3 Libraryモード本体

軸レールは常に表示する。リスト表示ではコンテンツ列とプレビューを並べ、深い分類でもカラムを増やさずにドリルダウンをコンテンツ列内で完結させる。作品を表示できる軸やドリル先ではグリッド表示へ切り替えられる。グリッドは残りの本体幅を使い、作品選択時は右側にインスペクターを開く。

**col0 — 軸レール（192px固定）:** 作品を並べ替える軸（ピボット）を選ぶ。3グループに区切る。

- ビュー: すべての作品 / 最近再生 / 最近追加 / お気に入り / 未再生 / ファイル欠損
- 分類軸: 軸表示がONのprefix定義から動的に生成 ＋ タグ / 追加日（初期設定ではサークル / CV / シリーズ / カテゴリ）
- スマートフォルダー: ユーザー定義の保存クエリ一覧 ＋「新規作成」

各行にアイコン・名前・件数・chevronを表示。選択状態は `.is-on` スタイルで明示。

**col1 — コンテンツ列（300px固定）:** 選んだ軸の結果を表示する。

- 単純ビュー（すべて/最近再生/お気に入りなど）: 作品行（32pxサムネ＋タイトル/サブ/メタ/右メタ）を直接列挙
- 分類軸（サークル/CVなど）: まず軸の値一覧。値を選択するとその値で絞り込んだ作品一覧をドリルヘッダー付きで同列に積む（新カラムを開かない）
- タグ軸: チェックボックス＋色スウォッチ付きタグ一覧。複数チェックでAND積集合フィルター。上部にANDチップバンドを表示

**プレビュー（右・可変幅、最小360px）:**

- 作品選択時 → リッチ詳細（7.6節）
- 軸・分類一覧時 → AxisLanding（スライス概要＋一括操作＋上位作品グリッド）
- スマートフォルダー選択時 → ルールビルダー（7.5節）

**作品グリッド（可変幅）:**

- 正方形タイル: カバーを1:1でトリミングし、設定したタイル幅でCSS Gridに配置する
- ジャスティファイド: カバーの縦横比を保ち、設定した行高さを基準に各行を敷き詰める
- 表示モード、配置方式、サイズはブラウザーのローカルストレージに保存する
- ファセットの値一覧と未絞り込みのタグ軸ではグリッドを表示せず、リスト表示を維持する

### 7.4 検索・フィルタリング・並び替え

**グローバル検索:** トップバーの検索ボックス。タイトル・CV・タグ・RJコードの部分一致。⌘K でフォーカス。

**タグAND積集合:** タグ軸でタグを複数選択するとAND絞り込みが有効になる。選択中のタグをANDチップバンドで常に表示し、ヒット件数をリアルタイム更新する。結果はプレビュー側のAxisLandingに表示する。

**軸スライス:** 分類軸の値を選択することで、その属性に属する作品のみに絞り込む。

**並び替え:** 追加日（新しい/古い順）、タイトル順、再生時間順。将来: 最近再生した順、ランダム順。

検索・絞り込み・ソートは**サーバーサイドで処理**する（クライアントサイドの全件フィルタリングは行わない）。

### 7.5 スマートフォルダー

保存済みのルールセットにより条件に合う作品を動的に抽出する機能。

ルールは `WHERE / AND / AND NOT` の接続詞と「フィールド・演算子・値」で構成する。例: 「長さ ≥ 3時間」「カテゴリ = 環境音 OR ASMR」「タグ ∋ 睡眠用 OR 長時間」「AND NOT タグ ∋ R-15」。

スマートフォルダーを軸レールで選択するとcol1に該当作品を表示し、プレビュー側にルールビルダーを表示する。ルール編集で結果を即時再評価する。

### 7.6 作品詳細（プレビュー内）

プレビューペインに表示するリッチ詳細。ヒーロー（カバー大表示＋登録ステータス＋タイトル）、タグ（編集可）、アクション（再生 / お気に入り / …）、トラック表（番号/タイトル/長さ/行アクション）、関連作品（同サークル/同タグのカード）で構成する。

統計（再生回数/累計時間/完聴率）・レーティング（★）・メモは現在提供しない。

### 7.7 プレイヤーバー

画面下部に常駐。再生状態により3段階で切替。

- 停止時（56px）: 細いヒントバー（「クリックして再生」等）
- 1ファイル再生時（78px）: カバー（46px）＋トラック名/作品名＋♥ / ⏮⏯⏭ / 幅広スクラブバー（経過時刻＋つまみ＋総尺）/ ループ・音量スライダー・拡大ボタン
- マルチch ミキサー（96px）: 最大3ch同時再生。現在は提供せず、「重ねて再生」ボタンを無効状態で表示する

ASMR作品の特性を考慮し、シークバーは十分な幅と当たり判定を確保する。±10秒ジャンプ・ループ再生トグルを標準コントロールとして提供する。

### 7.8 テーマ

現在はライト基調（紙色トーン）のみを提供する。デザイントークン（`milli/tokens.css`）には `.ml-dark` 変種があるが、テーマ切り替えUIは将来候補とする。

## 8. スキャンと初期セットアップ

### 8.1 初期セットアップフロー

1. 初回起動時、ルートフォルダーが未設定であれば設定画面に誘導
2. ユーザーがルートフォルダーを指定
3. ルートフォルダー以下を再帰スキャン（自動実行）
4. メタファイルが見つかった作品はDBに登録/更新
5. メタファイルがない作品候補（音声ファイルを含むフォルダー）はメタファイルを自動生成（3.5項参照）
6. スキャン結果のサマリーを表示（登録済み: N件、新規生成: N件、エラー: N件）

### 8.2 スキャンのトリガーと実行モデル

**現在のスキャントリガー:**

- **手動トリガー:** 設定モーダル内に「フルスキャン実行」ボタンを配置。前回スキャン日時も表示する
- **ヘッダーの再読み込みボタン:** ライブラリ一覧のヘッダーに簡易的な再読み込みボタンを配置。軽量な再スキャンまたはDB再読み込みに使用する
- **初回起動時:** ルートフォルダー設定完了後に自動でフルスキャンを実行

**新規作品の検出:** スキャンで新しい作品候補が見つかった場合、確認・登録用のポップアップを表示する。ポップアップではタイトルを確認・編集できる。新規作品はスキャン完了後にDLsite一括取得へキューイングし、進捗を別のSSEチャンネルで通知する。

ファイル監視（watcherによるリアルタイム検知）、アプリ起動時の自動スキャン、差分スキャンは将来候補とする。

**スキャン中のUI:** スキャンはバックグラウンドで実行し、スキャン中もライブラリの閲覧・再生は可能とする。完了したら結果のサマリーをトースト通知で表示する。

進捗は `GET /api/scan/events` のSSEで配信する。接続中は15秒間隔のpingを送り、再接続時は実行中ジョブの直近の進捗、または直近の完了・エラーを1件リプレイする。クライアントはスキャン実行中だけEventSourceを接続し、進行フェーズと件数を画面に反映する。

### 8.3 再スキャン

再スキャンではメタファイル内の作品IDで突合し、フォルダーの移動・リネーム後も同一作品として物理パスを更新する。登録済みの作品IDが見つからない場合は「行方不明」ステータスにする。同じ作品IDを持つメタファイルが複数見つかった場合は、後から検出した作品を再採番する。

## 9. リモートストリーミング

### 9.1 概要

PC上のローカル API サーバー（Hono + Node）を常駐させ、iPadなど別端末のWebブラウザからLAN経由で音声をストリーミング再生する。基本的なローカルサーバー化（`server/`）は実装済み。

### 9.2 アーキテクチャ

```
[PC (Hono サーバー)]                   [iPad等 (Webブラウザ)]
┌──────────────────────┐               ┌──────────────────┐
│  TS バックエンド       │◄── HTTP ──────│  Web UI (React)  │
│  ┌─────────────────┐ │               └──────────────────┘
│  │ core / adapters │ │  ← ローカルUIとリモートUIで共有
│  │ (Hono routes)   │ │
│  │ SQLite           │ │
│  └─────────────────┘ │
└──────────────────────┘
```

### 9.3 今後の拡張項目

- 認証付きリモートアクセス（LAN外からのアクセス制限）
- リモート公開時の配信方式とアクセス制御

## 10. データのポータビリティ

- メタファイルが作品フォルダーと共に移動するため、フォルダーごとのコピーで情報が維持される
- DB + ルートフォルダーのコピーで別環境への移行が可能
- タグやメタデータの一括エクスポート/インポート機能は将来検討

## 11. 現在の保証範囲と将来候補

### 現在保証する仕様

- Libraryモードはリスト表示とグリッド表示を持ち、グリッドは正方形とジャスティファイドの2方式に対応する

- スキャン進捗とDLsite一括取得進捗をSSEで通知する

- `.meta.json` の編集、スキャン、DLsite情報取得、カバーのサムネイル生成、File Explorerによる物理フォルダー閲覧を提供する
