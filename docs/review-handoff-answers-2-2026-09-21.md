# w1:p4への追加回答

C1の実測は今回いただいた確認結果として扱います。私の先行レビューは静的確認でした。以下は設計上の推奨で、既存の決定事項ではありません。今回も getWork と workRefresh の実装を読み直しました。

案Aを推します。ただし「変更範囲が小さい」という採用理由を外すことと、案Bそのものを無効とすることは区別してください。値とrevisionが一致する案Bも整合性を満たせます。Aの積極的な理由は、正本の編集を投影の更新状態やメディアprobeの成否から独立させ、編集値の所有者を明確にできることです。

## 1. getWorkとlive probeの扱い

通常の getWork から、最新ファイルを読み直して sourceRevision を付ける処理は外すのが適切です。編集用snapshotが値とrevisionを一緒に返し、保存コマンドがそのrevisionをCASに使います。ダイアログだけでなく、インラインタグ編集、DLsite適用のpreviewなど、正本を書く全入口が対象です。

投影の由来を示すrevisionを閲覧DTOに残すなら、projectedSourceRevisionなど、用途が異なると分かる名前にします。閲覧値と最新sourceのrevisionを合成しないことが契約です。ハッシュ計算自体は編集snapshot、CAS、投影入力の確認に残ります。

一覧・詳細は、metadataについてはcatalogの投影を読み、bookmark/resumeなどはuser側の状態を読む契約を推します。情報量は違っても、タイトル・タグなどの正本と鮮度の意味を変えません。全フィールドを一つのsourceRevisionで代表させる必要はありません。編集画面のsource値が背後の一覧より新しいことは許容します。正本が壊れているときも、閲覧可能な投影と編集不能を区別できます。

resolveWorkWithLiveProbeは「現在のメディアを観測する」「詳細DTOを作る」「catalogの総時間を更新する」をまとめています。案Aだけからprobe能力の廃止は導けません。ただし、通常の getWork と正本保存の成功応答からはこの組合せを外すのを推します。

現在のメディア確認は、再生準備や明示的なメディア再確認・投影更新の責務として残します。再生開始時に実ファイルを検証することと、閲覧時にライブラリの投影を更新することは別です。詳細で最新の技術情報を見せたい仕様なら、独立したlive observationとして返す選択もあります。その場合も、閲覧を契機に総時間や検索所属が変わる契約にはしない方が分かりやすいです。

なお、probe cacheのメモ化まで禁止する意味ではありません。内部キャッシュへの書込みと、検索・ソート・集計に使う公開済みのcatalog値の変更は区別します。

## 2. 一つの原則として決めてよいか

妥当です。一つの設計判断として「正本の変更、投影の生成・公開、閲覧の責務を分離する」とまとめるのを推します。ただし、編集snapshotの取得は正本を読む経路なので、「すべての読取りはcatalog」という原則にはしません。

各責務の契約は分けて記述してください。

- 編集用読取り: 同じsource読取りから編集値とrevisionを返す。
- 正本変更: 対象identity/locationとrevisionを検証し、意図した変更を確定する。bookmarkなど別の正本の変更を混ぜない。
- 投影: 一つのsource snapshotを入力とし、sourceを変更せずcatalogを作る。古い入力を誤って最新として公開しないため、公開前の確認も設計する。
- 閲覧: 公開済みの投影とuser状態を読む。最新sourceを混ぜて編集の基準を偽装しない。
- 結果: source確定、catalogへの反映、その後の応答生成・再取得を区別する。

特に最後は、経路を分けるだけでは解決しません。現状は個別投影のcatalog公開後にlive probeを含むWork取得が続くので、その後の例外まで「投影失敗」に分類すると誤ります。保存結果には確定した編集snapshotを使い、Workの再取得成功をsource保存成功の条件にしない方がよいです。通信断は引き続き結果不明になり得ます。

一つのADRにまとめても、C1の整合性と投影非変更性、GETの副作用、結果分類は独立した受け入れ条件にしてください。一括実装を必須にする理由はありません。CQRSフレームワークや永続イベントログの導入も必要ありません。

## 3. 二つのsyncは同じ理由で撤去するのか

推奨案では両方とも現在の呼出し経路から外します。ただし理由と残す能力は異なります。

| 現在の処理 | 外す場所・理由 | 残す責務 |
| --- | --- | --- |
| getWorkのreadMetaSource | 通常閲覧から外す。投影値に最新revisionを付けない | 編集snapshot、CAS、投影入力の確認 |
| resolveWorkWithLiveProbe | 通常閲覧・保存成功応答から責務を分離する | 再生準備、明示的メディア再確認、必要なら独立したlive observation |
| syncDetectedRjCode | scan・再投影から外す。正本を観測する処理が正本を書き換えない | コード候補の検出と、登録・明示的編集コマンドでの確定 |
| syncTotalDurationSec | GETから外す。閲覧で公開済みの検索・ソート用状態を変えない | メディア観測を受けた投影更新での総時間計算・公開 |

syncDetectedRjCodeの「候補を検出する」能力は有用です。登録仕様で自動採用するなら、登録コマンドが一度の正本確定に含め、その確定済みsnapshotを投影へ渡します。既存作品の通常scanでは候補提示までに留め、適用は正本変更として扱います。「投影途中で書いてから読み直す」形には戻しません。

syncTotalDurationSecはmeta正本への書込みではなく、派生値のcatalog更新です。そのため「投影は正本を変更しない」だけを決めた場合、これをGETから外すことまでは論理的に必須ではありません。私が外すのを推す理由は、閲覧と投影更新も分け、詳細を開くだけで一覧の時間ソート・smart folder所属などが変わる隠れた契機をなくしたいからです。

総時間の更新自体を廃止するのではありません。明示した更新経路で、トラックの解決結果と総時間を整合する投影として公開し、関連するqueryを更新します。既存のscanに加え、再生準備で新しい観測を得たときに投影を更新する仕様も選べますが、その場合は更新契機と通知を明示してください。単にGETが呼ぶ別helperへ移すだけでは責務は分離できません。

以上の整理なら、scan→DLsite導線の再設計を先に完成させなくても、共有すべきsource・cache・投影の境界を決められます。
